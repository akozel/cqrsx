Command path: from a request to the commit

What happens to a command between the moment an entry point hands it to the engine and the moment the caller gets its answer: the lock of its aggregate, the attempt that loads, decides, plans and writes, the conflict retry, and the report to the observer. The answer means the event is in the journal; the views follow later, on the read path, and the tasks on the task path.

Guarantee
An accepted command wrote its one event, the snapshot when one was due and its tasks in one SQL statement: all of them or nothing.
One key at a time
Inside a process the commands of one aggregate queue on its lock, first in, first out; other aggregates run in parallel. Between processes only the optimistic check of the write decides.
Four answers
Accepted, rejected by the aggregate, conflict after the retries, or unavailable: not run, or its outcome unknown.

Overall diagram

The engine builds one StoreCommandExecutor per aggregate type and process, over a JournalEventStore; on PostgreSQL the store writes through PostgresEventRepositoryWithOutbox. Everything a command does happens inside that executor while it holds the aggregate's lock, except the report to the observer, which comes after the lock is released.

Entry point
Cqrs::source(name) gives a Source; execute and execute_with_id find the executor of the aggregate type and start a causation chain from this source. A task handler uses TaskContext::execute, which continues the task's chain.
Executor
StoreCommandExecutor: the lock registry, the conflict retry policy, one CommandAttempt for its life, the commit wake-up and the observer. A second executor of the same type is like a second process: it has locks of its own.
Aggregate lock
A private registry with one line per key that is busy right now; an idle registry is empty. Limits: LockLimits, defaults DEFAULT_LOCK_MAX_WAIT (1 s) and DEFAULT_LOCK_MAX_WAITERS (128).
Decision
Decide::decide(self, &state, &rules): a command decides one event or a rejection, pure and synchronous, on the committed state.
Task planning
The engine sets a ReactionsPlanner: each aggregate's Reactions::react is one match over its events that plans tasks through Then.
Store
JournalEventStore loads and commits; its repository PostgresEventRepositoryWithOutbox turns a commit into one statement (persist_with_tasks).

One command step by step

The demo books a seat: POST /api/concerts/{id}/commands with BookSeat. Its handler calls cqrs.source("ui").execute_with_id::<Concert>(command_id, &concert_id, command); the concert decides SeatBooked, and its reactions plan the task encore_record_ticket for the fan's ledger.

Steps 3 to 6 are one attempt. The aggregate never sees the outbox: it decides an event, and the reactions turn the event into tasks. A command never runs an effect itself; the effect is a task, and the task commits with the event or not at all.

Conflicts and retries

Two guards keep one aggregate consistent. Inside a process the lock orders the commands of a key, so commands of one executor never conflict with each other. Between processes, or between two executors of one type, nothing is shared but the database: the write is an optimistic check. The event's primary key is (aggregate_type, aggregate_id, sequence): of two commands that loaded the same state, the second finds its sequence taken. Without a snapshot the insert is ON CONFLICT DO NOTHING and the statement reports zero written rows; with a snapshot the snapshot's revision check fails first or the primary key raises an error that rolls the snapshot back with the event. Either way the attempt is AttemptError::Conflict and nothing of it was written.

  • What is retried. Only AttemptError::Conflict. A rejection is an answer; a storage error may hide a commit that happened, so it is never repeated (Unavailable).
  • How. AggregateConflictRetryPolicy::default: three attempts in all, a pause of 5 ms before the second and 10 ms before the third (doubling, at most 50 ms), each ±20 %. After the last conflict the answer is CommandError::Conflict.
  • Inside the lock. The retry runs while the command still holds its lock, so the next command of the key waits for it and never sees a half-done command.
  • Every attempt starts over. It reloads the aggregate, decides a clone of the command with a clone of its metadata and plans again from its own decision. The task ids do not change: they are derived from the command id, not from the attempt. Only the tasks of the attempt that committed reach the outbox.

Snapshots

With snapshots on (JournalEventStore::with_snapshots; the engine sets 10, DEFAULT_SNAPSHOT_EVERY), a load reads the snapshot and only the events after it. The snapshot is written by the commit that reaches the next multiple of the interval, in the same statement as its event: the state after the event, its last_sequence and a revision one higher than the stored one. The first snapshot of an aggregate is an insert; later ones update the row only where its revision is still the one the attempt loaded, which is a second optimistic check. A snapshot that no longer deserializes after a change of the aggregate's type is not an error: the load reads the whole history, and the next snapshot replaces the old row.

Guarantees

The numbers refer to guarantees.md, which names the code and the tests that hold each guarantee.

Guaranteed

One command of a key at a time G-01, G-02
Inside a process the commands of one aggregate run one by one, in arrival order; waiting is bounded by time and by the number of waiters.
A refusal runs nothing G-03
A command refused by the lock loads, plans and writes nothing.
One load, one decision per attempt G-04
The decision sees the committed state; the planner sees that state and the state after the event.
Bounded retry on a conflict G-05
Three attempts, each reloading the aggregate and planning its tasks again.
Atomic write G-06
Event, snapshot and tasks in one statement; at most one event per command; never a task without its event.
Tasks only from the committed attempt G-15
A rejected or conflicting attempt publishes no task; a refused plan writes nothing G-08.
Stable task ids G-13
Every attempt of a command plans the same ids; the same command id on the same aggregate cannot publish its tasks twice.
Wake before the answer G-09
A commit with an event wakes the processors of its aggregate type before the caller is answered.
Causation on every event G-12
Command, correlation and causation id, source and recorded_at in the metadata of every event.

Not guaranteed

Order between processes G-11
Two processes, or two executors of one type, meet only at the optimistic check: the loser retries, and after three conflicts it gets Conflict.
A known outcome after a storage error G-10
Unavailable may follow a commit that happened. The command is not repeated automatically.
A command id that deduplicates events
The command id makes the task ids collide, which fails a repeated write that plans tasks. A repeated command without tasks commits a second event; whether that is allowed is the aggregate's decision.
Reading your own write
The answer means the event is in the journal. The views are updated after it, by their processors.
Reports in commit order, always
The observer hears the commands of one aggregate in commit order, unless on a multi-threaded runtime the next command commits and reports between the release of the lock and the report.
