# Components and terminology

This is the current inventory and naming contract for `cqrsx`.
Names follow CQRS, DDD and Event Sourcing. A command expresses intent; an aggregate
checks invariants; a domain event records an accepted fact. A query reads a read
model. An event handler reacts to committed events; a projection builds a read model.
An aggregate event history remains the source of truth; snapshots are checkpoints.

CqrsFramework coordinates command handling, task planning and EventStore commit; the
command executor wakes the projection processors of its aggregate type, which read the
journal themselves, and, the lock released, tells its observer what became of the command.
The engine assembles these components from the modules of an application (Engine); it
adds no logic of its own. The logical command path and the projection path are:

```text
CommandExecutor → CqrsFramework → Command::decide(state, rules) → TaskPlanner → EventStore
       │                                   (one event)          (reactions → tasks)  ↓ commit (events.tx, outbox)
       ├─ the lock released: CommandObserver.command(report) → e.g. an activity feed
       └─ CommitWakeup.wake() ─► ProjectionProcessor ◄── page after the checkpoint ── events
                                        │ claim / extend / advance / release ── projection_checkpoints
                                        └─ delivery per key: a live batch or a rebuild
                                                 ↓                            ↓
                                           EventHandler          RebuildableProjection (history → document)
                                                 └───────── ViewProjection → View ──────┘
```

The durable task path is:

```text
Decision → ReactionsPlanner → NewTask → atomic outbox publication → TaskQueue
                                             ↓ claim
TaskRuntime → Worker → TaskExecutor → TaskDispatcher → TaskAdapter → TaskHandler(task, &TaskContext)
                 (one dispatcher,    ↓ settle (retry pause:        (dependencies, executors:
                  every worker)   TaskQueue    the type's policy)   ctx.execute → next command)
```

## Engine

`Cqrs` assembles an application from `Module` roots. `Setup` gives a root its prefixed variables and
engine settings. The engine has a closed set of backends: memory, PostgreSQL for the journal, and
PostgreSQL or MongoDB for views. With `http`, `serve` runs routes, workers and processors together.
The [typical scenario](typical_scenario.md#bootstrap-and-configuration) shows the assembly.

## Reactions

Each aggregate's `Reactions` synchronously and purely maps decided events to tasks. The event and its
tasks commit together. A command decides one event or a rejection; neither commands nor reactions run
effects. A module's application layer expresses its flow through the aggregate's reactions and task types.

## Task context and dependencies

The common handler gets its `TaskContext`, task and dependencies by type. Module registration supplies
dependencies and binds retry policies. `ctx.execute` continues task causation; handlers must tolerate
repeated delivery. Context and dependency types are described in the inventory below.

## Derive macros

`Command`, `Commands`, `Event`, `Events`, `Task`, `Rejection` and `task_handler` are re-exported by
`cqrsx`. See the [macro guide](../../cqrsx-macros/README.md) for their roles.

## Verification

Verification compares each view document to the fold of its applied prefix of journal events, and
reports differences separately from documents still behind. It does not resend outbox effects.

| Command decision | `command::decide::Decide<A>`, `command::CommandInfo` | A command decides itself on the committed state of its aggregate: `decide(self, &state, &rules) -> Result<Event, Error>`, pure and synchronous (no I/O, no clock: it runs under the aggregate's lock and again on a conflict retry), one event or a rejection, so D-02 (one event per command) is a rule of the type. | Rejection report | `rejection::Rejection` | A business refusal as the API and an activity feed report it: `code()`, the stable key the UI texts are looked up by, and `params()`, the values they interpolate (a JSON object). | Command implementation | `CommandExecutorCore` | The store-independent core of command execution: `PostgresCommandExecutor` and `TestCommandExecutor` are this core over a store of their own, not other kinds of executor. One long-lived executor per aggregate type and process, shared in an `Arc`; it owns the aggregate locks, so two executors of one aggregate type are like two processes. `new(framework, retry_policy, lock_limits)`: the core owns one `CqrsFramework` (store, rules, planner) for its life, since no store holds state of a command; conflict retry is bounded; `with_task_planner`, `with_commit_wakeup` and `with_observer` configure it. Every command runs under its aggregate's lock and waits for it at most the lock's `max_wait`; a refusal is `Unavailable`, logged as a warning, and loads, plans and writes nothing. The id's text (`AggregateKey::of`, its `Display`) is formatted once per command, for the lock's key, and every attempt borrows it from the lock. | Command observer | `observer::{CommandObserver, CommandReport, Outcome, AnyCommandObserver, AnyCommandReport, AnyOutcome}` | What an executor tells about every command it ran, e.g. for an activity feed: `command(&CommandReport)` with the aggregate's typed id, the command as the caller passed it, its metadata (the map every committed event stores) and the outcome its answer reports: `Accepted { tasks }` (the tasks published with its event), `Rejected(&error)`, `Conflict` or `Unavailable` (a refused lock, a failed store, a refused plan). Once per command, on the caller's task, after its attempts, once the lock is released and the wake-up sent, before the answer: the next command of the key never waits for the observer, the caller does. The reports of one key come in the order of its commits, unless, on a multi-threaded runtime, the caller's thread is preempted between the release and the call long enough for the next command of the key to commit and report first. One observer per executor (`with_observer` on the core and both presets; a second replaces the first). The core reads neither `CommandInfo` nor `Rejection`: an observer that names a command or a rejection bounds its implementation on them. An observer neither blocks nor panics: a panic is the command's (the commit stays, the caller panics, the lock is already free). The report's fields are public, so a test or an executor of one's own builds one by hand. An observer of every aggregate type (an activity feed in a module that names no aggregate) is an `AnyCommandObserver`: it hears `AnyCommandReport::of(report)`, the same report with the type erased: the aggregate's type, its id as its text and as `&dyn Any` (for an observer that knows the type), the command as `&dyn CommandInfo`, the metadata, and the outcome with the rejection as `&dyn Rejection`; the engine wraps it into the observer of each of its executors. |
| Task planning | `planner::{Decision, TaskPlanner, TaskPlanError}`; private `Planning` | The building block under an aggregate's `ReactionsPlanner`; planners and their tuples remain available to lower-level integrations. A decision supplies the typed id, committed state, state after the event, command, event and metadata. The planner runs after `decide` on each attempt, under the lock and before commit; tasks and event commit atomically. Causation stamps tasks and sets their IDs; invalid causation refuses a plan with tasks. A refused plan is `AggregateError::TaskPlan`, never retried. Tuples of two to eight planners run in order, concatenate results and stop on the first error; there is no blanket implementation for closures. |
| Reactions | `reactions::{Reactions, Decided, Then, ReactionsPlanner}` | What follows each event of an aggregate: `Reactions::react(&Decided, &mut Then)`, one `match` over the aggregate's events (a new event without a branch does not compile), pure and synchronous like a planner. `Decided` is what one attempt decided, read-only: `id` (`&A::Id`), `state` (the state after the event, the copy made for the planner; what the event removed is in the event), `command`, `event` (the one event, D-02) and `metadata()`; `Decided::new` builds one by hand for a test. `Then` collects the tasks in the order of the calls: `task(payload)` (eligible at once) and `task_after(delay, payload)` (`TaskSchedule::After`, relative: a reaction has no clock); the first task that cannot be built (a payload that does not serialize, a delay no schedule holds) refuses the plan and nothing after it is built; `into_tasks` hands them over. | Aggregate locks | `LockLimits`, `LockLimitsError`, `DEFAULT_LOCK_MAX_WAIT`, `DEFAULT_LOCK_MAX_WAITERS`; private `AggregateLockRegistry`, `AggregateLockGuard`, `LockRefused::{TimedOut, TooManyWaiters}` | Inside one process, commands to one aggregate key run one at a time in arrival order (a Tokio mutex per busy key, FIFO); different keys stay parallel. A registry entry lives while the key's lock is held or awaited, so memory follows the busy keys. Waiting is bounded by time (`max_wait`, default 1 s) and by the commands waiting per key (`max_waiters`, default 128, the holder not counted); past either the command is refused before it runs. The registry belongs to the command executor; public are the limits and their defaults. Ordering holds only within one executor: between processes, or executors of their own, the optimistic check and conflict retry still decide. |

| Repository-backed store | `PersistedEventStore`, `PersistedEventRepository`, `EventStoreAggregateContext` | Serialized repository access, aggregate reconstruction from history, snapshot acceleration and optimistic metadata; a clone clones the repository and shares the upcasters. A commit goes through `persist_with_tasks(events, snapshot, tasks)`: its default has no outbox, refuses non-empty tasks before any I/O and is otherwise `persist`; a repository with an outbox overrides it. | Snapshot decisions | private `SnapshotPolicy::{Disabled, Every}`, `snapshot_prefix_len`, `checked_counter_add` | Choose checkpoints and check event-sequence/snapshot-version arithmetic. The interval is a `NonZeroUsize` (`new_snapshot_store(repo, interval)`), so a commit never divides by zero. |

| Event position | `Position`, `FeedEntry`, `PersistedEventRepository::{feed_after, head, aggregate_ids_after}`; `PostgresEventRepository::count_after`, `DEFAULT_COUNT_AFTER_CAP` | The journal of one aggregate type in commit order. Every event records the id of the transaction that wrote it (`events.tx`, default `pg_current_xact_id()`, index `events_feed_idx`); that id is its position. `feed_after(after, limit)` returns the events above `after` and below the snapshot horizon (`pg_snapshot_xmin(pg_current_snapshot())`), ordered by (tx, aggregate id, sequence), at least `limit` of them but never a transaction cut in two; `head` is the greatest position written; `aggregate_ids_after` pages the ids of a type. Order contract: inside an aggregate the position order is the sequence order; between aggregates it is the order in which transactions got their ids, the same at every read. The horizon makes the feed gap-free: everything below it has finished, so a slower transaction with a lower id is waited for, never skipped. A writing transaction left idle anywhere in the cluster holds every feed until it ends (`idle_in_transaction_session_timeout`). Not a subscription: a reader polls or is woken. A position is a transaction id shared by the whole database, so the distance between two positions is no number of events: `count_after(after, cap)` counts the events of a type above a checkpoint on the feed index and stops at `cap` (default 100 000), which is how far a projection is behind. |
| Event reaction | `EventHandler` | Handle committed events outside their original transaction; a projection processor calls it per aggregate key, in journal order. It is not a CQRS query or a durable task. `name()` identifies it in the processor's failure reports (default: the type name; a `ViewProjection` is named after its view, `View::NAME`). `Arc<H>` is a handler too, so one instance can serve a decorator and a processor alike. `RebuildableProjection` extends it with `rebuild(id, history, prefix)`: replace the document with the fold of `history[..prefix]` and refuse a document that is ahead of the history; `ViewProjection` implements it, and `Arc<P>` like `Arc<H>`. |
| Read-model data | `View`, `ViewContext`, `StoredView` | Materialized read-model state and its repository ID, version and `last_sequence`: the last event of the view's aggregate applied to the document (0 for a new one). `View::NAME` names the view once: its collection or table, its projection (`EventHandler::name`) and its checkpoint row (`CheckpointKey::of::<V, A>()`); one view per name, stored, so it never changes. `View::update` is a deterministic fold without side effects; the engine hands it a key's events in order and once each, so a view needs no check of its own. `StoredView { id, version, last_sequence, view }` is a document as the queries answer it (`From<(V, ViewContext)>` for what `load_with_context` answers). |
| Read-model projection | `ViewProjection`, `ViewRepository`, `PersistenceErrorObserver` | Update stored views with conflict retry, read views, and observe borrowed persistence errors without consuming them. A repository answers three queries, alike in memory, PostgreSQL and MongoDB: one document by id (`load_with_context`), every document (`list`) and the documents whose id lies in `[lower, upper)` (`range`, none when `lower >= upper`), ordered by the bytes of the ids (the order of `str`) whatever the store's collation; a key prefix and a separator make a group of ids one range (`range("fox:", "fox;")`). A query of its own is a port of the application's. Contiguity rule: a document takes only event `last_sequence + 1` of its aggregate; older events are skipped, a batch that jumps ahead fails with `PersistenceError::SequenceGap` before anything is written, and a batch that applies nothing writes nothing. A repository stores `last_sequence` next to the version and writes both under one optimistic check. `rebuild` replaces a document with the fold of a prefix of its aggregate's whole history under the same version check and refuses a document that is ahead of the history it was given, so a reader with a stale history never rolls a document back. |
| Projection checkpoint | `CheckpointStore`, `CheckpointKey`, `LeaseToken`, `Claimed`, `RebuildState`, `RebuildRequest`, `RebuildRequests`, `CheckpointStatus`, `CheckpointError`; `PostgresCheckpointStore`, `PROJECTION_CHECKPOINTS_SCHEMA` (`projection_checkpoints`, `projection_rebuild_keys`); `MongoCheckpointStore`; `MemCheckpointStore` | One row per projection and aggregate type: the position up to which everything is applied, the owner's lease (`owner`, `lock_token`, `locked_until`, compared with the store's clock), the failures in a row with the last error, and the rebuild flag, pace and cursor. Every operation is one statement (in MongoDB one atomic statement on one document); every write of an owner carries its token, and `false` or `None` means the lease is lost; `advance` and `advance_rebuild` move only forward and accept a repeat (an owner that lost the reply repeats them; MongoDB accepts a cursor again by equality, see MongoDB read side). Requests come from any node: `request_rebuild(pace)` (one at a time, `AlreadyRunning` otherwise), `request_rebuild_key(id)` (one row per key, taken by the owner in request order, `Invalid` for a projection nobody registered); `status` is what an operator sees. A row that does not exist is registered again by the processor before its next claim. `CheckpointKey::of::<V, A>()` is the row of the view `V` over the journal of `A`: `V::NAME` and `A::TYPE`. PostgreSQL 18 or later (`RETURNING old`). |
| Verification | `projection::verify::{verify, Verification, Difference}` | D-20: every document of a view against the fold of the part of its aggregate's history it has applied. `verify::<V, A>(journal, documents)` (`V: PartialEq`) lists the documents first and reads the histories after them, the keys of the journal a page of 100 at a time (`aggregate_ids_after`, `get_events`), so a command committed in between shows as behind, never as a false difference; it needs no lock and may run during a rebuild. `Verification { checked, behind_documents, behind_events, differences }`: a document behind its history (or missing) is counted apart with the events it still has to take; a `Difference { collection: V::NAME, id, kind }` is `differs` (not the fold of its prefix, or ahead of its history) or `unexpected` (no history). | Projection processor | `ProjectionProcessor`, `ProcessorConfig`, `ProcessorConfigError`, `DEFAULT_PROCESSOR_*`, `MIN_PROCESSOR_LEASE`, `DeliveryLimits`, `DeliveryLimitsError`, `DEFAULT_DELIVERY_CAPACITY`, `DEFAULT_DELIVERY_MAX_BATCH`, `MIN_DELIVERY_CAPACITY`, `ProjectionObserver` with `Applied`, `Advanced`, `Failed`, `Rebuilt`, `RebuildReason`, `RebuildEvent`, `LeaseEvent`, `Waiting`; private `Owner`, `LeaseKeeper`, `HistoryRebuilder`, `Bounded`, `OrderedDelivery`, `DeliverySlot`, `DeliveryReceipt`, `DeliveryError::{Failed, Panicked, Stopped}`, `Done`, `Rebuilder` | Feeds one projection from the journal of its aggregate type: registers its checkpoint row before every claim (a row dropped with the read side comes back at the start of the journal, and every document is rebuilt) and claims it, extends the lease every third of it (lost when the store refuses or the local deadline passes), reads pages from the checkpoint and hands every key's events to the key's worker, moves the checkpoint behind the completed prefix of the window (`pages_in_flight = capacity − 1` pages may be in flight; inside a failed page the checkpoint stops before the transaction of the failed key), records a failed round and pauses `retry_base · 2^(n−1)` up to `retry_max`, and otherwise waits for a commit wake-up or its poll. The delivery holds a bounded buffer per key (`DeliveryLimits`: `capacity` jobs, default 64, at least 2; a live job is the key's events of one page) drained in delivery order by one worker per busy key, up to `max_batch` live jobs (default 32) per handler call, taken from what has gathered without waiting for more; a rebuild job is a batch of its own, so a rebuild and the live events of one key never run at once. The outcome reaches every receipt of the batch (`Done::{Applied, Rebuilt}`); a failure or a panic fails only its batch and is logged once with the processor's name and the operation (`deliver`, `rebuild`). It reads the journal only for a reason: a wake-up, the poll, a full page before (a page short of `page_size` is the end of what the journal shows), the window having been full, or the end of a pause; the receipt of a page is none. After a wake-up it waits `settle` (`with_settle`, default 0, at most the poll interval) before it reads, so the commits of a burst share a page: one read, one document write and one checkpoint move instead of one per commit, for a lag of that much. A document that refuses an event as a gap is healed in place: a rebuild of its key is queued behind the job and the page waits for it; no failure is counted. A rebuild of the whole journal walks the keys page by page (`rebuild_page`) between live pages and records its cursor; requested keys are rebuilt as they come; a rebuild reads the key's history, folds it and replaces the document (`RebuildableProjection::rebuild`: one write, or with a pace the first event and then one event per pause; a document newer than the history read makes it read again), and a paced rebuild stops at its next pause once the owner is gone. Writes are bounded by `concurrency`. On shutdown the owner waits up to one lease for what is in flight, moves the checkpoint and releases the row; a lost lease makes it claim again. Nothing is fatal: storage errors are logged and retried. The reading stops on a slow key only once the window holds `pages_in_flight` pages with that key. |

| SQL assets | `EVENT_STORE_SCHEMA`, `TRANSACTIONAL_OUTBOX_SCHEMA`, `PROJECTION_CHECKPOINTS_SCHEMA`, `REQUEUE_FAILED_OUTBOX_TASK` | Canonical schemas (the event store with `events.tx` and `events_feed_idx`, the outbox, the projection checkpoints with the requested rebuild keys) and operator requeue with stable task identity. |
| Process lifecycle | `host::lifecycle::{run, run_with_processors, Stopped, ReadSideStopped}`, `HostError`, private `StopReason`, `TaskRuntimeExit`, `shutdown_signal` | Signal/shared cancellation, inbound/runtime failure priority and coordinated drain. `run_with_processors` starts the projection processors beside `run` on the same token, only once everything that could fail at start has succeeded (a failed start holds no checkpoint), and awaits them after the inbound server and the task runtime: the processors finish what is in flight and give their checkpoints back; whatever stops first stops the rest. `Stopped` is the host's outcome and the read side's (`ReadSideStopped`, `the read side stopped: …`, a panicking processor); `HostError::log(message)` logs a failure without a panic payload. |
| Logging | `LoggingConfig`, `LoggingInitError` | Explicit process-wide subscriber installation; imports/defaults do not initialize it. |
| Technical support | private `diagnostics`, `env`, `locking::{lock, get_mut}`, `log_task_failure`, `log_projection_event`, `log_projection_failure`, `log_projection_batch_failure`, `log_projection_batch_panic`, `log_sqlx_failure`, `log_mongodb_failure`, `log_poisoned_lock`, `log_broken_invariant` | Sanitized diagnostics, confirmed task-failure logging shared by execution/recovery, and integer parsing. Projection logs carry the projection's name and the aggregate type, never an aggregate id: `info` on a lease acquired, lost or released, a rebuild started, finished or interrupted and a key healed; `warn` on a failed operation with its category and the failed rounds in a row; `error` once per failed or panicked batch of a key's worker (`log_projection_batch_failure`, `log_projection_batch_panic`), with the operation and the number of jobs. A failed storage operation of the PostgreSQL stores and of the MongoDB checkpoint store is one `error` with the operation, a fixed category and the SQLSTATE or the server's code, never the message. Every `std::sync::Mutex` of the crate is taken through `locking`: under it runs one short operation on a container, so a mutex poisoned by another thread's panic is logged (`error` with the lock's name), cleared and used on. A broken internal invariant (a closed semaphore, a lost delivery buffer, a worker without an index, a task payload that is not an object) is one `error` with the component and the invariant, and the operation fails or skips the step; the crate does not panic outside tests (clippy's panic lints are `deny`). |

a store that is never reachable; an in-memory JSON view repository with PostgreSQL version rules and the three queries in the order of the ids' bytes (`put(id, version, last_sequence, view)` and `clear` for tests); an in-memory `PersistedEventRepository` with the PostgreSQL write rules by meaning, an outbox (`outbox::<A>()`: `OutboxEntry` with the sequence of the write's last event; tasks need an event, an id once, a conflict publishes nothing; a task queue in memory over that outbox (`MemTaskQueue::new(journal)`): the statements of the PostgreSQL queue by meaning (a claim of the due tasks of a format by availability and id under a lease with a fresh token, a settlement fenced by the token of a live lease, a retry after its pause or a failure on the last attempt, the recovery of expired leases after the redelivery backoff), by the Tokio clock, every statement under the journal's lock, with `tasks()` to inspect and `lose_settlements(bool)` for a process that stops before its acknowledgements; | Private test support | inline CQRS fixtures, `task::test_support`, integration-suite fixtures, log capture and isolated-process helpers | Test-owned fakes and observation; no production service or singleton. |

There is no generic production Helper or Service to merge. Constructors and
fallible `with_*` methods provide fluent configuration; the engine's `Builder` is the one
builder, since an engine is assembled from modules it calls only when it is built.
`Arc` denotes shared ownership, not singleton lifetime. The logging subscriber is
explicit process-global infrastructure. PostgreSQL is the production event-store
backend; MongoDB is an optional read side (read models and projection checkpoints);
MemStore remains a public testing tool.

## Naming and integration rules

- Use Query for reading, EventHandler for reacting to events, ViewProjection for
  building a materialized View. A projection processor makes a view durable through its
  checkpoint; any other required reaction uses outbox tasks. A processor may hand a
  handler the same events again (a retry, a rebuild), so handling must be repeat-safe.
- A view document is the fold of `View::update` over the contiguous prefix
  `1..=last_sequence` of its aggregate's events and never anything else: the
  document, not the sender, decides what is new. Delivery may therefore repeat
  events and come from several processes (a rebuild next to live delivery, two
  nodes). A gap is an error that stops the document, not a document with a hole.
- Use flow for the business sequence of a module (its application layer: what follows
  each fact) and aggregate phases for domain consistency. A Module is one part of an
  application (`concert`, `fan`): what it plugs into the engine is registered in its root;
  modules see each other only through what they share. A Reaction is what follows an
  event of an aggregate (`Reactions`); it plans tasks, never runs anything. The Engine is
  the assembly of the components from the modules; it holds no logic of its own, and a
  backend is where the engine keeps its data (memory, PostgreSQL, MongoDB for the views).
- Position denotes the place of an event in the commit order of its aggregate type's
  journal, the id of the transaction that wrote it; Feed denotes reading that journal
  from a position, page by page, below the snapshot horizon. Neither is a subscription.
- Use Task for durable work and attempt for a claim. `TaskAttempt::task_id()` is
  stable; `number()` counts claims, including skipped invocations. Use
  `tokio_task_id` for Tokio identities and handles for spawned execution.
- Handler performs the operation, Adapter translates representations, Dispatcher
  routes, Executor bounds one invocation, Worker consumes repeatedly, Supervisor
  manages workers, Runtime assembles the subsystem. EventHandler and TaskHandler
  share the handler role with different inputs and delivery contracts.
- Lock (aggregate lock) denotes one command's exclusive, in-process hold on one
  aggregate key; commands awaiting it stand in the key's line. It is neither a Queue
  nor a Buffer: nothing is stored, and the waiting command is the request itself,
  which may give up. Nor is it a database lock: other processes meet only at the
  store's optimistic check.
- Processor denotes the reader of one aggregate type's journal that feeds one projection
  from a Checkpoint. Delivery is its local buffer per key, drained by the key's worker in
  journal order; a DeliveryReceipt is the outcome of one job. It is not a Queue: nothing
  in it is durable, the checkpoint is. Checkpoint is the durable row with the position; Lease is the ownership of
  that row for a time, renewed by the owner and compared with the store's clock; Rebuild is
  the replacement of one key's document from its history, through the key's worker; a
  Wake-up is a hint that the journal grew, not a delivery.
- One collection, one projection: a view names its collection and its projection once
  (`View::NAME`); two processors with two names over one collection write the same
  documents without knowing of each other, and the framework does not detect it.
- A view fed by several aggregates (one document built from the events of several keys,
  possibly of several types) is not what `ViewProjection` builds. It needs a `last_sequence`
  per feeding stream, a fold that gives the same document in any interleaving of the
  streams, one checkpoint per feeding aggregate type all feeding one handler, and a full
  rebuild that wipes once and then rebuilds every key of every type in parallel; a partial
  rebuild needs a reverse index the journal does not keep. The checkpoint rows and the
  document format do not stand in its way; the library ships the single-stream kind.
- A wiped document restarts its version, so a write of an owner that lost its lease and
  began before the wipe can land on the recreated document. Wipe is a demo operation: do
  not wipe under load with more than one node.
- MongoDB is only the read side: a checkpoint holds a position of the PostgreSQL journal,
  so the two databases are reset together (a journal recreated under an old checkpoint
  starts below it, and its events never reach the views). The read side alone is dropped
  documents first, checkpoints second; the processors rebuild everything by themselves.
- An event handler never executes a command, not even from a task it spawns. A
  projection writes its read model and nothing else: the follow-up would be recorded
  nowhere, lost by a crash before it commits and repeated by every rebuild that hands
  the handler the same events again. A follow-up command is an outbox task instead: the
  executor's TaskPlanner plans it from the command's decision, the task commits
  atomically with the command's events and only with them (an aggregate's Reactions plan it), and a TaskHandler executes
  the follow-up command, deciding from the current state whether it still applies. The
  framework does not detect a command executed from an event handler; this rule is the
  only guard.
- A command's future is not cancellation-safe while its commit is in flight: dropped
  then (an HTTP handler whose client disconnected), it may leave the events and the
  outbox tasks committed while the caller learns nothing, and the processors find the
  events at their next poll instead of at once. An application whose callers must know
  the outcome runs the command in a task of its own.
- Queue denotes durable ownership; Buffer denotes local waiting. The external
  environment names `OUTBOX_QUEUE_CAPACITY` and `OUTBOX_QUEUE_REFILL_PERCENT` map to Rust
  `buffer_capacity` and `buffer_refill_percent` and stay supported. SQL names, task formats and other environment keys are unchanged.
- Settings types name what they hold. Config is every setting of one component,
  handed to its constructor; it may hold other Configs and Limits. Policy chooses
  behaviour in a situation (`AggregateConflictRetryPolicy`, `ConnectionPingPolicy`, `TaskPolicy`).
  Limits is a set of bounds inside another component's settings (`LockLimits` in
  `PostgresCommandConfig`, `DeliveryLimits` in `ProcessorConfig`); the field and the
  getter take the type's name (`lock_limits`, `delivery_limits`). Each has a checking
  `new` that returns a `…Error` naming the value, getters, and a `Default` built from
  public `DEFAULT_*` constants in the value's own type; a lower bound is a `MIN_*`
  constant. An enum policy has its variants instead of `new`, and settings without a
  sensible default (`PostgresCommandConfig`, whose snapshot interval the application
  chooses) have no `Default`. A Config whose values are typed checks nothing: `PostgresCommandConfig::new` takes a
  `NonZeroUsize` interval and returns `Self`. The engine's `Settings` hold many values: its checking `new`
  takes those checked together and fluent `with_*` set the others; `from_lookup` reads them
  all and its errors name the variable. Known deviations, to align: `AggregateConflictRetryPolicy`
  (no constants, no getters), `TaskStorageConfig` and `TaskWorkerPoolConfig` (private
  constants), `LoggingConfig` (no constant, an infallible `new`).
- Factory constructs components; Plan precedes effects; Result/Report describe
  confirmed outcomes. Recovery scheduling is not successful task execution. A Planner
  plans tasks from a Decision before the commit (`TaskPlanner`); a `CommitReport` is
  what the commit confirmed. A command decides its event, never tasks; the aggregate's
  Reactions say what follows each event (`ReactionsPlanner` is their planner).
- Outbox denotes atomic event/task publication and its schema/environment contracts.
  Task execution and settlement use separate commits; they are not a UnitOfWork.
- Prefer `task::runtime::prepare` or
  `postgres::task_runtime::prepare_task_runtime`. Preparation keeps the one dispatcher
  every worker shares (assembled by `TaskHandlers`) and the policies of the task types, and
  performs no storage/background work. Run starts the workers on first poll.
  Low-level `task::runtime::supervisor::run` accepts custom executors using the same
  lifecycle engine. Import contracts from their defining modules.
- A task handler is a function with `#[task_handler]` next to its task: its parameters
  are the task, the context and the dependencies, provided by type; the next command is
  `ctx.execute::<A>(..)`, never an executor the handler holds. It answers done, retry or
  fail, and never a pause: the policy of the task's type is bound at assembly.

## Local PostgreSQL

From the workspace root, run `docker compose up -d postgres` (or
`podman compose up -d postgres`). Compose initializes the event-store, outbox and
projection-checkpoint schemas in a dedicated `cqrsx` database and persistent volume. Initialization SQL
runs only for a fresh volume. Tests provision their own PostgreSQL and MongoDB
containers (`tests/support/{postgres,mongo}.rs`, host ports leased by
`tests/support/port_lease.rs`).

Connect with `postgresql://cqrsx:cqrsx@localhost:5433/cqrsx`.
Set `CQRSX_POSTGRES_PORT` to override the default host port `5433`.
The credentials are intended for local development.
Stop PostgreSQL with `docker compose down`; the database volume is retained.
