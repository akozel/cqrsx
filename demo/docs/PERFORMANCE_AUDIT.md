## 1. Коротко

1. **Ёмкость всей системы ограничивает outbox, а не команды, и короткие прогоны этого не видят.** За окно прогона `02b`
   (14 с вместе с разогревом) касса приняла 49.5 тыс. броней, а outbox закрыл 2.6 тыс. задач из примерно 99 тыс.: на
   каждую бронь их две. Остальное слилось уже после окна. На горячем ключе за окно закрывается полторы задачи из
   двух. Устойчивую пропускную способность (бронь, задача, команда `Fan`, письмо) покажет только прогон до 5 минут с
   постоянной входящей частотой ([04/02](backlog/04_operation_costs/02_sustained_capacity_run.md), бывшая 02/10).
2. **Самая дорогая операция базы — закрытие задачи (settle), и дорогая она из-за выбора индекса.** Условие
   `status = 'processing'` подходит под частичный индекс `transactional_outbox_expired_idx`. PostgreSQL ищет строку по
   нему, а не по первичному ключу, и читает все мёртвые записи этого индекса. При сливе settle — 73 % времени SQL,
   0.40 мс и 92 блока на вызов. Условие лишнее: `lock_token = $2` уже гарантирует его через CHECK таблицы. Без него в эксперименте:
   0.27 → 0.07 мс, 122 → 17.5 блока. Это одна строка кода (**Q-1**).
3. **Потолок горячего ключа — время, пока команда держит блокировку: около 1.45 мс.** За это время идут три оператора SQL.
   Два из них — снапшот и события после него — повторяют загрузку, которую предыдущая команда в той же очереди только что
   держала в памяти. Если передавать состояние следующей команде в очереди, останется один оператор (**C-1**).
4. **Каждый оператор SQL по-прежнему стоит два обращения.** Пакетов на оператор 4.03–4.06: при возврате соединения в пул
   sqlx пингует его. В sqlx 0.9.0 то же самое (**N-1**).
5. **Остаток на горячем ключе из тикета 03/04 в основном объясняется учётом, а не ценой процессора.** Метрики «на
   команду» делят на принятые команды всю работу окна. С процессором цепочка outbox успевает за окно больше: 1.26 → 1.45
   закрытых задач на команду. Отсюда большая часть «+11 % CPU PostgreSQL и +7…10 % WAL» (**M-1**).

## 4. Карточки

### Q. Очередь outbox

#### Q-1. settle идёт не по тому индексу

**Сейчас.** В settle сначала выбирается строка задачи: `cqrsx/src/postgres/task_queue/settlement.rs:76`,
`WHERE id = $1 AND lock_token = $2 AND status = 'processing'`. Условие `status = 'processing'` совпадает с предикатом
частичного индекса `transactional_outbox_expired_idx (locked_until, id) WHERE status = 'processing'`
(`cqrsx/sql/002-transactional-outbox.sql:33`). По статистике в нём мало строк (только задачи в аренде), а `id = $1`
годится как условие на его второй столбец. Поэтому PostgreSQL 18 выбирает его, а не первичный ключ. План из
эксперимента (и обобщённый, и для конкретных параметров):

```text
CTE owned
  ->  LockRows
        ->  Index Scan using transactional_outbox_expired_idx on transactional_outbox
              Index Cond: (id = $1)
              Filter: ((lock_token = $2) AND (status = 'processing'::text))
```

Пока идёт слив, в этом индексе лежат записи всех задач, уже закрытых с прошлого VACUUM. Каждый settle читает их все.
Пример: слив всплеска броней, 8 воркеров закрывают 2 000 задач/с. Через 10 с в индексе 20 тысяч мёртвых записей, и
каждый следующий settle проходит их заново.

**Что видно.**
- Стенд: при сливе 0.402 мс и 92 блока на вызов, 73 % времени SQL; на горячем ключе 0.202 мс и 42 блока, 35 %.
- Эксперимент: текущий settle — 0.273 мс и 122 блока, без условия на `status` — 0.071 мс и 17.5 блока.

**Предлагаю.** Убрать `AND status = 'processing'` из выборки `owned`. Смысл не меняется: по CHECK таблицы
(`sql/002…:23`) `lock_token` не `NULL` ровно у строк в `processing`, поэтому `lock_token = $2` уже означает
`processing`. Комментарий в коде должен объяснять, почему условия нет, иначе его вернут. Тест — существующие тесты
fencing settle. Дополнительно можно сделать интеграционный тест на `EXPLAIN (FORMAT JSON)`: settle идёт по
`transactional_outbox_pkey`. Образ PostgreSQL на стенде и в тестах закреплён (18.6).

**Эффект.** Оценка по долям из §2:
- при сливе время SQL −50…55 %;
- на горячем ключе время SQL −25 %, CPU PostgreSQL на команду −10…15 %.

Скорость слива в `db` должна заметно вырасти. Насколько — покажет замер `03a-drain-w8` в профиле `db` до и после.

**Дальше, по желанию.** Одиночный `UPDATE` без CTE и без `FOR UPDATE` даёт 0.061 мс против 0.071, ещё −14 %. Но тогда
надо заново обосновать порядок «сначала блокировка, потом проверка времени». Комментарий в `settlement.rs` защищает от
случая, когда держатель блокировки отпустил строку неизменённой. В этой схеме строку в `processing` без изменения не
блокирует никто: восстановление аренды меняет каждую строку, которую блокирует. Решение за владельцем cqrsx.

#### Q-2. Выполненная задача удаляется

**Сейчас.** Задача за жизнь пишет строку трижды: вставка, claim, settle. Settle — это `UPDATE` с новой версией строки
и новой записью в первичном ключе, потому что меняются столбцы индексов и их предикатов (HOT невозможен). Выполненные
задачи остаются в таблице навсегда (бывшая 02/11). Таблица растёт,
и вместе с ней дорожает X-ray (D-1).

**Предлагаю.** Settle `Completed` — это `DELETE … WHERE id = $1 AND lock_token = $2 AND locked_until > clock_timestamp()
RETURNING …`. Повтор и `failed` остаются `UPDATE`, `failed` хранится для оператора, как сейчас.

Эксперимент, 80 тыс. settle (после Q-1):

| | Среднее, мс | Блоков | WAL на вызов | Таблица после слива |
|---|---|---|---|---|
| `UPDATE` в `completed` | 0.071 | 17.5 | 267 Б | 86 МБ, 80 тыс. живых строк |
| `DELETE` | 0.0135 | 6.5 | 66 Б | 38 МБ, 0 живых строк |

Это закрывает 02/11 без фоновой уборки.

**Что нужно решить.**
- **X-ray** показывает последние строки outbox и счётчики по статусам. Выполненные задачи из него исчезнут: о них
  будет говорить журнал, то есть событие `TicketRecorded` и письмо в ящике.
- **Хуки стенда** считают `outbox_completed` через `count(*)`. Их надо перевести на `pg_stat_user_tables.n_tup_del` или
  на счёт settle.
- **Режим.** Сделать удаление единственным поведением или политикой `CompletedTasks::{Delete, Keep}`. Правило
  «меньше режимов» говорит за первое.

#### Q-3. Закрывать задачу вместе со следующим claim

**Сейчас.** Каждая задача — свой claim и свой settle. Claim пакетный, но пачка не больше свободного места в буфере.
На стенде и в демо буфер равен числу воркеров (`OUTBOX_QUEUE_CAPACITY = 2`), а воркер будит producer сразу, как взял
задачу. Поэтому на горячем ключе claim забирает 1.03 задачи за вызов: два оператора на задачу.

**Предлагаю.** Воркер не закрывает задачу сам, а отдаёт итог producer. Следующий claim закрывает накопленные задачи и
берёт новые одним оператором: CTE `settled AS (UPDATE/DELETE … FROM unnest($ids, $tokens, …))` перед `ready`. Если
забирать нечего, producer закрывает накопленное сам, не позже чем через несколько миллисекунд.

**Почему.** Около 0.1 мс CPU базы на оператор уходит на накладные расходы (§2.1), и счёт операторов здесь главное.
Обсуждение [05](discussions/05_outbox_task_throughput.md), §4 п.6 («пакетная обработка не нужна, claim уже пакетный»)
замеры не подтверждают: учёт очереди — 86 % времени SQL слива.

**Цена и риски.**
- Итог каждой задачи (`OwnershipLost`, `Failed`) возвращается воркеру или в лог.
- Локальный бюджет аренды (`lease_budget.rs`) должен учитывать задержку закрытия.
- Нужна модель сбоев для «закрыто вместе с claim».

**Эффект.** Оценка: на горячем ключе −1.5 оператора на принятую команду (−16 %), при сливе −30…40 % операторов на
задачу.

#### Q-4. Голова очереди и autovacuum

Claim при сливе читает 112 блоков ради 2.6 строки. В эксперименте 124 из 132 буферов уходят на просмотр начала
`transactional_outbox_ready_idx`. Там лежат версии `pending` уже забранных задач, мёртвые до VACUUM. При
`autovacuum_naptime` по умолчанию (60 с) быстрый слив почти всё время идёт по раздутой голове очереди. Q-2 этого не
меняет: мёртвую версию оставляет сам claim.

**Предлагаю** в рамках [04/09](backlog/04_operation_costs/09_postgres_long_run_settings.md) (бывшая 02/13):
- параметры хранения таблицы в схеме cqrsx: `autovacuum_vacuum_scale_factor = 0`, порог в тысячи строк,
  `autovacuum_vacuum_cost_delay = 0`;
- `autovacuum_naptime` порядка секунды на стенде;
- замер на `03a` и на 5-минутном прогоне.

Пачка claim больше 2 тоже размазывает этот просмотр по большему числу задач. Эксперимент оценить VACUUM не смог:
длинный `CALL` сам держал горизонт очистки. Нужен стенд.

#### Q-5. UUIDv7 для id задач

`cqrsx/src/task.rs:60` создаёт id через `Uuid::new_v4()`: вставки ложатся в случайные страницы первичного ключа. На
коротком сливе разницы нет: таблица целиком в кэше, в эксперименте v4 и v7 совпали в пределах 1–2 %. Польза появится
при длинной работе (локальность страниц, меньше полных страниц в WAL после контрольной точки). Ещё одна польза — для
X-ray: «последние задачи» становятся чтением ключа по убыванию (D-1). Цена — одна строка, приоритет низкий.

### C. Путь команды

#### C-1. Следующая команда в очереди берёт состояние у предыдущей

**Сейчас.** На горячем концерте всегда около 39 команд ждут блокировку. Каждая, получив её, читает снапшот, читает
события после него (в среднем 4.5), разбирает JSON зала (до 40 мест, 2–5 КБ) и применяет события. Всё это предыдущая
команда держала в памяти долю миллисекунды назад.

**Предлагаю.** Запись реестра блокировок (`cqrsx/src/cqrs/command/locks.rs:119`) живёт, пока у ключа есть держатель или
очередь. Пусть она переносит закоммиченное состояние: контекст плюс применённые события, как их применяет путь
снапшота в `persisted.rs`. Следующая команда пропускает оба чтения и решает на нём. Запись по-прежнему идёт с
оптимистической проверкой: номер события и версия снапшота. Если писала другая нода, будет конфликт, состояние
выбрасывается, и команда загружает агрегат как сейчас.

Правила:
- состояние передаётся только после успешного коммита; любая ошибка или конфликт его выбрасывает;
- после конфликта состояние выключено до закрытия очереди ключа;
- когда очередь пуста, запись реестра закрывается вместе с состоянием. Устаревшего кэша для простаивающих ключей нет,
  память растёт только с числом занятых ключей.

**Чем это отличается от 02/07.** Тикет 07 отложен с доводом «дочитка хвоста остаётся в любом случае», и это вывод
задачи 05, сделанный до блокировок. Под блокировкой агрегата (08a) внутри ноды гонки нет. Условие возврата, записанное
в 07, теперь выполнено: «одна нода владеет агрегатом, кэш всегда свежий, хвост можно не дочитывать и полагаться на
конфликт при записи». Это верно для одной ноды и для `BALANCE=key`.

**Эффект.** Оценка: из критической секции уходят два обращения из трёх и разбор снапшота. Удержание 1.45 → ~0.8–1.0 мс,
потолок ключа ~700 → ~1 000–1 250 принятых/с. На PostgreSQL — минус два оператора на каждую команду из очереди.

**Риски.**
- `round_robin` на двух нодах: после каждой записи соседа состояние устарело, будет конфликт и перезагрузка, лишняя
  неудачная вставка на команду. Горячему ключу и так нужна привязка по ключу: 08b, две ноды по очереди −22 %.
- `EventStore::commit` должен вернуть новый контекст, или его оставит у себя хранилище.
- Модель свойств блокировок надо расширить.

Сначала M-3.

#### C-2. Задачи outbox из принятого события

**Сейчас.** Задачи привязываются к команде до её выполнения: `FrameworkFactory::framework(tasks)`,
`cqrsx/src/cqrs/command/executor.rs:16` («called once per command, before its first attempt»). Задаче отмены нужны
данные из состояния (id брони, сумма возврата). Поэтому демо читает концерт до команды
(`demo/back-end/src/application/concert/cancel_booking.rs:59`): два оператора и разбор снапшота вне блокировки на
каждую отмену. На горячем ключе отмена — половина команд: 4 775 лишних загрузок за окно, −9 550 операторов из 86 167
(11 %).

При этом событие `BookingCancelled` уже несёт всё, что нужно задаче: место, фаната, id брони, id отмены, возврат
(`domain/concert/events/booking_cancelled.rs`).

**Предлагаю.** Второй способ передать задачи: функция от решённых событий, `Fn(&[A::Event]) -> Result<Vec<NewTask>, _>`.
Её вызывают после `handle` на каждой попытке, внутри блокировки и до коммита. Демо строит `encore_record_cancellation`
из `BookingCancelled`. Попутно уходит окно между предварительным чтением и коммитом.

**Цена.** API исполнителя (`CommandExecutor`, `CommandExecutorCore`, `TestCommandExecutor`), demo `cancel_booking.rs`,
тесты.

#### C-3. Создание агрегата без чтения

**Сейчас.** Анонс концерта загружает агрегат, которого нет: снапшот (пусто), события после 0 (пусто), CTE. Три оператора,
из них два заведомо пустых. В `02a` профиля `db` предел — PostgreSQL (174–197 % из 200 % в прогонах
`perf-db-*05-02a-*`, коммит `a747f06`).

**Предлагаю.** Команда, создающая поток, пропускает загрузку и решает на `A::default()` с номером 0. Её объявляет
агрегат, например `fn creates(command: &Self::Command) -> bool`, или вызывает отдельный метод исполнителя. Коммит пишет
событие № 1 с обычной проверкой. Если поток уже есть, вставка конфликтует, и команда идёт обычным путём: загрузка,
решение, домен отказывает «концерт уже анонсирован». Этот конфликт — без паузы политики повторов.

**Эффект.** `02a`: 3 → 1 оператор на анонс. Оценка: +50…100 % анонсов/с в `db`, пока предел не перейдёт к MongoDB или
бэкенду. На горячем ключе эффекта нет.

**Риск.** Решение агрегата на состоянии по умолчанию должно совпадать с решением на загруженном пустом потоке. Это
верно по построению: загрузка пустого потока и даёт `A::default()`.

#### C-4. CPU бэкенда на команду

Три мелкие траты на каждую команду. Часть из них — внутри блокировки горячего ключа.

- **`SqlQueryFactory` собирается заново на каждую команду.** `PostgresFrameworkFactory::framework`
  (`postgres/command.rs:79`) → `PostgresEventRepositoryWithOutbox::new` (`outbox.rs:32`) → `PostgresEventRepository::new`
  → `SqlQueryFactory::new` (`event_repository.rs:131`): 12 `format!` строк SQL на команду. Собрать один раз в фабрике и
  делить (`Arc`).
- **Клон снапшота.** `TryFrom<SerializedSnapshot>` (`store/persisted.rs:593`) копирует всё дерево JSON перед разбором:
  `serde_json::from_value(snapshot.aggregate.clone())`. Достаточно передать его по значению.
- **JSON через промежуточный `serde_json::Value`.** Чтение: текст → `Value` → структура
  (`serialized_event.rs:118`, `:125`). Запись: структура → `Value` → текст (`serialized_event.rs:98–99`,
  `persisted.rs:534`). Можно разбирать прямо из текста (`sqlx::types::Json<…>`, `RawValue`), а `Value` строить только
  когда подходит upcaster. Это меняет API `SerializedEvent` и `SerializedSnapshot`, что допустимо.
- Мелочь: `EventSink::write` клонирует каждое событие и берёт асинхронный мьютекс (`event_sink.rs:24`).

Эффект не измерен. Проверить в профиле `app` на `02b` и на горячем ключе: CPU бэкенда на команду. Первые два пункта
почти бесплатны.

#### C-5. Групповая запись (02/09) — после C-1

Когда команда держит блокировку и состояние (C-1), следующий шаг — решить в памяти сразу несколько ждущих команд ключа и
записать их события одним CTE. Задача сейчас дешевле, чем когда писался 09:
- обработчиков в команде больше нет (03/05);
- процессор уже группирует ленту по транзакциям (`processor/owner.rs:81`, `Transaction`).

Осталась главная цена: метаданные и задачи на каждую команду в одной записи, частичные отказы, повтор пачки, правило
`WritePlan` «одно событие на запись» (`outbox/write_plan.rs:91`). Брать, только если горячим ключам мало C-1.

### N. Соединения

#### N-1. Пинг при возврате соединения (02/16)

**Что видно.** Пакетов на оператор 4.03 (`02b`) и 4.06 (горячий ключ): два пакета сам оператор, два — пинг, когда
соединение возвращается в пул. Пинг безусловный и в sqlx 0.8.6, и в вышедшем 2026-05-06 sqlx 0.9.0
(`sqlx-core-0.9.0/src/pool/connection.rs:314`). Вариант «В» тикета 16 (обновить sqlx) проверен и не помогает.
Кроме пинга, каждый возврат порождает задачу tokio (`spawn(return_to_pool)`). Это CPU бэкенда на каждый оператор.

**Варианты.**

| Вариант | Что убирает | Цена |
|---|---|---|
| Б′. снапшот и события после него читать на одном соединении | 1 пинг из 3 на команду | низкая; соединение не держится во время `handle` |
| Б. одно соединение на команду (загрузка и запись) | 2 из 3 | соединение держится во время `handle`: в демо это микросекунды CPU, в общем случае риск для пула (М2 эпика 02) |
| Г. sqlx с отключаемым пингом при возврате: PR в sqlx, до слияния `[patch.crates-io]` с форком | все пинги при возврате: команды, очередь, процессоры | поддержка форка до слияния |

После C-1 горячий ключ и так делает один оператор на команду из очереди. Ожидаемый эффект по аналогии с задачей 02
(пинги при выдаче): −4…7 % CPU PostgreSQL на команду и минус половина пакетов.

### P. Проекции

#### P-1. Новый документ витрины без чтения

**Сейчас.** `ViewProjection::apply_events` (`cqrsx/src/cqrs/projection.rs:509`) всегда читает документ (`find_one`) перед
записью. Для нового концерта чтение ничего не находит, потом идёт `insert_one`: две операции MongoDB на документ. В
профиле `full` с wrk потолком анонсов была MongoDB, около 13 тыс./с (README эпика 02).

**Предлагаю.** Если пачка ключа начинается с события № 1, первая попытка пропускает чтение и вставляет документ: контекст
с версией 0 даёт `insert_one`. Дубликат ключа означает, что документ уже есть: повторная доставка после падения или
пересборка рядом. Тогда обычный путь: чтение, пропуск уже применённого по правилу непрерывности.

**Эффект.** `02a`: 2 → 1 операция MongoDB на анонс, плюс сдвиг закладки раз на страницу. Цена низкая.

#### P-2. Пул MongoDB против параллельности процессоров

Демо создаёт клиента MongoDB без `max_pool_size` (`demo/back-end/src/process.rs:199`). У драйвера по умолчанию 10
соединений (`mongodb-3.9.1/src/cmap.rs:50`). Каждый из двух процессоров пишет до 16 документов одновременно
(`DEFAULT_PROCESSOR_CONCURRENCY`, `processor/config.rs:20`). Через тот же клиент идут закладки, аренды, статус и чтения
HTTP. На страницах с сотнями ключей (`02a`, `02b`) до 32 операций ждут 10 соединений.

**Предлагаю.** `ENCORE_MONGODB_POOL_SIZE`: по правилу «каждое значение — переменная», с умолчанием не меньше суммарной
параллельности. Замер `02a` в `full` и `02b` при 10, 32 и 64. Это гипотеза.

#### Не советую сейчас: кэш документа у рабочего ключа

Он сэкономил бы `find_one` только ключам, у которых в буфере стоит следующая пачка. На горячем ключе это 70–100 чтений
в секунду, а MongoDB там не предел: она занята на 0.34 ядра из трёх.

### M. Замеры

#### M-1. «На команду» в сценариях с цепочкой

Метрики «на команду» на стенде — вся работа окна k6, делённая на принятые команды `Concert`. Но цепочка (бронь →
`encore_record_ticket` → команда `Fan` → `encore_send_e_ticket`) асинхронна, и её доля в окне зависит от кода. Горячий
ключ, 40 VU, `db`:

| Серия | settle на принятую команду | коммитов на принятую команду | WAL на команду | CPU PostgreSQL на 1000 |
|---|---|---|---|---|
| `perf-04-before` (обработчик в команде) | 1.23 / 1.27 / 1.29 | 1.61–1.63 | 4 381–4 495 | 1 462–1 532 |
| `perf-04-after` (процессор) | 1.46–1.48 | 1.73 | 4 824–4 849 | 2 136–2 252 |
| `perf-04b-s10` (процессор, пауза 10 мс) | 1.39 / 1.45 / 1.50 | 1.69–1.75 | 4 717–4 922 | 1 632–1 865 |

С процессором команда `Fan` больше не ждёт передачи событий в витрину, поэтому цепочка проходит за окно дальше. Около
+0.2 settle с claim и +0.1 коммита команды `Fan` на каждую команду `Concert` дают по оценке +0.35 КБ WAL, то есть
примерно +8 %. Это большая часть «необъяснённого остатка» тикета 03/04 по WAL и CPU PostgreSQL. Гипотеза о hint bits
при контрольных суммах на 14-секундных прогонах маловероятна: полная страница пишется только при первой модификации
после контрольной точки, а свежие страницы только что записаны.

Падение пропускной способности на 8–10 % может быть следствием той же более плотной фоновой работы. Проверить:
горячий ключ при `WORKERS=0`, то есть цепочка стоит.

**Предлагаю.** В сценариях с цепочкой считать «на команду» от снимка `before` до снимка `drained`. Хук уже снимает
`drained` для `03a`. Либо показывать цепочку отдельной строкой.

#### M-2. WAL, FPI и ожидания по операторам

Хук выгружает из `pg_stat_statements` вызовы, время, строки и блоки, но не `wal_records`, `wal_fpi` и `wal_bytes`
(они есть с PostgreSQL 13). `pg_stat_wal.wal_fpi` тоже не снимается. С ними любой вопрос «откуда WAL» решается
таблицей, а не гипотезой: блокировка строки в settle (`FOR UPDATE`), полные страницы, обрезка страниц при чтении.

Второе — выборка `pg_stat_activity.wait_event` раз в 100 мс во время прогона. Она покажет:
- конкуренцию за правые страницы `events_feed_idx` и `transactional_outbox_ready_idx` при 50 писателях: CTE в `02b`
  стоит 0.233 мс против 0.128 мс на горячем ключе;
- ожидание сброса WAL.

#### M-3. Удержание блокировки по фазам

Гистограммы только на стенде: ожидание блокировки, снапшот, события после него, решение, коммит, пробуждение. Сделать
через отдельную фичу или `tracing` с дешёвым подписчиком. Без этой раскладки оценка C-1 остаётся оценкой, а выбор между
C-1, N-1 и C-5 — догадкой.

#### M-4. Ёмкость системы — 5-минутный прогон (02/10)

§2.3 и §2.1 показывают, что `02b` меряет приём всплеска, а не то, что система выдерживает. Слив после 02/04 — около
2 000 задач/с при 8 воркерах в `db`. Это около 1 000 броней/с через всю цепочку на двух ядрах PostgreSQL. При 2 воркерах
(умолчание демо и стенда) — около 300/с. Прогон с постоянной входящей частотой (k6 `constant-arrival-rate`, не дольше
5 минут, D-22) — тот замер, по которому стоит судить Q-1…Q-4. Его стоит сделать базовой линией до них.

### D. Demo

#### D-1. X-ray sidecar сканирует журнал каждые 400 мс

Это только dev-стек: на стенде sidecar нет. `PgInspector` (`demo/sidecar/src/postgres.rs`) на каждый опрос
(`SIDECAR_POLL_MS=400`) в одной транзакции REPEATABLE READ делает:
- последние 200 событий через `ORDER BY metadata->>'recorded_at'` (`postgres.rs:12`): JSON разбирается в каждой строке
  журнала, плюс сортировка;
- `count(*)` событий, снапшотов и outbox;
- `GROUP BY aggregate_type, aggregate_id` по всем событиям;
- `GROUP BY status` по outbox;
- последние 200 задач через `ORDER BY created_at` (`postgres.rs:21`), индекса нет.

Журнал в миллион событий превращает каждый опрос в секунды CPU базы. Открытая транзакция держит горизонт очистки и
мешает VACUUM очереди (Q-4).

**Предлагаю.**
- Оценки из `pg_stat_user_tables`/`pg_class` вместо `count(*)`.
- Последние события — по `tx` из `events_feed_idx`, по одному запросу на тип агрегата.
- Последние задачи — по ключу, если взять UUIDv7 (Q-5).
- Группировки — по требованию, а не на каждом опросе.

### Мелочи

- **Ключ снапшотов (02/12).** Эксперимент: 50 обновлений на строку, ключ без `last_sequence` даёт 99.9 % HOT, кучу 24
  против 288 КБ, индекс 16 против 40 КБ, время −8 %, WAL −3 % (WAL почти весь — сам JSON снапшота). Миграция больше не
  нужна (обратная совместимость не требуется), цена — одна строка схемы и цель `ON CONFLICT`. Ценность — против
  раздувания при длинной работе.
- **`jsonb` в outbox** (`payload`, `metadata`, CHECK `jsonb_typeof`). JSON разбирается на каждой вставке внутри CTE
  команды, то есть внутри блокировки горячего ключа, и обратно в текст на claim. `json` дешевле, но выигрыш мал.
- **Журнал активности демо.** Около двух записей на команду (`command.accepted` и `projection.updated` от процессора):
  каждая — JSON, время в RFC 3339 и общий мьютекс. Для демо нормально, для нагрузочных профилей стоит помнить.
- **Частота снапшота (10).** После C-1 горячие ключи перестанут платить за хвост. Запись снапшота останется: около
  2.8 КБ WAL (зал на 40 мест) на каждое десятое событие. Стоит перемерить вместе с C-1.

## Приложение A. Эксперимент с очередью

Одноразовый контейнер `postgres:18.6-alpine` (тот же образ, что на стенде; `data_checksums = on`), параметры
`shared_preload_libraries=pg_stat_statements`, `pg_stat_statements.track=all`. Схема — `cqrsx/sql/001` и `002` без
изменений. Хранимая процедура повторяет слив:
- засеять 40 000 задач типа A (`encore_record_ticket`);
- цикл: claim пачки из 8 точным SQL из `claim.rs`;
- на каждую задачу A — вставка задачи B (`encore_send_e_ticket`, как CTE команды `Fan`) и settle;
- те же claim и settle для пачек B.

Каждый оператор — своя транзакция (`COMMIT` после каждого), id задач `gen_random_uuid()` или `uuidv7()`. Время ниже —
`mean_exec_time` из `pg_stat_statements`. Контейнер удалён после замера, скрипты жили в каталоге сессии.

| settle, 80 000 вызовов | Среднее, мс | Блоков на вызов | WAL на вызов, Б |
|---|---|---|---|
| как сейчас (`… AND status = 'processing'`, план по `expired_idx`) | 0.2733 | 121.9 | 280 |
| без условия на `status` (план по первичному ключу), CTE и `FOR UPDATE` как сейчас | 0.0709 | 17.5 | 267 |
| один `UPDATE … WHERE id AND lock_token AND locked_until > clock_timestamp()` | 0.0609 | 12.4 | 231 |
| `DELETE` с теми же условиями | 0.0135 | 6.5 | 66 |

Claim (10 000 вызовов по 8 строк): 0.15–0.19 мс и 130–176 блоков на вызов во всех вариантах. На середине слива
124 из 132 буферов claim уходят на просмотр начала `transactional_outbox_ready_idx`. UUIDv7 против v4: settle 0.0716
против 0.0709 мс, вставка 0.0662 против 0.0670 мс — разница в шуме.

Ключ снапшотов: две таблицы по 200 строк с JSON зала на 40 мест (2.3 КБ после сжатия), по 50 обновлений на строку:

| Ключ | HOT-обновлений | Куча | Индекс | Среднее, мс | WAL на вызов, Б |
|---|---|---|---|---|---|
| `(aggregate_type, aggregate_id, last_sequence)` — сейчас | 0 из 10 000 | 288 КБ | 40 КБ | 0.195 | 2 886 |
| `(aggregate_type, aggregate_id)` | 9 988 из 10 000 | 24 КБ | 16 КБ | 0.180 | 2 795 |
