# 05. Задачи и их обработчики

Статус: согласовано, 2026-10-27.

## Назначение

Задача — долговечный шаг после коммита: она переживает падение и исполняется хотя бы раз. Здесь описано, как
пользователь задаёт данные задачи и что она делает.

## Как это выглядит

```rust
// fan/application/record_cancellation.rs
/// The box office cancelled a booking: the fan's ledger records the cancellation.
#[derive(Debug, Clone, Serialize, Deserialize, Task)]
#[task(name = "encore_record_cancellation", version = 1)] // a stored contract: unchanged
pub struct RecordCancellation {
    pub booking_id: Uuid,
    pub cancellation_id: Uuid,
    pub concert_id: ConcertId,
    pub seat: SeatId,
    pub fan_id: FanId,
    pub refund: u32,
}

/// The ledger records the cancellation: a repeat (R11) is already done, a ticket not recorded yet (R10) is retried.
#[task_handler]
pub async fn record_cancellation(task: RecordCancellation, ctx: &TaskContext) -> TaskResult {
    let ledger = FanLedgerId::new(&task.fan_id, &task.concert_id);
    match ctx.execute::<Fan>(&ledger, task.command()).await {
        Err(Rejected(FanError::AlreadyCancelled { .. })) => done(),
        Err(Rejected(FanError::UnknownTicket { .. })) => retry("ticket not recorded yet"),
        other => other.into(), // accepted: done; conflict, unavailable: retry; another rejection: fail
    }
}
```

Контракт собран только из типов `shared`, поэтому книжка не знает кассу. Касса сама переводит в него свой факт (01):

```rust
// concert/application/fan_ledger.rs: what the box office asks of a fan's ledger, built from its own facts.
/// Everything comes from the fact; nothing is read.
pub fn record_cancellation(concert_id: &ConcertId, cancelled: &BookingCancelled) -> RecordCancellation {
    RecordCancellation {
        booking_id: cancelled.booking_id,
        cancellation_id: cancelled.cancellation_id,
        concert_id: concert_id.clone(),
        seat: cancelled.seat.clone(),
        fan_id: cancelled.fan_id.clone(),
        refund: cancelled.refund,
    }
}
```

```rust
// fan/application/issue_refund.rs
/// One refund per cancellation: the cancellation id is the mail's key. `mail` is the port from shared/application;
/// the module root provides it (07).
#[task_handler]
pub async fn issue_refund(task: IssueRefund, mail: &Mailer) -> TaskResult {
    mail.send(refund_mail(&task)).await.into() // a failed send: retry after the task type's pause
}
```

## Что пишет пользователь

- **Данные задачи и её контракт.** Имя и версия не меняются: задача хранится в outbox и переживает выпуск новой
  версии кода.
- **Построение из факта.** Все данные берутся из события, ничего не читается.
  - Из факта своего модуля задачу строит её конструктор (`IssueRefund::of`).
  - Факт другого модуля переводит в контракт сам производитель (`concert/application/fan_ledger.rs`, 01).
- **Обработчик — функция с `#[task_handler]`.** Её параметры — задача, контекст и зависимости. Она делает следующую
  команду другому агрегату или внешний эффект и решает, какой ответ агрегата значит «уже сделано», а какой — «рано,
  повторить».
- **Регистрация в корне модуля (07):** обработчик и его зависимости (`.provide(..)`).
- **Политика задачи — у её типа.** Корень модуля привязывает тип задачи к политике при регистрации:
  `.task(issue_refund).policy(MAIL)` (07); значения политики — паузу перед повтором и бюджет попыток — он берёт из
  окружения. Реакция политику не называет (04).
- **Дополнительные сведения о задаче** — поле с `#[label]`. Оно записывается в метаданные задачи, а не в её тело.

## Что делает движок

- **Доставка:**
  - claim пачкой, аренда, буфер, воркеры;
  - таймауты обработчика и хранилища;
  - возврат просроченных аренд.
- **Повторы:**
  - бюджет попыток и пауза перед повтором — по политике типа задачи;
  - без политики работают умолчания движка: бюджет из конфигурации, пауза 5 с × 2^(попытка−1), не больше 300 с;
  - ответ «отказ» останавливает доставку.
- **Зависимости обработчиков.** При сборке движок проверяет, что каждому обработчику хватает подключённых зависимостей.
- **Причинность.** Команда из `ctx.execute` продолжает причинность задачи: correlation id остаётся тем же, причиной
  становится задача. Служебные поля метаданных, например контекст трассировки, едут дальше сами (04).
- **Сбои команды.** Конфликт и недоступность команды превращаются в повтор задачи без участия пользователя.
- **Settle:** одна задача — одна транзакция.

Все эти настройки принадлежат движку (07); их имена и действующие значения не меняются.

## Правила

- **Хотя бы раз,** поэтому эффект безопасен при повторе. Ключ — id задачи (`ctx.task_id()`) или бизнес-ключ: для
  письма о возврате это id отмены.
- **Обработчик решает по текущему состоянию, применим ли шаг** (R9–R11): задача может прийти дважды или не вовремя.
- **Обработчик — функция без состояния.** Её зависимости общие для всех воркеров.
- **Ответы:** готово, повторить или отказ. Причина в ответе — без данных задачи и без секретов. Паузу перед повтором
  обработчик не считает.
- **Версии контракта.**
  - Тип без суффикса — текущая версия.
  - При несовместимом изменении старый тип переименовывается в `…V1` и живёт со своим обработчиком, пока в outbox не
    кончатся его задачи. Реакция ставит только новую версию.
  - Записанные имя и версия задаются в контракте, а не именем типа, поэтому переименовать тип безопасно.

## Как тестировать

- Обработчик — обычная функция. Тест вызывает её с почтой, которая записывает письма, или с тестовым контекстом над
  тестовым движком.
- Цепочка целиком — в тестовом движке, `cqrs.run_tasks()` (04).

## Решено

- 2026-10-26: задача и её обработчик живут в модуле, чью команду она исполняет (01).
- 2026-10-26: задачу из события другого модуля строит производитель; контракт задачи собран только из типов
  `shared` (01).
- **2026-10-26: обработчик — функция с `#[task_handler]`.**
  - Зависимости — её параметры; корень модуля подключает их через `.provide(..)`.
  - Альтернативы — отдельный тип с полями-зависимостями (`impl TaskHandler`) и метод самой задачи с зависимостями из
    контекста. Они в [списке пересмотра](../revisit.md).
- **2026-10-26: версии контракта — правило из раздела «Правила».** Возможно, его стоит доработать до перевода старой
  версии в новую (`#[task(version = 2, from(1) = upgrade_v1)]`). Тема в [списке пересмотра](../revisit.md).
- **2026-10-26: паузу перед повтором считает движок,** обработчик её не считает. Действующие значения остаются
  прежними:
  - почта — растущая пауза от 1 с до 8 с (`ENCORE_TASK_RETRY_BASE_MS`, `ENCORE_TASK_RETRY_MAX_MS`);
  - шаги цепочки — ровно 1 с.
- **2026-10-27 (бэклог, вопрос 2): политика привязана к типу задачи при регистрации** — обе её части, пауза перед
  повтором и бюджет попыток.
  - Корень модуля объявляет значения из окружения, `.policy(MAIL, Retry::backoff(..), max_attempts)`, и
    привязывает типы: `.task(issue_refund).policy(MAIL)`. Тип без политики работает по умолчаниям движка.
  - Ключи `ENCORE_TASK_RETRY_BASE_MS`, `ENCORE_TASK_RETRY_MAX_MS` и `ENCORE_TASK_MAX_ATTEMPTS` остаются.
  - Выбор при постановке (`then.task(x).policy(MAIL)`, имя политики в метаданных задачи) отклонён: новая запись в
    строках outbox и проверка только при планировании, а не при сборке. Нужна ли политика для отдельной постановки —
    тема 11 [списка пересмотра](../revisit.md).
- **2026-10-27: контракт задачи — `#[derive(Task)]` с `#[task(name, version)]`,** как у событий (02).
- **2026-10-27: метаданные задачи — дополнительные сведения, которых нет в теле задачи;** не обязательно служебные.
  - Поле с `#[label]` записывается в метаданные, а не в тело.
  - Дублировать тело в метаданных нельзя, поэтому ключи `concert_id` и `fan_id` больше не пишутся. Это исключение из
    требования 1 (задача 01).
  - Их всё равно никто не читал: X-ray берёт из метаданных только `correlation_id`.
