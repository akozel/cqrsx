# 01. Обзор: компоненты, границы, взаимодействие

Статус: согласовано, 2026-10-26.

## Назначение

Карта приложения на cqrsx: из чего оно состоит, что пишет пользователь, что делает движок и кто кого видит.
Остальные файлы раскрывают по одному компоненту.

## Компоненты

| Компонент | Что пишет пользователь | Что делает движок | Файл |
|---|---|---|---|
| Модуль | корень модуля: что он подключает к движку, своя настройка | собирает модули в приложение | 07 |
| Агрегат | состояние, `apply`, тип id, настройки правил | загружает снапшот и события после него, пишет снапшоты | 02 |
| Событие | факт с данными, его тип и версия | хранит в журнале, отдаёт реакциям и витринам | 02 |
| Команда | правила: какое событие случилось или почему отказ | блокировка агрегата, повтор при конфликте, коммит | 03 |
| Реакция | что следует за каждым событием: задачи | вызывает реакцию под блокировкой до коммита, пишет задачи вместе с событием | 04 |
| Задача и её обработчик | данные задачи и что сделать: следующая команда или внешний эффект | outbox: claim, аренда, воркеры, таймауты, повторы | 05 |
| Витрина | как событие меняет документ; запросы | процессор: закладка, воркер на ключ, порядок, повторы, перестройка | 06 |
| Приложение | `main.rs`: СУБД журнала и витрин, список модулей | пулы, рантаймы, HTTP, остановка | 07 |

## Граница модулей

**Граница модуля — агрегат.** Модуль владеет одним агрегатом. Одна команда меняет один агрегат в одной транзакции.

Другой агрегат меняется только следующим шагом: событие → реакция → задача → команда другого агрегата:

```text
concert: команда CancelBooking → событие BookingCancelled → реакция кассы
           └─► задача RecordCancellation (outbox, вместе с событием)
fan:         обработчик задачи → команда RecordCancellation → событие TicketCancelled → реакция книжки
               └─► задача IssueRefund → письмо
```

- **Прямых вызовов между агрегатами нет:** ни из правил, ни из реакций.
- **Шаг между модулями долговечен:** задача записана вместе с событием, исполняется хотя бы раз.
- **Согласованность между агрегатами — в конечном счёте:** книжка узнаёт об отмене после коммита кассы.

## Три пути

**Команда** — из HTTP-запроса или из обработчика задачи:

```text
HTTP ─► presentation: запрос → команда
          └─► движок: execute(id, команда)
                ├─ блокировка агрегата: очередь ключа, лимиты ожидания
                ├─ загрузка: снапшот и события после него
                ├─ domain: команда решает → событие или отказ             (03)
                ├─ application: реакция на событие → задачи               (04)
                ├─ коммит: событие, снапшот и задачи одним оператором
                └─ пробуждение витрин этого типа агрегата
          ◄── принято | отказ с кодом | конфликт | недоступно
```

**Задача** — из outbox:

```text
outbox ─► движок: claim пачкой, аренда, буфер, воркеры, таймаут, повторы
            └─► application: обработчик задачи                             (05)
                  ├─ команда другому агрегату: путь команды выше, причинность от задачи
                  └─ или внешний эффект: письмо
            ◄── готово | повторить | отказ
```

**Витрина** — из журнала:

```text
журнал ─► движок: процессор витрины, закладка под арендой, воркер на ключ
            └─► application: витрина, событие меняет документ              (06)
HTTP GET ─► presentation: запрос к витрине
```

**Отмена брони целиком:**
1. Касса решает `BookingCancelled`.
2. Реакция кассы ставит задачу «записать отмену в книжку».
3. Коммит события вместе с задачей.
4. Воркер исполняет задачу: команда `Fan.RecordCancellation`.
5. Книжка решает `TicketCancelled`.
6. Реакция книжки ставит задачу «вернуть деньги».
7. Коммит.
8. Воркер отправляет письмо.

Витрины «зал» и «кошелёк» догоняют журнал сами.

## Дерево

Решено 2026-10-26, на пробу (README дизайна): модуль — один каталог со слоями внутри.

```text
src/
├── main.rs                 движок: СУБД журнала и витрин, список модулей
├── concert.rs              корень модуля: что он подключает к движку; своя настройка — здесь
├── concert/
│   ├── domain/             агрегат Concert, команды, события
│   ├── application/        flow кассы: реакции на события, задачи книжки из фактов кассы, витрина «зал»
│   └── presentation/       HTTP кассы, в том числе операции над одним концертом
├── fan.rs
├── fan/
│   ├── domain/             агрегат Fan, команды, события
│   ├── application/        flow книжки: реакции, задачи с обработчиками, витрина «кошелёк»
│   └── presentation/       HTTP книжки
├── operations.rs           модуль без агрегатов
├── operations/
│   ├── application/        лента активности, операции над всеми витринами
│   └── presentation/       здоровье, настройки, лента, перестройка, статус, сверка
└── shared/                 общее ядро: только то, что нужно нескольким модулям
    ├── domain/             id и зал: value objects без правил модулей
    ├── application/        порт почты
    └── infrastructure/     почтовый клиент
```

Порт почты лежит в `shared/application/`, потому что общая инфраструктура не может зависеть от модуля.

Если раскладка окажется неудобной, вернёмся к слоям сверху и модулям внутри слоёв: `domain/concert`,
`application/concert` и так далее.

## Кто кого видит

**Внутри модуля** — правила чистой архитектуры:
- **`domain`** видит только контракты агрегата из cqrsx и `shared/domain`. Ни `application`, ни движок, ни
  ввод-вывод.
- **`application`** видит свой `domain`, API движка для реакций, задач и витрин и порты из `shared/application`.
  Ввода-вывода напрямую нет.
- **`presentation`** видит `application` и `domain` своего модуля и вызывает движок: команды и запросы к витринам.
- **Корень модуля** видит всё своё, `shared/infrastructure` и API сборки движка.

**Между модулями:**
- `domain` разных модулей друг друга не видят; общее лежит в `shared/domain`.
- **Реакция производителя ставит задачу потребителя.**
  - `application` кассы видит контракты задач книжки и сама переводит своё событие в такой контракт.
  - Книжка о кассе не знает: контракт её задачи собран только из типов `shared`.
- `main.rs` видит корни модулей.

Сейчас `tests/architecture.rs` проверяет слои как каталоги верхнего уровня и запрещает presentation любой путь
`cqrsx`. Правила переедут внутрь модулей.

## Что гарантирует движок

Коротко; полный список — в задаче 01, раздел «Что не меняется»:
- **Порядок команд.** Внутри процесса команды к одному агрегату идут по одной, в порядке прихода, с лимитами ожидания.
- **Атомарная запись.**
  - Событие, снапшот и задачи пишутся вместе, а задача без события не пишется.
  - Повтор при конфликте решает и планирует заново.
- **Id задач выводятся из команды,** поэтому повтор команды не публикует задачи дважды.
- **Задачи исполняются хотя бы раз,** с арендой, таймаутом и повторами.
- **Витрины** читают журнал от закладки, ничего не пропускают и сохраняют порядок событий ключа.

## Словарь

- **Модуль** — часть приложения с одним агрегатом и его слоями. Один каталог; подключается к движку как плагин.
  Модуль без агрегата — `operations`.
- **Агрегат** — граница согласованности и граница модуля: состояние, которое меняют только его события.
- **Команда** — намерение; агрегат решает её: событие или отказ.
- **Событие** — факт, который уже случился; хранится в журнале.
- **Application** — слой модуля в смысле чистой архитектуры. То, что в нём описано, — **flow** модуля, его
  бизнес-поток: реакции на события, задачи с обработчиками, витрины.
- **Реакция** — что следует за событием: задачи, которые запишутся вместе с ним.
- **Задача** — долговечный шаг после коммита: переживает падение, исполняется хотя бы раз. Только через задачу
  один модуль меняет агрегат другого.
- **Обработчик задачи** — что делает шаг: следующая команда или внешний эффект.
- **Витрина** — документ для чтения, построенный из событий одного агрегата.
- **Движок** — cqrsx: всё, что между этими частями.
- **Обиходные слова → термины движка:**
  - «очередь команд» — outbox задач;
  - «очередь проекций» — журнал, который процессор витрины читает от закладки.

## Решено

- **2026-10-26, на пробу: модуль — один каталог со слоями** `domain`, `application`, `presentation`. Корень модуля —
  файл рядом с каталогом.
- **2026-10-26: модуль `operations` без агрегатов.**
  - Что в нём: служебные маршруты (здоровье, настройки), лента активности и операции над всеми витринами
    (перестройка, статус, сверка).
  - Механику отдаёт движок, модуль показывает её в нынешнем HTTP демо.
  - Операции над одним концертом остаются в `concert/presentation/`.
- **2026-10-26: общее ядро — `shared/`.** Там только то, что нужно нескольким модулям: id и зал в `shared/domain`,
  почта в `shared/application` (порт) и `shared/infrastructure` (клиент).
- **2026-10-26: граница модуля — агрегат.** Другой агрегат меняется только задачей, которую ставит реакция: команда →
  событие → реакция → задача → команда другого агрегата. Задача и её обработчик живут в модуле, чью команду она
  исполняет.
- **2026-10-26: один агрегат на модуль по умолчанию.** API сборки принимает несколько агрегатов. Когда понадобится —
  по подкаталогу на агрегат в `domain/` и `application/`.
- **2026-10-26: задачу из события другого модуля строит производитель.**
  - Контракт задачи книжки собран только из типов `shared`.
  - Касса переводит в него свой факт: `concert/application/fan_ledger.rs`, функция
    `fan_ledger::record_cancellation(id, cancelled)`.
  - Зависимость односторонняя: касса знает книжку, а книжка о кассе не знает.
