# 04. Application: от запроса до коммита

Статус: согласовано, 2026-10-26. Главный файл дизайна.

## Назначение

Application — слой модуля в смысле чистой архитектуры. То, что в нём описано, — flow модуля, его бизнес-поток: что
следует за каждым событием агрегата. Код должен читаться как бизнес-логика: «случилось X — дальше Y». Ни очередей, ни
повторов, ни пробуждений.

## Как это читается

```rust
// concert/application.rs: what follows each fact of the box office.
impl Reactions for Concert {
    fn react(decided: &Decided<'_, Self>, then: &mut Then) {
        match decided.event {
            ConcertEvent::ConcertAnnounced(_) => {}
            ConcertEvent::SeatBooked(booked) => then.task(fan_ledger::record_ticket(decided.id, booked)),
            ConcertEvent::BookingCancelled(cancelled) => then.task(fan_ledger::record_cancellation(decided.id, cancelled)),
        }
    }
}
```

```rust
// fan/application.rs: what follows each fact of a fan's ledger.
impl Reactions for Fan {
    fn react(decided: &Decided<'_, Self>, then: &mut Then) {
        match decided.event {
            FanEvent::TicketRecorded(recorded) => then.task(SendETicket::of(decided.id, recorded)),
            FanEvent::TicketCancelled(cancelled) => then.task(IssueRefund::of(decided.id, cancelled)),
        }
    }
}
```

Каждая ветка — одна строка: факт → следующий шаг. Шаг — это задача; её данные и обработчик лежат в одном файле (05).

Задача живёт в модуле, чью команду исполняет, а строит её модуль, которому принадлежит событие ([01](01_overview.md),
решено 2026-10-26):
- контракт `RecordCancellation` и его обработчик лежат в `fan/application/record_cancellation.rs`;
- `concert/application/fan_ledger.rs` переводит в этот контракт факт кассы.

Задачу можно отложить: `then.task_after(delay, task)`. Задержка только относительная, потому что у реакции нет часов.
Пример вне демо — неоплаченная бронь:

```rust
ConcertEvent::SeatReserved(reserved) => then.task_after(Duration::from_secs(15 * 60), ReleaseUnpaid::of(decided.id, reserved)),
```

Политику задачи — паузу перед повтором и бюджет попыток — реакция не называет: она привязана к типу задачи в корне
модуля, `.task(issue_refund).policy(MAIL)` (05, 07; решено 2026-10-27 при построении бэклога вместо выбора при
постановке). В демо шаги цепочки идут по политике `STEP` (пауза 1 с), письма — по `MAIL` (пауза от 1 до 8 с).

## Порядок исполнения

Как ваш пункт 4 ложится на движок:

| Шаг | Кто | Где это написано |
|---|---|---|
| 1. HTTP-запрос → команда | presentation | `concert/presentation/` |
| 2. агрегат решает: событие или отказ | domain | 03 |
| 3. по типу события — задачи | реакция в application | этот файл |
| 4. коммит события и задач | движок | — |
| 5. витрины и следующие команды | движок | — |

**Шаги 2–4 — одна попытка движка:** под блокировкой агрегата, до коммита. При конфликте с другим процессом движок
повторяет попытку: загружает агрегат заново, команда решает заново, реакция вызывается заново. Поэтому реакция — это
описание, которое вызывает движок, а не код, который сам вызывает движок.

**Шаг 5 тоже делает движок,** и это не рассылка по очередям:
- витрины сами читают журнал от своей закладки, а коммит их только будит;
- задачи забирают воркеры outbox.

В application этого кода нет.

## Что видит реакция

`Decided` — то, что решила одна попытка:
- `id` — id агрегата (`&ConcertId`);
- `state` — состояние после события;
- `command` — команда, которую решили;
- `event` — событие;
- `metadata()` — метаданные команды, только для чтения: причинность, время, служебные поля вроде контекста
  трассировки.

Копия состояния не нужна: реакция получает ссылку на состояние, которое движок держит под блокировкой, и ничего не
может в нём испортить.

## Правила реакции

Они следуют из гарантий движка:
- **Чистая и синхронная:** без ввода-вывода, часов и случайности. Реакция идёт под блокировкой и повторяется при
  конфликте, поэтому одно и то же решение должно давать одни и те же задачи. Данные извне приходят в команде.
- **Одно событие на команду (D-02):** реакция видит одно событие.
- **Задача пишется только вместе с событием.** Отказ команды не пишет ничего.
- **Если задачу не удалось построить** (данные не сериализуются), команда получает отказ «недоступно». Ничего не
  записано, причина — в журнале приложения.
- **Id задачи выводит движок** из id команды. Та же команда дважды не опубликует задачу дважды.
- **Служебные поля метаданных движок переносит сам:** команда → события → задачи → следующая команда.
  - Реакция их не копирует.
  - Сейчас дальше едут только id причинности; `correlation_id` уже служит сквозным id всей цепочки.
  - Контекст трассировки (например, `traceparent`) поедет тем же путём.
  - В демо таких полей пока нет, поэтому записанное в журнал и в outbox не меняется.

## HTTP и сценарий

По умолчанию отдельной функции сценария нет. HTTP-обработчик превращает запрос в команду и отдаёт её движку:

```rust
// concert/presentation/execute_command.rs
let outcome = cqrs.execute::<Concert>(&concert_id, command).await;
```

Функция сценария нужна, когда до команды надо сходить наружу, например узнать цену у внешнего сервиса. Тогда она
живёт в application модуля, а результат передаёт в команде:

```rust
pub async fn book_seat(cqrs: &Cqrs, prices: &impl Prices, concert_id: &ConcertId, request: BookSeatRequest) -> Outcome<Concert> {
    let price = prices.of(&request.seat).await?; // outside, before the lock
    cqrs.execute::<Concert>(concert_id, request.into_command(price)).await
}
```

Ответ движка — один из четырёх исходов (03): принято (с записанными задачами), отказ с кодом, конфликт, недоступно.

## Варианты: где живёт реакция (решено: А)

| | А. У событий агрегата (решено) | Б. В сценарии команды | В. Потребитель подписывается |
|---|---|---|---|
| Как выглядит | один `match` по событиям агрегата в `concert/application.rs` | файл на команду: «отмена брони: …, затем задача» | `fan/application` объявляет: «на `Concert::BookingCancelled` — записать отмену» |
| «Каждая отмена возвращает деньги», какой бы командой она ни случилась | да | нет: другая команда с тем же событием забудет реакцию | да |
| Новое событие без реакции | ошибка компиляции | задачи молча нет | задачи молча нет |
| Откуда читается путь | от события, по ссылкам | от команды | от потребителя; касса не показывает последствий |
| Модули | касса ссылается на задачи книжки | так же | касса не знает о книжке |

Черновик — вариант А: это «на каждое событие удобный `match`» из вашего шага 3, и полноту проверяет компилятор.
Вариант Б ближе к описанию «сценарий получает команду и событие». Но команды и события у нас соотносятся один к
одному, а команду вариант А тоже видит — через `decided.command`.

## Как тестировать

Сценарий целиком проверяется в тестовом движке в памяти, без PostgreSQL:

```rust
#[tokio::test]
async fn a_cancellation_refunds_the_fan() {
    let (cqrs, mail) = test_app(); // Cqrs::in_memory() with both modules and a recording mailer (07)
    cqrs.execute::<Concert>(&radiohead(), announce()).await.unwrap();
    cqrs.execute::<Concert>(&radiohead(), book("A1", "fox")).await.unwrap();
    cqrs.execute::<Concert>(&radiohead(), cancel("A1", "fox")).await.unwrap();
    cqrs.run_tasks().await; // every task, down to the last one
    assert_eq!(mail.kinds(), ["e_ticket", "refund"]);
}
```

Реакцию можно проверить и отдельно: это функция от `Decided`, собранного руками.

## Решено

- **2026-10-26: реакция — вариант А:** один полный `match` по событиям агрегата в `<module>/application.rs`.
- **2026-10-26: реакция видит метаданные команды только для чтения** (`decided.metadata()`).
  - Служебные поля — причинность и контекст трассировки — движок переносит по цепочке сам.
  - Реакция их не копирует.
- **2026-10-26: имена** — `Reactions`, `Decided`, `then.task(..)`.
- **2026-10-26: отложенные задачи нужны:** `then.task_after(delay, task)`, задержка только относительная.
- **2026-10-27 (бэклог, вопрос 2): реакция только ставит задачу** — `then.task(x)`, `then.task_after(delay, x)`;
  политика — у типа задачи в корне модуля (05, 07), не при постановке.
- **2026-10-26: ленту активности ведёт модуль `operations`.** Он подписывается на всех наблюдателей движка: команды,
  задачи, витрины. Модули для ленты ничего не пишут.
- **2026-10-26: ответ «принято» перечисляет записанные задачи** — как сейчас, для наглядности. Исход «принято» у
  движка несёт их форматы.
- **2026-10-26: подписи ленты дают derive-макросы модуля.**
  - Имя команды берётся из `#[derive(Commands)]`, ключи подписи — из атрибута `#[label]` на поле команды (`fan_id`),
    код и параметры отказа — из `#[derive(Rejection)]` (03).
  - Формат записи ленты не меняется.
  - Ревью после реализации: удобно ли это и не протекают ли нужды ленты в домен модулей. Тема в
    [списке пересмотра](../revisit.md).
