# 06. Витрины и запросы

Статус: согласовано, 2026-10-27; вопрос 1 открыт по решению пользователя.

## Назначение

Витрина — документ для чтения, построенный из событий одного агрегата. Здесь — как пользователь описывает, как
событие меняет документ, и как HTTP этот документ читает.

## Как это выглядит

```rust
// concert/application/views/concert_hall.rs
/// The hall of one concert: seats, sales, revenue.
#[derive(Debug, Default, Clone, Serialize, Deserialize)]
pub struct ConcertHall {
    concert: Option<ConcertSummary>,
    seats: BTreeMap<String, SeatEntry>,
    sold: i64,
    revenue: i64,
}

impl View<Concert> for ConcertHall {
    const NAME: &'static str = "concert_halls"; // collection and checkpoint name: unchanged

    fn update(&mut self, event: &EventEnvelope<Concert>) {
        match &event.payload {
            ConcertEvent::ConcertAnnounced(announced) => self.announce(announced),
            ConcertEvent::SeatBooked(booked) => self.book(booked, event.sequence, recorded_at(event)),
            ConcertEvent::BookingCancelled(cancelled) => self.free(cancelled, event.sequence, recorded_at(event)),
        }
    }
}
```

Витрина подключается в корне модуля: `.view::<ConcertHall>()` (07). Где хранить документы — в MongoDB или в
PostgreSQL, — решает `main.rs`: `.projections(MongoDb)`.

Запросы из HTTP — три запроса движка для любой витрины:

```rust
let hall = cqrs.view::<ConcertHall>().get(&concert_id).await?;       // GET /concerts/{id}
let halls = cqrs.view::<ConcertHall>().list().await?;                // GET /concerts
let wallets = cqrs.view::<FanWallet>().range("fox:", "fox;").await?; // every ledger of one fan
```

## Что пишет пользователь

- **Документ** и то, как каждое событие его меняет (`update`).
- **Имя витрины.** Это имя коллекции и строки закладки, и оно не меняется.
- **Свой порт запросов модуля** — только для запроса, которого нет среди трёх запросов движка.

## Что делает движок

- **Процессор на каждую витрину** читает журнал её типа агрегата от закладки.
  - Закладка — под арендой, поэтому две ноды не применяют события одновременно.
  - Пробуждение после коммита, а без пробуждения — опрос.
- **Воркер на ключ** применяет события ключа в порядке журнала.
- **Ничего не пропускается.**
  - Документ — свёртка непрерывного префикса событий (`last_sequence`).
  - Разрыв — документ перестраивается из истории.
  - Ошибка — повтор с растущей паузой.
- **Пачки** и лимиты буфера.
- **Перестройка** всей витрины или одного ключа идёт без остановки записи.

## Правила

- **`update` чистая:** тот же префикс событий даёт тот же документ, и на этом держится перестройка. Время берётся из
  метаданных события (`recorded_at`), а не из `now()`.
- **Порядок и однократность гарантирует движок.** События ключа приходят по порядку и по одному разу, поэтому
  проверка «последняя запись побеждает» в витрине не нужна.
- **Витрина пишет только свой документ.** Никаких команд — правило `cqrsx/doc/components.md`.
- **Одна коллекция — одна витрина.**
- **Витрина из событий нескольких агрегатов** — не то, что строит `View` (тоже `components.md`).

## Как тестировать

- `update` напрямую: свёртка событий в документ.
- Тестовый движок: команды, ожидание, пока витрины догонят журнал, затем `cqrs.view::<ConcertHall>().get(..)`.

## Решено

- 2026-10-26: витрина живёт в `application/` своего модуля — `concert/application/views/` (дерево, 01).
- 2026-10-26: операции над всеми витринами (перестройка, статус, сверка) показывает модуль `operations`, а механику
  отдаёт движок. Операции над одним концертом — перестройка зала, хронология, машина времени — остаются в
  `concert/presentation/` (01).
- **2026-10-27: запросы к витринам.**
  - Движок даёт три запроса для любой витрины: документ по id, все документы, диапазон id. Сейчас их даёт порт
    `ReadModelStore<V>`.
  - Для особого запроса у модуля свой порт.
  - Обсудить после эпика — тема в [списке пересмотра](../revisit.md).
- **2026-10-27: для `operations` движок даёт типизированный API.**
  - `cqrs.views().status()`, `.rebuild(name)`, `.rebuild_key(name, id)`, `.verify(name)` и наблюдатели для ленты
    активности.
  - `operations` только переводит их в нынешние форматы JSON.
- **2026-10-27, временно: одна `View` для MongoDB и PostgreSQL.** Витрины демо проходят один набор тестов в памяти,
  на PostgreSQL и на MongoDB. Операция «стереть витрины» работает в обоих хранилищах.
- **2026-10-27 (бэклог, вопрос 5): сверка — компонент cqrsx** (`projection::verify`, перенос кода демо с его
  тестами); `operations` переводит её ответ в прежний JSON.
- **2026-10-27: проверка «последняя запись побеждает» из витрин демо убирается.**
  - Её ввели ради перестройки: в исходном плане библиотека не знала, какие события документ уже видел.
  - Эпик 03 перенёс эту гарантию в движок: `last_sequence` у документа, перестройка через воркер ключа.
  - Документы не меняются: номер события и время у места остаются, отмена по-прежнему оставляет место со статусом
    «свободно».
  - После реализации проверить перестройку под нагрузкой — тема в [списке пересмотра](../revisit.md).
