# Дизайн API движка

Здесь согласуем, как приложение на cqrsx выглядит для пользователя: что пишет программист и что берёт на себя
движок. Это приблизительный API. Поведение движка дизайн не меняет: контракт неизменности — в
[задаче 01](../01_requirements_and_backlog.md), раздел «Что не меняется».

## Как дорабатываем

- Один файл — одна тема, каждую дорабатываем отдельно.
- Статус файла: черновик → на обсуждении → согласовано.
- Каждый файл заканчивается разделами «Решено» (с датой) и «Открытые вопросы».
- Код в файлах — набросок на сквозном примере, а не готовый API. Имена в набросках обсуждаемы.
- Бэклог миграции (задача 01) строится от согласованных файлов.
- По правилу бэклога законченное удаляется. К концу эпика согласованный дизайн переезжает в документацию cqrsx.

## Сквозной пример

Encore — касса концерта и книжка фаната:
- **касса** (модуль `concert`): объявить концерт, забронировать место, отменить бронь;
- **книжка фаната** (модуль `fan`): записать билет, записать отмену;
- **задачи:**
  - записать билет в книжку → отправить электронный билет;
  - записать отмену в книжку → вернуть деньги письмом;
- **витрины:** зал концерта (`concert_halls`), кошелёк фаната (`fan_wallets`).

Каждый файл показывает свой кусок главного пути: **отмена брони → запись отмены в книжку фаната → письмо о
возврате**, плюс витрины, которые это отражают. Если куски соседних файлов не стыкуются, дизайн не готов.

## Решено

- **2026-10-26: место и состав.** Каталог дизайна — внутри эпика 05. Файлы и шаблон — как выше.
- **2026-10-26: модуль — один каталог со слоями внутри.** Пробуем; если будет неудобно, вернёмся к слоям сверху и
  модулям внутри слоёв.
  - `concert/` и `fan/` — модули-плагины. Внутри — `domain/`, `application/`, `presentation/`, а если у модуля свои
    внешние адаптеры, ещё `infrastructure/`.
  - `domain` никогда не лежит внутри `application`: application зависит от домена, а не наоборот.
  - Общее для модулей лежит в `shared/`.
- **2026-10-26: `application` — слой модуля в смысле чистой архитектуры,** так он называется и в коде, и в
  документах. То, что в нём описано, — flow модуля, его бизнес-поток. Термин workflow в `cqrsx/doc/components.md`
  заменяется на flow.
- **2026-10-26: корень модуля — файл рядом с каталогом** (`concert.rs`). В нём — что модуль подключает к движку и его
  собственная настройка. `main.rs` только перечисляет модули.
- **2026-10-26: процедурные макросы и метапрограммирование приветствуются** везде, где они делают код читаемее.
  Первый случай — тип и версия события (02).
  - В cqrsx появится крейт макросов, например `cqrsx-macros`. `syn` 2, `quote` и `proc-macro2` уже есть в
    `Cargo.lock` и в офлайн-кэше, а `trybuild` там нет.
  - Покрытие 97 % держим тестами функций развёртки над `proc_macro2`, а проверки «не компилируется» — doctest'ами
    `compile_fail`.
- **2026-10-27: решения по вопросам бэклога** (README эпика) внесены в 04, 05, 06, 07: политика у типа задачи,
  HTTP — фича `http`, `Setup` без общих ресурсов, сверка в cqrsx.
- **2026-10-26: отправная точка — направление из задачи 01:**
  - реакции по агрегату;
  - типизированный id;
  - чистый `handle`;
  - задача с обработчиком в одном файле;
  - тестовый движок в памяти.
