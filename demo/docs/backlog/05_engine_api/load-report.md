Отчет подготовлен 28 октября 2026 года по сохраненной серии от 27 октября и дополнен повторными прогонами 28 октября. «До» — коммит `91dda19`, «после» — `78356bf`. Исходный журнал `work/13-checks.log`, план `work/13-plan.md` и файлы в `demo/load/results/` с префиксами `e05s-base-` и `e05s-head-` локальные: они игнорируются git и могут отсутствовать в другом checkout. Ключевые параметры и результаты также приведены в [задаче 13](13_measurement_before_after.md).

## Вывод

По этой серии явного падения пропускной способности после миграции не видно: медианы принятых команд изменились от −0,1% до +1,1%, диапазоны пяти повторов пересекаются. Это не доказывает эквивалентность производительности или отсутствие небольших регрессий: выборка мала, измерительное окно короткое, а часть показателей различается. В частности, p99 в сценарии с восемью обработчиками вырос с 40,5 до 51,2 мс по медианам, хотя диапазоны пересекаются; этот показатель требует повторного измерения.

## Методика

Изолированный стенд `encore-load`: k6, приложение, PostgreSQL и MongoDB. Образ до миграции собран из `git archive 91dda19`, после — из чистых входов сборки `78356bf`. В одном сеансе выполнено 40 основных прогонов: четыре точки × две версии × пять повторов, с перемешанным порядком; дополнительно восемь проверочных прогонов. Все 48 завершились с кодом 0. Пул PostgreSQL — 20; измерительное окно по умолчанию — 10 с после 3 с прогрева, затем очередь сливалась. CPU ограничивался квотами, а не закреплением ядер: квоты могут влиять на хвостовые задержки.

## Стоимость и корректность

- На протяжении окна нагрузки CPU бэкенда, PostgreSQL и MongoDB на 1000 принятых команд во всех четырех точках укладывался в критерий ±5% по медиане и пересечения диапазонов. При сливе горячего ключа CPU на 1000 задач изменился больше чем на 5% для бэкенда и MongoDB при пересекающихся диапазонах: например, профиль app, бэкенд 557 (542–676) → 609 (598–619) мс, +9,4%. Вывод о причине и соответствии критерию делать рано.
- Для каждого сценария повторно запущено сравнение сохраненных `pg_statements`: одинаковые множества из 12 нормализованных SQL-операторов, по пять прогонов каждой версии. Это сравнение множеств, а не доказательство равенства частот. Число операторов на команду и на всю цепочку имеет пересекающиеся диапазоны; загрузок агрегата на коммит примерно одна.
- WAL на команду за всю цепочку снизился: горячий ключ app 5801 → 5609 Б (−3,3%), db 5820 → 5612 Б (−3,6%), распределенные бронирования 5750 → 5486 Б (−4,6%), восемь worker 5760 → 5480 Б (−4,9%). Диапазоны не пересекаются. Журнал связывает основную часть снижения с исключением `concert_id` и `fan_id` из метаданных задач; разложение по операторам поддерживает это объяснение, хотя сумма операторов и WAL по позиции совпадают не точно.
- При сливе горячего ключа в профиле db число задач на `claim` изменилось с 1,97 (1,96–1,97) до 1,98 (1,98–1,99); диапазоны не пересекаются. Журнал указывает на различное заполнение пакетов, но причина окончательно не установлена. В профиле app диапазоны пересекаются.
- В 10 основных прогонах с `VERIFY=1` обе версии вернули `ok`, ноль отстающих документов и ноль расхождений. В основных прогонах очереди слились без оставшихся и ошибочных задач. Эта проверка охватывает заданные сценарии, а не все возможные отказы и гонки.
- В точке с verify медиана пика памяти бэкенда снизилась с 262 (160–274) до 61,5 (60,8–69,4) МиБ. Согласно журналу пик приходится на verify; прежняя реализация собирала BSON-документы в память перед декодированием, новая читает курсор по одному документу. Это измерение пика конкретного сценария, а не общего потребления памяти приложения.
- `/api/config` совпал во всех проверочных прогонах. Сырые списки имен переменных из текста отличаются из-за конструирования имен и тестовых строк; журнал содержит ручной разбор этих отличий. Проверка ленты завершилась кодом 1: один `command.rejected` появился только после миграции. В журнале он объяснен гонкой задач и успешным повтором, а поля совпадают с эталоном. Многие типы событий не возникли ни в одном проверочном прогоне, поэтому полного сравнения ленты эти измерения не дают.

## Ограничения и следующие шаги

Первоначально в текущей среде не было клиентов Docker/Podman и Compose: `demo/load/run.sh --check` вернул `neither docker nor podman found`. Затем временный клиент был установлен вне репозитория и проведена дополнительная серия, описанная ниже. На хосте работали сторонние контейнеры, включая dev-стек; их не останавливали.

Для уверенного заключения стоит повторить сравнение в одной спокойной сессии, по возможности с закреплением ядер, увеличить длительность окна и число повторов, отдельно исследовать p99 сценария с восемью worker, CPU при сливе и изменение заполнения `claim`. Проверить ленту отказов и повторов отдельным контролируемым сценарием. Сопоставимость результатов сохраняется только при одинаковых настройках, образах, нагрузке и измерительном стенде.

## Дополнение: повтор горячего ключа 28 октября

Проведены 20 дополнительных прогонов (оба профиля `app` и `db`, по пять повторов для каждой версии, 40 VU, 5 с прогрева, 20 с измерения и слив). После 17-го прогона серия прервалась примерно на пять минут и затем продолжилась в прежнем порядке; CPU ограничивался квотами, dev-стек работал. Все 20 очередей слиты без ошибок. Диапазоны — min–max пяти прогонов.

В профиле app принятых команд/с 667 (572–669) → 672 (586–675), в db 707 (386–713) → 668 (602–713). В db медиана p99 77,7 (74,0–243) → 102 (75,7–111) мс: рост на 31,9% при пересекающихся диапазонах. В обоих профилях CPU бэкенда, PostgreSQL и MongoDB на 1000 задач при сливе изменился по медиане менее чем на 5% с пересечением диапазонов; диапазоны заполнения `claim` тоже пересеклись. Таким образом, отличия по CPU и claim из первой серии в повторе не воспроизвелись, но их причина не установлена. Сравнение SQL снова показало по 12 одинаковых нормализованных операторов на профиль.

Контрактный тест, создающий все 13 типов событий ленты и сравнивающий поля с эталоном, прошёл на архиве `b251e24` до миграции и на `78356bf` после. Различие наборов в живых нагрузочных прогонах при этом сохраняется: в одном из них после миграции зафиксирован дополнительный `command.rejected` из гонки задач, затем успешно повторенной. Это сравнение вернуло код 1; контролируемый тест покрывает формы записей, но не доказывает одинаковую частоту такой гонки.
