## Зачем

Пользователь, 2026-10-26: чтобы понять бизнес-логику демо, приходится много раз прыгать между слоями, из сервиса в
сервис. А нужно вот что:
1. описать агрегат;
2. описать инварианты и бизнес-правила в обработчике команды;
3. на каждое событие агрегата сделать удобный `match` и прикрепить к нему задачи outbox;
4. отдать команду движку cqrsx и пользоваться результатом;
5. в соседнем файле описать обработчик задачи.

«Для этого мы и разрабатываем framework».

Как сейчас (HEAD `91dda19`):
- **Путь «отмена брони → запись в книжку фаната → письмо о возврате» проходит через 22 файла демо.** Бизнес — в
  шести доменных (состояние, правила и события `Concert` и `Fan`) и в двух строках «после этого события — эта задача».
- **Остальное — проводка, которую навязывает API cqrsx:**
  - исполнитель собирается руками на каждый агрегат: `PostgresCommandConfig`, `AggregateConflictRetryPolicy`,
    `LockLimits`, `with_task_planner`, `with_commit_wakeup`;
  - задачи: `TaskPayload`, `NewTask::new(..)?.with_metadata(..)?.with_max_attempts(..)?`, `TaskPlanner` с `Decision`,
    `TaskPlanError` и кортежами, разбор id агрегата из строки в каждом планировщике;
  - обработчики задач: `BoxedTaskAdapter::json`, `TaskDispatcher`, фабрика диспетчеров на каждый воркер,
    `prepare_task_runtime`;
  - команда из обработчика задачи: причинность из задачи, `run_chain_step`, `map_fan_outcome` — демо пишет их сама;
  - повторы почтового клиента со своей паузой (`ENCORE_TASK_RETRY_BASE_MS`, `ENCORE_TASK_RETRY_MAX_MS`);
  - прослойки `ConcertApp`, `FanApp`, `CommandService` и сценарии в одну строку: они держат исполнитель, ведут
    журнал активности и переводят ошибки;
  - витрины: процессор на каждую, хранилище закладок, пробуждения, рантайм проекций, проверка
    (`bootstrap/projections*.rs`, 194 строки);
  - `config.rs` демо: 580 строк и 38 ключей окружения, почти все настраивают механизмы фреймворка.
- **Сборка на PostgreSQL из README cqrsx — 26 импортов.**

## Требования пользователя

Записаны 2026-10-26, близко к тексту:
1. **Логика работы движка, гарантии доставки, политики и лимиты остаются прежними.** Меняется только опыт
   пользователя API движка. Это самое главное требование.
2. **Конфигурация приложения занимает пару строк.** Простой bootstrap указывает тип СУБД для журнала событий (event
   store) и для витрин (projections).
3. **Новые компоненты подключаются просто:** агрегат, outbox, витрина.
4. **Приложения подключаются как плагины.** В bootstrap прописывается модуль, например `concert`. Внутри модуля
   подключается более конкретная проводка, если она нужна.
5. **Внутри модуля-плагина в `domain` описывается cqrs:** агрегат, команды, события.
6. **Внутри `application` — простой способ описать реакции и обработчики, без технических деталей фреймворка.**
   Очереди, механизмы пробуждения, устойчивость к сбоям (resilience), надёжность (durability), повторы (retry),
   насыщение (saturation), каналы — всё это уходит во фреймворк.
7. **На уровне демо остаются только ветвления бизнес-сценариев, в декларативном стиле.**
8. **Все гарантии согласованности остаются** (повтор требования 1).

## Что не меняется

Ниже — что именно значит требование 1. Агент дополняет список, привязывает каждый пункт к коду и к тесту, который его
держит. Гарантия без теста получает тест до миграции.

**Команда**
- **Блокировка агрегата внутри процесса:**
  - команды к одному ключу выполняются по одной, в порядке прихода;
  - лимиты ожидания и очереди — `LockLimits`: 1 с, 128 ожидающих; в демо `ENCORE_COMMAND_LOCK_MAX_WAIT_MS` и
    `ENCORE_COMMAND_LOCK_MAX_WAITERS`;
  - отказ в блокировке ничего не загружает, не планирует и не пишет (`cqrsx/src/cqrs/command/{executor,locks}.rs`).
- **Одна попытка — это загрузка (снапшот и события после него) → решение → планирование задач → запись.**
- **Повтор при конфликте с другим процессом** — `AggregateConflictRetryPolicy`: 3 попытки, пауза 5–50 мс, разброс
  0.2. Каждая попытка заново загружает агрегат и заново планирует задачи (`cqrsx/src/cqrs.rs`,
  `cqrsx/src/cqrs/command/retry.rs`).
- **Событие, снапшот и задачи пишутся одним оператором, атомарно** (`cqrsx/src/postgres/outbox/write.rs`):
  - одна запись в PostgreSQL несёт не больше одного события (D-02, `write_plan.rs`);
  - задача без события не пишется.
- **Снапшот — каждые N событий** (`ENCORE_SNAPSHOT_EVERY`, 10).
- **Ошибка планирования отказывает команде, ничего не записав:** ответ `Unavailable`, категория `task_plan` в журнале.
- **Коммит с событиями будит процессоры своего типа агрегата.** Пока запись в полёте, команду отменять нельзя.
- **Один исполнитель на тип агрегата и процесс.** Два процесса встречаются только в оптимистической проверке
  хранилища.

**Причинность и идентичность**
- Ключи `command_id`, `correlation_id`, `causation_id` и `source` есть в метаданных каждого события. Там же
  `recorded_at`, по нему сортирует sidecar.
- **Ядро ставит причинность на каждую задачу и выводит её id:** UUID v5 от типа и id агрегата, id команды, формата
  задачи и её порядкового номера. Та же команда дважды на одном агрегате не публикует задачи дважды: второй коммит
  отклоняется целиком (`cqrsx/src/cqrs/command/{causation,planner}.rs`).
- **Команда из обработчика задачи продолжает причинность задачи** (`Causation::from_task`).

**Outbox и задачи**
- Доставка «хотя бы раз»; эффект обработчика безопасен при повторе.
- **Claim и буфер:**
  - claim пачкой (`FOR UPDATE SKIP LOCKED`);
  - буфер Q = C, подзагрузка, когда в буфере меньше 25 % (04/19);
  - аренда (в демо 30 с) с проверкой её длины;
  - опрос (в демо 300 мс) и claim, когда освободился воркер;
  - таймаут обработчика (в демо 5 с) и хранилища (в демо 3 с);
  - возврат просроченных аренд на каждом тике (`cqrsx/src/task/runtime/supervisor.rs`,
    `cqrsx/src/postgres/task_queue/`).
- **Повторы:** `Retry` и `Permanent`, бюджет попыток (`ENCORE_TASK_MAX_ATTEMPTS`), пауза перед повтором.
- **Settle** — по первичному ключу; одна задача — одна транзакция settle (04/03; пакетный settle отклонён в 04/08).
- Упавший воркер перезапускается; при остановке рантайм дорабатывает начатое.

**Проекции**
- Процессор на витрину читает журнал своего типа агрегата от закладки, которую держит под арендой.
- Воркер на ключ, события в порядке журнала; ни одно событие не пропускается.
- Разрыв — документ перестраивается из истории. Повторы — с растущей паузой.
- Пачки — `DeliveryLimits`; пауза после пробуждения.
- Перестройка всей витрины или одного ключа идёт без остановки записи.
- MongoDB — только для чтения; закладка принадлежит журналу PostgreSQL.

Код — `cqrsx/src/cqrs/projection/` и `cqrsx/src/mongodb/`, правила — в `cqrsx/doc/components.md`.

**Ресурсы и жизненный цикл**
- **Пулы:** три пула PostgreSQL демо (команды и очередь, история, проекции) с их размерами, таймаут оператора,
  проверка соединения при выдаче, пул MongoDB.
- **Порядок остановки** (`demo/back-end/src/process.rs`):
  1. HTTP;
  2. рантайм задач;
  3. процессоры дорабатывают начатое и отдают закладки;
  4. пулы закрываются.

**Внешние контракты**
- **Не меняются:**
  - схемы SQL и тексты операторов (набор в `pg_stat_statements` на стенде);
  - форматы задач и их JSON (`encore_record_ticket v1` и другие);
  - типы и версии событий, ключи метаданных;
  - HTTP API;
  - имена переменных окружения и их значения по умолчанию: `OUTBOX_*` библиотеки, `ENCORE_*` демо.
- Действующие значения настроек демо остаются прежними, даже если меняется место, где они заданы.

**Исключения, согласованные с пользователем:**
- **2026-10-27: ключи `concert_id` и `fan_id` больше не пишутся в метаданные задач.** Они дублируют тело задачи, а
  метаданные — только для сведений, которых в теле нет (design/05). Записанные строки outbox остаются как есть.
- **2026-10-27: обработчики задач общие для всех воркеров** (`&self`, без фабрики диспетчеров): перезапуск воркера
  после паники переиспользует диспетчер вместо свежего (задача 09). Перезапуск и дренаж при остановке остаются;
  обработчики демо состояния не держат, поэтому поведение демо не меняется.

**Как доказать неизменность** — задачи бэклога:
1. **Тесты гарантий cqrsx переносятся на новый API без ослабления и проходят:** `cqrsx/tests/postgres/{command,
   planning}.rs`, `outbox/`, `event_store/`, `projection/`, `cqrsx/tests/cqrs/`, `cqrsx/tests/mongo/`, модель свойств
   блокировок (`property_locks_match_a_fifo_model` в `cqrsx/src/cqrs/command/locks.rs`).
2. **Тесты демо проходят,** в том числе `tests/write_side.rs` и регрессии гонок отмены в `cancel_booking.rs`.
3. **Стенд `encore-load`, до и после,** на точках:
   - `01-hot-key-vus40` в профилях `db` и `app`;
   - `03a-drain-w8`;
   - `02b-spread-vus50`.

   Что должно совпасть:
   - тот же набор текстов SQL;
   - те же числа операторов и WAL на команду;
   - принятых в секунду — в пределах разброса.
4. **Действующая конфигурация демо до и после сравнивается построчно.**

## Принятое направление

2026-10-26 пользователь одобрил направление («это похоже на правду»). Агент берёт его как отправную точку; отступление —
с обоснованием и вопросом пользователю.
- **Реакции — по агрегату.** `match` по событиям агрегата прикрепляет к каждому задачи; новое событие без ветки —
  ошибка компиляции.
  - Это заменяет правило 04/20 «процесс в одном типе»: `TicketDelivery` и `Refund` и кортежи планировщиков.
  - Механика 04/20 остаётся внутри: планирование под блокировкой на каждой попытке, штамп причинности, id v5,
    атомарная запись.
- **Типизированный id агрегата:** `execute(&ConcertId, ..)`, в реакцию приходит `&ConcertId`, строки не разбираются.
- **Решение — синхронная чистая функция команды (`Decide<A>`),** без `EventSink`. Она возвращает одно событие или
  отказ: одна команда — одно событие, по D-02 (design/03).
  - Проверено 2026-10-26: ни один агрегат cqrsx и демо не ждёт в `handle` ничего, кроме `sink.write`.
  - Гонки в тестах устраивают обёртки хранилища.
- **Задача и её обработчик — в одном файле.**
  - Обработчик один на все воркеры (`&self`), без фабрики.
  - Контекст задачи исполняет команды других агрегатов: причинность наследуется, конфликт и недоступность сами
    превращаются в повтор.
- **Тестовый движок в памяти** собирается так же, как боевой, и умеет прогнать задачи до конца: «забронировал,
  отменил, прогнал задачи, проверил письма».
- **Журнал активности демо — наблюдатель команд движка:** одна реализация на все команды.
- **Строительные блоки остаются** (`CommandExecutorCore`, `TaskPlanner`, адаптеры, раннер) — для своих хранилищ и для
  тестов самой cqrsx. Из README и из демо они уходят.

Наброски кода, дерево модулей и решения по ним — в каталоге [design/](design/README.md). Там API согласуется
с пользователем по файлам.

## Что исследовать

1. **Инвентарь публичного API cqrsx,** которым пользуются демо и README. Для каждого элемента: типовой путь,
   строительный блок или внутреннее.
2. **Гарантии → код → тесты** по разделу «Что не меняется». Найти гарантии, которые не держит ни один тест.
3. **Целевой API согласуется с пользователем в [design/](design/README.md),** по файлам; бэклог строится от
   согласованных файлов. Где вопрос ещё открыт, нужны 2–3 варианта: дерево демо, путь «отмена → возврат» целиком,
   число файлов и понятий фреймворка на один бизнес-поток. Дать рекомендацию и назвать каждое правило слоёв, которое
   вариант нарушает. Сейчас `tests/architecture.rs`:
   - запрещает `presentation` любой путь `cqrsx`;
   - разрешает `domain` только `cqrsx::cqrs::{aggregate, event, event_sink, testing}`.

   Модуль одним каталогом со слоями внутри (`concert/{domain, application, presentation}`, решено 2026-10-26 на
   пробу) меняет и само дерево: сейчас слои — каталоги верхнего уровня.
4. **Настройки:**
   - какие ключи читает сам фреймворк, с умолчаниями-константами, как сейчас `OUTBOX_*`, а какие остаются приложению;
   - где живут умолчания демо, которые отличаются от библиотечных, чтобы действующие значения не изменились. Сейчас
     это `outbox_default` в `config.rs`: 2 воркера, буфер 2, опрос 300 мс, обработчик 5 с, аренда 30 с, хранилище 3 с.
5. **Зависимости модулей:** как модуль получает почтовый клиент, пулы и настройки своих правил
   (`ENCORE_TICKET_LIMIT`).
6. **Операции демо поверх движка:** перестройка витрин, проверка (verify), машина времени, статус, X-ray. Что им нужно
   от движка.
7. **Порядок миграции, при котором каждый коммит зелёный:** все проверки `CLAUDE.md`, покрытие 97 %.
   - Например: фасад поверх нынешних механизмов → перевод демо → удаление старого API из README и демо → чистый
     `handle`.
   - Как перенести тесты cqrsx: 61 реализация `Aggregate`, тесты на `TestCommandExecutor`, `TaskPlanner`,
     `PostgresCommandExecutor`.
8. **Документы:**
   - README cqrsx: быстрый старт = типовой сценарий;
   - `components.md`: новые термины — модуль, реакция, движок;
   - `demo/PLAN.md`: решение, которое заменяет D-25 «процесс в одном типе»;
   - `demo/docs/API_MAPPING.md`.

## Риски

- **Фасад незаметно меняет поведение:** другой порядок шагов, другой пул, другое умолчание. Защита — тесты гарантий
  и сравнение на стенде.
- **Реакции по агрегату разносят процесс по файлам агрегатов.** Связь шагов держится на типах задач. Проверить на
  пути «отмена → возврат», что он читается.
- **`EventSink` позволяет следующему решению видеть уже применённое событие;** чистый `handle` так не умеет. Найти
  агрегаты с несколькими событиями на команду, которым это нужно.
- **Модули-плагины ломают правила слоёв:** запрет `cqrsx` в `presentation`, список разрешённого в `domain`, слои как
  каталоги верхнего уровня.
- **Сложность может просто переехать в движок,** этажом ниже. То, что ушло из демо, должно стать проще и в cqrsx.

## Результат

Бэклог построен 2026-10-27 (задачи 02–15). Исследование по пунктам «Что исследовать»:
1. **Инвентарь API** — в задачах: типовой путь (`Decide`, `Reactions`, `#[task_handler]`, `View`, `Module`, `Cqrs`),
   строительные блоки, которые остаются для своих хранилищ и тестов cqrsx (`CommandExecutorCore`, `TaskPlanner`,
   адаптеры, `supervisor::run`), внутреннее (всё остальное) — задачи 05, 07, 09, 11, 14.
2. **Гарантии → код → тесты** — guarantees.md; семь пробелов, все закрываются в 02 или 11.
3. **Целевой API** — design/, дерево — задача 03; вариант слоёв сверху остаётся запасным (тема 15 пересмотра).
4. **Настройки:** движок читает все ключи механизмов сам с приставкой (`Cqrs::from_env("ENCORE")`), модули — свои
   через `Setup`; умолчания демо — `.defaults(..)` в `main.rs`; эталон действующей конфигурации — задача 02;
   перечень ключей по владельцам — задача 12.
5. **Зависимости модулей** — реестр по типу (`.provide`, `ctx.dependency::<T>()`), проверка при сборке — задачи 09, 11.
6. **Операции демо над движком** — `cqrs.views()`: статус с отставанием, перестройка, перестройка ключа, сверка;
   машина времени — история агрегата без снапшотов через `shared/infrastructure` — задачи 10, 11.
7. **Порядок миграции** — README эпика, каждый шаг — зелёный коммит; перенос 62 реализаций `Aggregate` — задача 05.
8. **Документы** — задача 14; D-26 заменяет D-25.
