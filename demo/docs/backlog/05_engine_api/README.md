# Эпик 05. API движка для типового сценария

[← все эпики](../README.md)

Цель — чтобы приложение на cqrsx описывало только бизнес. Агрегат, его правила и события — в `domain`. Реакции на
события и обработчики задач — декларативно в `application`. Bootstrap в пару строк: СУБД журнала и витрин и модули
приложения, которые подключаются как плагины. Очереди, пробуждения, повторы, лимиты и каналы — внутри фреймворка.

**Главное правило эпика: поведение движка не меняется.** Остаются прежними:
- логика работы;
- гарантии согласованности и доставки;
- политики, лимиты и действующие настройки;
- тексты SQL и внешние контракты.

Меняется только опыт пользователя API. Что именно не меняется — задача [01](01_requirements_and_backlog.md), раздел
«Что не меняется»; как это доказано — [таблица гарантий](guarantees.md): гарантия → код → тест → задачи эпика.
Согласованный API — [design/](design/README.md) (семь файлов, 2026-10-27).

Задачи берём по порядку номеров. Почему такой порядок:

1. **02 первой.** Пробелы в тестах гарантий закрываются до того, как код начнёт меняться: эталоны действующей
   конфигурации, ленты активности и пауз повторов, инструмент сравнения множеств SQL. Иначе нечем доказать, что
   умолчание или пул не поменялись незаметно.
2. **03 — переезд дерева до правок API.** Чистые перемещения, один коммит; дальше каждая правка демо ложится на место,
   и дерево «на пробу» оценивается на знакомом коде.
3. **04 → 05 → 06 → 07 — снизу вверх по пути команды:** сначала контракты, которые не трогают поведения (derive),
   затем решение команды (`Decide`), типизированный id и реакции. Каждый шаг — отдельный зелёный коммит; 05 самый
   широкий (62 реализации агрегатов в cqrsx), поэтому он не совмещён ни с чем.
4. **08 и 09** снимают прослойки демо вокруг команд и задач: наблюдатель команд даёт ленту, контекст задачи — следующую
   команду; паузы повторов переезжают в политики, когда их уже считает исполнитель.
5. **10 (витрины)** независима от 05–09 и может идти параллельно после 03; стоит перед 11, потому что сборке нужны
   `View::NAME` и запросы движка.
6. **11, затем 12:** сначала сборка и движок в памяти (общая часть и тесты сценариев без баз), потом бэкенды
   PostgreSQL и MongoDB, настройки из окружения и `serve()`; демо избавляется от `config.rs`, `process.rs`, `bootstrap/`.
7. **13 → 14 → 15:** замер на стенде на окончательном коде, документы с цифрами, пересмотр решений — последняя задача.

Что уходит из демо по ходу эпика: `CommandService`, `ConcertApp`, `FanApp`, сценарии в одну строку (08); `ChainStep`,
`run_chain_step`, `map_fan_outcome`, фабрика диспетчеров, формула паузы почты (09); порт и адаптер витрин, LWW,
сверка (10); `config.rs`, `process.rs`, `bootstrap/` (12). Путь «отмена → возврат» — семь файлов в двух модулях
вместо 22 в четырёх каталогах.

## Общие правила

- **Задачи берём по одной, в порядке бэклога.** Каждый коммит проходит все проверки `CLAUDE.md`, покрытие ≥ 97 %.
- **Неизменность поведения доказывается** тестами гарантий ([guarantees.md](guarantees.md)) и эталонами задачи 02;
  раздел «Поведение не меняется: чем доказано» каждой задачи ссылается на строки таблицы. Задача, которая
  переименовывает тест, правит таблицу. На стенде — задача 13, по правилам README эпика 04 («до» и «после»
  вперемешку, образ «до» из `git archive`).
- **Один коммит на задачу:** `refactor(cqrsx): <что>; adopt in demo`, для задач только про демо —
  `refactor(demo): <что>`, про документы — `docs(backlog): …`. В коммит входят изменение, тесты, `components.md` и
  перевод демо.
- **Стенд** — только проект `encore-load`, прогоны не дольше 5 минут; dev-стек пользователя не трогать.
- **Коммит** — только по явной просьбе пользователя.
- **Обратная совместимость не нужна:** API, схема и скрипты меняются так, как чище.
- **Каждое настраиваемое значение** — константа умолчания и переменная окружения с прежним именем; режимов и
  переключателей не добавляем.
- **Перед закрытием эпика** — [список тем для пересмотра](revisit.md), задача 15.
