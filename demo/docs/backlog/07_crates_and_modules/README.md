# Эпик 07. Крейты и модули cqrsx

[← все эпики](../README.md)

Цель — чтобы устройство фреймворка читалось как его модель, а границы между частями проверял компилятор. Сейчас
верхний уровень `cqrsx` повторяет историю кода (форк cqrs-es и наращивание по эпикам): модуль `cqrs` собрал
и контракты домена, и исполнение команд, и журнал, и всю сторону чтения; `cqrs` и `task` зависят друг от друга по
кругу; бэкенд в памяти лежит в `testing`; PostgreSQL и MongoDB разрезаны между своими модулями и `engine`; семь фич
с цепочками зависимостей и 134 `cfg(feature)`. Внутри подсистем код разложен хорошо — его не трогаем.

Источник — разбор структуры 2026-10-31 (в чате с пользователем): дерево модулей, оценка выноса в крейты, система фич.

**Главное правило эпика: поведение не меняется.** Остаются прежними логика, гарантии согласованности и доставки,
действующие умолчания и лимиты, тексты SQL, имена переменных окружения, JSON `GET /api/config`, ленты и коды отказов.
Меняются пути, имена, крейты и фичи.

## Итог (2026-10-31)

Эпик выполнен: десять задач приняты и закоммичены по одной (ход и журнал — [status.md](status.md)).

- **Дерево ядра читается как модель:** `domain → task → journal → command → reactions → projection → view → worker →
  memory`. Зависимости идут только сверху вниз, без циклов: журнал не знает ошибок команды, `task` не знает `worker`.
- **Семь крейтов вместо двух:**
  - `cqrsx` — ядро, без фич;
  - `cqrsx-engine` — фичи `postgres`, `mongodb`, `http`, по умолчанию ни одной;

- **Имена и путь команды.** Derive называются как трейты и лежат рядом с ними. Команда исполняется одной публичной

## Как будет устроено

### Крейты и зависимости

```text
cqrsx-macros ← cqrsx ← { cqrsx-postgres, cqrsx-mongodb } ← cqrsx-engine ← приложение
               cqrsx ← cqrsx-testing ← тесты приложения (dev-dependency)
               cqrsx-fixtures (publish = false): dev-dependency тестов фреймворка, от cqrsx не зависит
```

| Крейт | Что в нём | Фичи |
|---|---|---|
| `cqrsx-macros` | derive и `#[task_handler]`; раскрытия называют только `::cqrsx` | — |
| `cqrsx` | ядро: контракты домена, задача как данные, журнал, команды, реакции, проекции, витрины, исполнение задач, бэкенд в памяти | — |
| `cqrsx-postgres` | журнал и снимки, outbox, очередь задач, контрольные точки, витрины, пул, SQL | — |
| `cqrsx-mongodb` | витрины и контрольные точки | — |
| `cqrsx-engine` | `Cqrs`, `Builder`, `Module`, `Setup`, `Settings`, запросы витрин, точки входа команд, `serve` | `postgres`, `mongodb` (включает `postgres`), `http`; по умолчанию — ничего |
| `cqrsx-testing` | `TestFramework`, проверки результата, `MemStore`, `TestCommandExecutor`, `UnavailableStore`; dev-dependency приложения | — |
| `cqrsx-fixtures` | контейнеры PostgreSQL и MongoDB, аренда портов, захват логов для тестов | — |

Фичи `worker`, `host`, `logging` исчезают: исполнение задач компилируется всегда (процессоры проекций и так требуют
tokio rt, экономия была одним `async-channel`), `host` и `logging` — части `serve`. `mongodb` включает `postgres`:
контрольная точка в MongoDB хранит позицию журнала PostgreSQL. `http` включает процесс (сигналы, логгер, остановка),
потому что другого режима процесса нет. Все `cfg(feature)` сходятся в выборе бэкенда и в `serve` движка.

Демо: `cqrsx`, `cqrsx-engine = { features = ["postgres", "mongodb", "http"] }`, `cqrsx-testing` в dev-dependencies.

### Дерево ядра

Центральный контракт модуля — в его родительском файле, поэтому путь короткий: `cqrsx::view::View`,
`cqrsx::task::Task`, `cqrsx::worker::TaskHandler`.

```text
cqrsx/src/
├── lib.rs          только mod, extern crate self as cqrsx, __private
├── domain/         что пишет домен: aggregate (Aggregate), event (Event, Events, EventEnvelope),
│                   command (Command, Decide, Label), rejection (Rejection); derive — рядом с трейтами
├── task.rs, task/  задача как данные: Task, NewTask, TaskSchedule; format, attempt, policy
├── journal.rs, journal/
│                   EventStore, PersistenceError; persisted, repository, serialized_event, snapshot, upcaster,
│                   feed (Position, FeedEntry), wakeup (CommitWakeup)
├── command.rs, command/
│                   CommandExecutor, CommandGatewayError, CommitReport, AggregateError; executor, attempt
│                   (бывший CqrsFramework, закрытый), locks, retry, observer, metadata, causation, planner
├── reactions.rs    Reactions, Decided, Then, ReactionsPlanner
├── projection.rs, projection/
│                   EventHandler, RebuildableProjection; processor (owner, lease, delivery, rebuild, config,
│                   observer), checkpoint, runtime
├── view.rs, view/  View; projection (ViewProjection), repository (ViewRepository, StoredView), verify
├── worker.rs, worker/
│                   TaskHandler, TaskResult, task_handler; context, dependencies, handlers, dispatcher, adapter,
│                   executor, queue, runtime
├── memory.rs, memory/
│                   бэкенд в памяти: event_repository, task_queue, checkpoint_store, view_repository
├── diagnostics.rs  safe_type, StorageFailure: что адаптеры дают логам ядра (публичный, задача 08); лог-строки ядра —
│                   закрытые
└── mutex.rs        lock, get_mut: std::sync::Mutex по правилу 10 (публичный: им пользуются движок и cqrsx-testing)
```

Зависимости внутри ядра — строго сверху вниз, без циклов:
`domain → task → journal → command → reactions → projection → view → worker → memory`
(модуль зависит только от модулей левее). Три правки, без которых цикл остаётся: `CommitWakeup` переезжает в
журнал, `impl CheckpointKey { fn of::<V, A>() }` — в `view.rs`, порт журнала
перестаёт возвращать ошибки команды ([задача 06](06_command_execution.md)).

Задачи берём по порядку номеров. Почему такой порядок:

1. **01 первой.** Без тестов PostgreSQL и движка ядро сегодня покрыто на 97,08 % строк — впритык; `projection/runtime.rs`
   покрыт на 0 %, его проверяют только тесты движка и `host`. Дыры закрываются тестами в памяти до переездов, иначе
   задача 08 упрётся в порог.
2. **02–04 — дерево ядра внутри одного крейта.** Компилятор видит всё сразу, а переезд крейтов потом идёт по уже чистым
   границам. Три задачи, а не одна: каждая — один обозримый коммит, и после каждой всё зелёное.
3. **05 после переездов:** derive встают рядом с трейтами уже на новых местах, и раскрытия макросов правятся один раз.
4. **06 до крейтов:** пресеты PostgreSQL удаляются раньше, чем их пришлось бы переносить в `cqrsx-postgres`; порт
   журнала без ошибок команды снимает последний цикл внутри ядра.
5. **07 до 08:** движок нельзя оставить в ядре, когда адаптеры станут крейтами (цикл `cqrsx → cqrsx-postgres → cqrsx`).
   Поэтому сначала уходит движок (пока на фичах ядра `postgres`/`mongodb`), затем адаптеры, и фичи ядра исчезают.
6. **09 после 08:** юнит-тесты ядра перестают пользоваться тестовыми инструментами — после этого их можно вынести.
7. **10 последней:** общий проход документов, матрица фич, пороги покрытия по крейтам, сверка числа тестов с «до».

## Общие правила

- **Задачи берём по одной, в порядке бэклога. Одна задача — один коммит**, коммит делает оркестратор после
  приёмки (поручение пользователя 2026-10-31; ход — в [status.md](status.md)). Сообщение: `refactor(cqrsx): <что>; adopt in demo`; для 10 — `docs: …`.
- **Каждый коммит зелёный:** fmt, clippy, тесты рабочей области, сборка и тесты демо (`demo/back-end`, включая эталоны
  `tests/contracts.rs` и правило архитектуры `tests/architecture.rs`). Покрытие (`llvm-cov`) — в 01, 08 и 10: в 02–05
  только переезды и переименования, для них прогона покрытия не делаем.
- **Поведение не меняется: чем доказано.** Набор тестов не теряет ни одного теста (меняются пути и имена, не проверки);
  [таблица гарантий эпика 05](../05_engine_api/guarantees.md) правится, если тест переехал или переименован; эталоны
  демо (`tests/contracts.rs`, `tests/golden/`) остаются байт в байт. Число тестов «до» записывает 01, каждая задача
  сверяет его со своим.
- **В коммит задачи входят** перевод демо, `cqrsx/doc/components.md` (пути, раздел «Source layout»), README и
  `typical_scenario.md` там, где задача ломает пути, и правки `.claude/rules/rust-style.md`, если в правиле назван
  старый путь.
- **Без фасадов и алиасов:** старый путь исчезает в той же задаче, где появляется новый. Исключения — решение 2.
- **Замеров производительности нет** (решение пользователя 2026-10-31): горячий путь не меняется. Переезды не меняют
  сгенерированный код; код горячего пути обобщён по агрегату и собирается в крейте приложения, как сейчас; вызов через
  `dyn` вместо `match` (если его выберет план 06) стоит наносекунды против транзакции в миллисекунды. Мерим только то,
  от чего зависит доказательство: число тестов и покрытие.
- **Правила кода** применяются к коду, который задача переносит и меняет; переписывать перенесённый код ради стиля
  не нужно.
