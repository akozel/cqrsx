## Сейчас

- На стенде есть точки 01 (горячий ключ), 02b (разные концерты), 03a (слив задач). Они проходят путь «команда →
  событие → витрина → задача» demo, где у каждого агрегата одна витрина, каждое событие планирует не больше одной
  задачи и у задач нет `#[label]`.
- Расходы, которые растут с числом витрин и задач (F1, F2, F5 и другие из задачи 04), на этих точках почти не видны.
- Счётчика аллокаций нет: малую экономию копирований стенд не отличит от шума (разброс CPU на команду — несколько
  процентов, см. задачу 05/13).

## Станет

### 1. Подсчёт аллокаций: `cqrsx/tests/allocations.rs`

- Своя `#[global_allocator]`-обёртка над `System`: счётчики числа аллокаций и байт (атомики). Отдельный тестовый
  crate, поэтому на остальные тесты не влияет. Тест помечен `#[ignore]` и запускается явно:
  `cargo test --release -p cqrsx --test allocations -- --ignored --nocapture`.
- Движок в памяти (`Cqrs::in_memory()`), runtime `current_thread`, чтобы чужие потоки не попадали в счётчик.
- Тестовый агрегат с одной командой и одним событием; K витрин по его событиям (K ∈ {1, 4}); реакция планирует M
  задач на событие (M ∈ {0, 1, 4}); у задачи есть вариант с полем `#[label]` (для F2).
- Фазы считаются отдельно: прогрев, затем N команд (`execute`), затем `catch_up()` (витрины), затем `run_tasks()`
  (задачи). Итог — таблица: аллокаций и байт на команду, на событие на витрину, на задачу, для каждого (K, M, label).
- Результат детерминирован: два запуска на одном коммите дают одинаковые числа; это проверяется перед записью «до».

### 2. Синтетический модуль нагрузки `probe` (demo, feature `load`)

- Feature `load` в `back-end/Cargo.toml`; в обычной сборке модуля нет. `main.rs` подключает `.module(probe::module)`
  только под этой feature.
- Свой агрегат `Probe` (одна команда — одно событие), маршрут `POST /api/probe/{id}`. Код модулей `concert`, `fan`,
  `operations` не меняется.
- `ENCORE_LOAD_VIEWS=K` (0–4): K дешёвых витрин по событиям `Probe` (счётчик событий на id). Разные `View::NAME`
  через константный параметр типа или `macro_rules!`.
- `ENCORE_LOAD_TASKS=M` (0–4): реакция планирует M пустых задач на событие; у задачи одно поле `#[label]`.
- Значения по умолчанию — 0; переменные перечислены в `.env.example` с пометкой, что они только для стенда.

### 3. Стенд

- `back-end/Dockerfile` получает аргумент `CARGO_FEATURES` (по умолчанию пусто); образы эпика собираются с `load`.
- `load/k6/probe.js`: `KEYS=n` — число id (1 — горячий ключ для F1, иначе у каждого VU свои id).
- `perf/compose.probe.yaml` передаёт `ENCORE_LOAD_VIEWS`/`ENCORE_LOAD_TASKS` в бэкенд (через `LOAD_COMPOSE_EXTRA`),
  `perf/series.sh` — обёртка серии по образцу задачи 05/13: план строк `<префикс> <образ> <сценарий> КЛЮЧ=…`,
  перемешивание `random.Random(f"{seed}-{pass}")` с журналом порядка, запуск под сабрипером.
- **Образ «до»** — `encore-load-backend:e06-base` из коммита этой задачи (`git archive`), с feature `load`.

## Этапы

1. Тест `allocations.rs`; два запуска подряд дают одинаковые числа.
2. Модуль `probe`, feature `load`, `.env.example`; тесты модуля в памяти (команда, K витрин, M задач).
3. `probe.js`, `compose.probe.yaml`, `series.sh`, аргумент Dockerfile; проверочные прогоны `REPEAT=1` всех точек.
4. Коммит задачи; образ `e06-base` из него; базовая серия (8 конфигураций × 3 повтора).
5. Таблица «до» — в этот файл: аллокации по (K, M, label) и медианы стенда с min–max.

## Риски

- **Модуль `probe` меняет обычную сборку demo.** Он целиком под feature `load`; проверка — `cargo build` demo без
  feature собирается без модуля и маршрута.
- **Счётчик ловит аллокации фоновых задач движка.** Runtime `current_thread` и замер фаз только после прогрева; если
  числа плавают между запусками — искать фоновые таймеры, а не усреднять.
- **Шум хоста** (замедление примерно раз в 5 минут): перемешанный порядок и `REPEAT=3`, доверять CPU на операцию.

## Как проверить

- `cargo test --release -p cqrsx --test allocations -- --ignored --nocapture` дважды — одинаковый вывод.
- Сборка demo с `--features load` и без; `bash -n` скриптов; `node --check probe.js`.
- Серия только на стенде `encore-load`; dev-стек пользователя не трогается.
