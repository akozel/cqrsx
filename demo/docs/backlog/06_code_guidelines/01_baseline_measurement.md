## Сейчас

- На стенде есть точки 01 (горячий ключ), 02b (разные концерты), 03a (слив задач). Они проходят путь «команда →
  событие → витрина → задача» demo, где у каждого агрегата одна витрина, каждое событие планирует не больше одной
  задачи и у задач нет `#[label]`.
- Расходы, которые растут с числом витрин и задач (F1, F2, F5 и другие из задачи 04), на этих точках почти не видны.
- Счётчика аллокаций нет: малую экономию копирований стенд не отличит от шума (разброс CPU на команду — несколько
  процентов, см. задачу 05/13).

## Станет

### 1. Подсчёт аллокаций: `demo/load/epic06/allocations/tests/allocations.rs`

- Своя `#[global_allocator]`-обёртка над `System`: счётчики числа аллокаций и байт (атомики). Отдельный тестовый
  crate, поэтому на остальные тесты не влияет. Тест помечен `#[ignore]` и запускается явно:
  `cargo test --release --locked --manifest-path demo/load/epic06/Cargo.toml -p epic06-allocations -- --ignored --nocapture`
  (до 2026-10-30 — `cqrsx/tests/allocations.rs`, `cargo test --release -p cqrsx --test allocations …`).
- Движок в памяти (`Cqrs::in_memory()`), runtime `current_thread`, чтобы чужие потоки не попадали в счётчик.
- Тестовый агрегат с одной командой и одним событием; K витрин по его событиям (K ∈ {1, 4}); реакция планирует M
  задач на событие (M ∈ {0, 1, 4}); у задачи есть вариант с полем `#[label]` (для F2).
- Фазы считаются отдельно: прогрев, затем N команд (`execute`), затем `catch_up()` (витрины), затем `run_tasks()`
  (задачи). Итог — таблица: аллокаций и байт на команду, на событие на витрину, на задачу, для каждого (K, M, label).
- Результат детерминирован: два запуска на одном коммите дают одинаковые числа; это проверяется перед записью «до».

### 2. Синтетический модуль нагрузки `probe` (`demo/load/epic06/backend`)

- Crate `epic06-backend` своего workspace `demo/load/epic06`: модуль `probe` и `main.rs` demo с ещё одним
  `.module(probe::module)`; модули demo он берёт из библиотеки `encore_backend` по пути. В demo модуля нет (до
  2026-10-30 он был там под cargo feature `load`).
- Свой агрегат `Probe` (одна команда — одно событие), маршрут `POST /api/probe/{id}`. Код модулей `concert`, `fan`,
  `operations` не меняется.
- `ENCORE_LOAD_VIEWS=K` (0–4): K дешёвых витрин по событиям `Probe` (счётчик событий на id). Разные `View::NAME`
  через константный параметр типа или `macro_rules!`.
- `ENCORE_LOAD_TASKS=M` (0–4): реакция планирует M пустых задач на событие; у задачи одно поле `#[label]`.
- Значения по умолчанию — 0; переменные описаны в README каталога `demo/load/epic06/`.

### 3. Стенд

Всё — в `demo/load/epic06/`; `run.sh` и файлы постоянного стенда не меняются.

- `Dockerfile` собирает образ бэкенда стенда с `probe` (`encore-load-backend:<тег>`, `perf/build.sh`).
- `k6/probe.js`: `KEYS=n` — число id (1 — горячий ключ для F1, иначе у каждого VU свои id). Сценарий для `run.sh` —
  `../epic06/k6/probe` (путь от `demo/load/k6`).
- `perf/compose.probe.yaml` передаёт `ENCORE_LOAD_VIEWS`/`ENCORE_LOAD_TASKS` в бэкенд и монтирует сценарий для k6
  (через `LOAD_COMPOSE_EXTRA`), `perf/series.sh` — обёртка серии по образцу задачи 05/13: план строк
  `<префикс> <образ> <сценарий> КЛЮЧ=…`, перемешивание `random.Random(f"{seed}-{pass}")` с журналом порядка, запуск
  под сабрипером.
- **Образ «до»** — `encore-load-backend:e06-base`: движок и demo коммита `a270a06` (`git archive`) с каталогом
  `demo/load/epic06/` поверх (`perf/build.sh e06-base <журнал> a270a06`).

## Этапы

1. Тест `allocations.rs`; два запуска подряд дают одинаковые числа.
2. Модуль `probe` и бэкенд стенда с ним; тесты модуля в памяти (команда, K витрин, M задач).
3. `probe.js`, `compose.probe.yaml`, `series.sh`, `Dockerfile` каталога; проверочные прогоны `REPEAT=1` всех точек.
4. Образ `e06-base`; проверочные прогоны всех девяти конфигураций. Серия «до → после» — шесть из них
   (`demo/load/epic06/perf/series.plan`): пользователь ограничил серию 40 минутами (2026-10-30).
5. Таблица «до» — в этот файл: аллокации по (K, M, label) и медианы стенда с min–max.

## Риски

- **Замеры оставляют следы в cqrsx, demo или стенде.** Всё в `demo/load/epic06/`; проверка —
  `grep -rn 'ENCORE_LOAD\|epic06\|/api/probe' cqrsx cqrsx-macros demo --exclude-dir=epic06 --exclude-dir=docs
  --exclude-dir=results --exclude-dir=target` пуст.
- **Счётчик ловит аллокации фоновых задач движка.** Runtime `current_thread` и замер фаз только после прогрева; если
  числа плавают между запусками — искать фоновые таймеры, а не усреднять.
- **Шум хоста** (замедление примерно раз в 5 минут): перемешанный порядок и `REPEAT=3`, доверять CPU на операцию.

## Как проверить

- `cargo test --release --locked --manifest-path demo/load/epic06/Cargo.toml -p epic06-allocations -- --ignored
  --nocapture` дважды — одинаковый вывод.
- Workspace `demo/load/epic06`: build, fmt, clippy `-D warnings`, тесты (`--locked`, офлайн); `bash -n` скриптов;
  `node --check k6/probe.js`.
- Серия только на стенде `encore-load`; dev-стек пользователя не трогается.

Что видно:

- **Команда без задач** — 192 аллокации и 20 КБ. Каждая запланированная задача добавляет к команде 27–29 аллокаций и
  около 4 КБ (сборка задачи, её JSON, запись в outbox), задача с `#[label]` — ещё 6 аллокаций: перенос поля в
  метаданные (F2).
- **Событие в витрине** — 84 аллокации и 10,9 КБ, но 77,85 аллокаций и 10,1 КБ из них — чтение страницы журнала в
  памяти: `MemEventRepository::feed_after` копирует все события типа (с прогревом — 2 048), а процессор читает две
  страницы (1 000 событий и пустую). Это слагаемое хранилища в памяти, не движка; тест читает те же две страницы ещё
  раз после замера и вычитает их. Собственная цена движка — 6,3 аллокации и 0,8 КБ на событие на витрину; от K она не
  зависит (каждая витрина читает и раскладывает события сама). Значит, правки F1/F5 будут видны в этой колонке, и
  каждая аллокация в ней — 16 % от неё.
- **Задача** — 15,9 аллокаций и 1,9 КБ без label, 22,9 и 2,7 КБ с label: label стоит задаче 7 аллокаций и 0,75 КБ
  (F2: при разборе он возвращается из метаданных в тело). При M = 4 на задачу на 1,6 аллокации больше, чем при M = 1: очередь в памяти перед
  каждым захватом собирает индексы ожидающих задач, а их за раунд из 10 команд 40, а не 10.

Отклонения от задачи: счётчик — crate `stats_alloc` (dev-dependency `cqrsx`), а не своя обёртка над `System`: своя
требует `unsafe`, а правило 32 его запрещает, и задача 06 включает `unsafe_code = "forbid"` на все цели crate, тесты
тоже. Чтобы фазы не смешивались, команды и задачи выполняются через `tokio::task::unconstrained` (процессоры,
разбуженные коммитами, не получают управления внутри фазы; тест проверяет, что перед догоном каждая витрина отстаёт
ровно на 1 000 событий), а часы runtime остановлены (`start_paused`): таймеры процессоров и опрос `catch_up` идут
только когда runtime простаивает, поэтому число опросов, а с ним и аллокаций, не зависит от скорости машины.
