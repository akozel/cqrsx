# Эпик 06. Код cqrsx по правилам

[← все эпики](../README.md)

Цель — привести `cqrsx` и `cqrsx-macros` к [правилам кода](../../../../.claude/rules/rust-style.md) (34 правила,
приняты 2026-10-30 на основе Google Rust Style Guide) и закрепить их lints, чтобы нарушения не возвращались. Источник
задач — [аудит 2026-10-30](../../cqrsx-style-audit.html) на HEAD `e995a53`: 11 находок с риском, 43 места, где
возможен panic, 16 молчаливых восстановлений mutex, 18 лишних копирований, 84 механические правки по lints, около
130 элементов и 26 модулей без документации. Номера правил в задачах — номера из файла правил.

**Правила эпика.**
- **Поведение движка не меняется**, кроме исправлений из задачи 02: там каждая находка — сегодняшнее падение или
  неверное поведение, и каждая перечислена. Тексты SQL, имена переменных окружения, действующие умолчания и JSON
  `GET /api/config` остаются прежними.
- **Одна задача — один коммит.** Каждый коммит зелёный по `CLAUDE.md` (fmt, clippy, тесты, оба прогона покрытия
  ≥ 97 %). Правки demo, которых требует задача, — в том же коммите.
- **Lints включаются вместе с исправлениями:** группа попадает в `[lints]` в том же коммите, где число её срабатываний
  доходит до нуля. Иначе `clippy -D warnings` упадёт.
- **Совместимость не держим** (проект не выпущен): переименования без псевдонимов, устаревшее удаляется.
- **Ускорения — только по замеру.** Правка из задачи 04, которая усложняет код и не даёт видимого выигрыша ни в
  подсчёте аллокаций, ни на стенде, остаётся на решение пользователя (так в эпике 04 были отклонены 03u и 05).
- **Demo этот эпик не проверяет:** правила действуют и для него, но его аудит — отдельная работа после эпика.

Задачи берём по порядку номеров. Почему такой порядок:

1. **01 первой.** Подсчёт аллокаций и синтетический модуль нагрузки появляются до правок кода. Образ «до» — коммит
   задачи 01, поэтому синтетика есть и в «до», и в «после», и стенд сравнивает одинаковые точки.
2. **02 — сразу после замера.** Это падения и неверное поведение, которые есть уже сейчас; правки малые и местные.
3. **03 до 04.** Правки panic меняют те же функции, что и правки копирований (`delivery.rs`, `owner.rs`, `task.rs`);
   сначала поведение и lints, затем замеряемые ускорения на устоявшемся коде.
4. **04 — единственная задача, ради которой мерим по ходу:** каждое исправление проверяется подсчётом аллокаций, вся
   задача — стендом против 01.
5. **05 после задачи 05/15.** Переименования и типы API задевают тот же API, что пересмотр решений эпика 05. Если
   05/15 затянется, 06 и 07 можно взять раньше 05 — они от неё не зависят по смыслу, только по месту правок.
6. **06 и 07 — механика и чистка**, на скорость не влияют; их проверяет итоговый замер.
7. **08 последней:** итоговая серия против 01 ловит регрессии всех задач сразу.

## Как мерим

Подробно — в задаче [01](01_baseline_measurement.md); здесь — главное.

**Что от чего растёт.** Событие по контракту одно на команду (`Decide` возвращает `Result<Event, Error>`), поэтому
расходы «на событие» на стороне записи — это расходы на команду. Расходы проекций растут с числом витрин: каждая читает
и декодирует события сама. Расходы задач — с числом задач на событие. В demo сейчас у каждого агрегата одна витрина,
каждое событие планирует не больше одной задачи, и у задач нет `#[label]`. Поэтому часть исправлений на нынешнем demo
не проявится, и в замер добавлены синтетические витрины и задачи.

| Где растёт | Находки (задача 04) |
|---|---|
| на команду | F4 (metadata), F7 (replay), `into_map`, запись событий в PostgreSQL, снимок раз в N команд |
| на событие × на витрину | F1 (объединение заданий на горячем ключе), F5 (поиск ключа), `event_type`/`event_version` строкой, копия ключа в `owner.rs` |
| на задачу | F2 (задачи с labels), F6 (при сборке) |
| запросы и движок в памяти | F3, ключи витрин в `engine/views.rs` |

**Два способа.**
1. **Подсчёт аллокаций** — тест `cqrsx/tests/allocations.rs` со своим счётчиком аллокаций на движке в памяти: число
   аллокаций и байты на команду, на событие в каждой витрине и на задачу при K витрин и M задач на событие. Без шума,
   за секунды, вклад каждого исправления виден отдельно.
2. **Стенд** `demo/load` тем же способом, что в задаче [05/13](../05_engine_api/13_measurement_before_after.md):
   образы «до» и «после» собираются заранее, серии вперемешку, порядок вариантов перемешан в каждом проходе,
   `REPEAT=3`, каждый прогон не дольше 5 минут. Прежние точки 01 app/db, 02b, 03a и новые — модуль `probe` с K
   витрин и M задач. Главная метрика — CPU бэкенда на 1 000 команд и на 1 000 задач: пропускная способность горячего
   ключа упирается в ожидание записи WAL и от правок в памяти не сдвинется.

## Открытые вопросы

1. **Синтетика в demo** — cargo feature `load` с модулем `probe` (задача 01): подходит ли такой способ и какие
   значения брать. Предложено: витрин K = 1 и 4, задач на событие M = 1 и 4.
2. **Как вести эпик** — по одной задаче с отчётом после каждой или через оркестратора, как эпик 05.

## Вне эпика: решить отдельно

Находки аудита вне правил кода:
- `Cqrs::describe()` публичный и отдаёт `DATABASE_URL` и `MONGODB_URI` целиком, с паролем; сейчас его читают только
  тесты. Предложение: маскировать пароль в описании.
- `host/lifecycle.rs:122` форматирует `JoinError` через `to_string()`: в tokio это включает сообщение panic, а правило
  в `host/error.rs:24–25` это запрещает.
- Движок в памяти (`Cqrs::in_memory()`) работает на хранилищах из модуля `cqrs::testing`. По дереву кажется, что это
  код только для тестов. Предложение: вынести их, например, в `memory`; тогда граница правила 8 видна по пути.
