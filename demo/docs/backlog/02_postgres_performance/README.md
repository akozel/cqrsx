# Эпик 02. Пропускная способность PostgreSQL-хранилища

[← все эпики](../README.md)

Источник: оценка «а что если event store на NoSQL» (2026-10-20). Вывод: на одном узле смена СУБД заметного прироста
не даст. Два из трёх потолков стенда вообще не в базе, а третий в основном съедают лишние обращения к Postgres, и их
можно убрать в текущем коде. Этот эпик — список таких улучшений. Каждая задача самостоятельна: что сейчас, что
станет, зачем на примере, риски, как измерить, критерии приёмки. Код «после» — эскиз, имена можно менять.

Итого 9–11 обращений, а по делу нужно два: прочитать состояние и записать событие. Пинги при возврате идут
в фоновой задаче и на время ответа не влияют, но тратят CPU Postgres (М1) и держат соединение вне пула до
ответа (М2). Базовая линия это подтверждает: анонс в 02a — 3 SQL-запроса, но 18 пакетов, то есть 9 обращений. Операция очереди задач
(claim, settle) стоит ещё 5 обращений вместо одного ([04](04_single_statement_queue.md)).

## Почему меньше обращений — это больше пропускной способности

Задачи ссылаются на эти три механизма.

- **М1. Работа за каждое сообщение.** Даже пустой пинг для Postgres — это пробуждение процесса, разбор протокольного
  сообщения, системные вызовы и ответ. В 02a Postgres уже загружен на 94 % на пике, и каждое лишнее сообщение
  отнимает CPU у полезных запросов. На стороне бэкенда то же самое: пробуждения tokio, кодирование и декодирование
  в sqlx.
- **М2. Соединение занято, пока идёт разговор.** Пул — это ограниченное число линий. Пусть в пуле 20 соединений, а
  команда в сумме держит их 1.5 мс: больше 20 / 1.5 мс ≈ 13 тыс. команд/с пул не пропустит. При 0.6 мс потолок
  ≈ 33 тыс./с.
- **М3. Окно гонки.** Между «прочитал состояние» и «записал событие» другой запрос может записать своё, и наша
  запись получит конфликт. Чем больше обращений в этом окне, тем оно шире и тем больше 409 на популярном агрегате.

## Общие правила

- Одна задача — один коммит: `perf(cqrsx): <что>; adopt in demo`. Для задач только про стенд — `perf(load): <что>`.
  В коммит входят изменение, тесты, `cqrsx/doc/components.md` и перевод demo.
- Агент не коммитит по своей инициативе (`git commit`, `--amend`, `push`): только когда пользователь прямо
  попросит. Иначе он оставляет готовое рабочее дерево и предлагает сообщение коммита и список файлов.
- Замер против базовой линии из задачи 01: точки задачи из раздела «Что мерить» ниже, тот же бюджет CPU и пул 20.
  Во время замера на машине ничего не собирать и не запускать: компиляция параллельно с замером сдвинула
  даже CPU на команду на 12–24 %. Пока задача в работе — `REPEAT=1` (1–2 минуты: видно, сдвинулись ли
  метрики на команду), для приёмки — `REPEAT=3`. Сравниваем пропускную способность, p99, CPU на 1000 принятых
  команд и запросы и пакеты на команду. Результат записать в тикет (статус, коммит, цифры «было → стало») и в `demo/docs/PROGRESS.md`.
- Правка, которая не дала выигрыша, не вливается автоматически: решаем по цифрам, оставить ли её ради простоты кода.
- Покрытие `cqrsx` не ниже 97 %, матрица фич из корневого `CLAUDE.md`, wire-формат demo не меняется.
- Схема (`cqrsx/sql/`) меняется без миграций: проект не выпущен, базы пересоздаются (правило эпика 03).
- Стенд изолирован (`encore-load`). Запущенный dev-стек пользователя не трогаем.

## Что мерить

Полная матрица нужна только для базовой линии: 28 минут, из них 11 уходит на слив с двумя воркерами. Задача
меряет **одну точку** в **профиле, где узкое место — то, что она меняет**, и сравнивает код «до» и «после» в
одной сессии, чередуя прогоны: тогда обе версии меряются в одних и тех же условиях хоста.

- **Профили.**
  - `full` — бюджет стенда 4/4/3/4. С wrk потолок анонсов — MongoDB (~13 тыс./с), а с k6 — сам генератор
    (~11 тыс./с); в обоих случаях правка в PostgreSQL в req/s не видна, только в метриках на команду.
  - `db` даёт PostgreSQL 2 ядра, и потолком становится он.
  - `app` даёт бэкенду 2 ядра. Под квотой многопоточный бэкенд упирается в неё рывками, и req/s гуляет на
    десятки процентов (замер задачи 02: 7.7–11 тыс. у одной версии). Здесь надёжны только метрики на
    команду; для req/s нужны выделенные ядра (cpuset, `load/README.md`, «CPU isolation»). PostgreSQL в
    профиле `db` под квотой ведёт себя ровно.
- **Генератор.** wrk (`perf/generator/`) тратит ~21 мс CPU на 1000 запросов против ~245 у k6 и упором не
  бывает. Сценарий для него пока только у анонсов; горячий ключ, брони и слив идут на k6, там стенд медленнее
  его предела.
- **Время.** Одна точка, два профиля, «до» и «после», `REPEAT=3`: 12 прогонов по ~23 с и две сборки по ~21 с —
  около 5 минут. Один профиль — около 3 минут. Пока задача в работе, хватает одного прохода.

Порядок замера (из каталога `perf/`, `<base>` — коммит до задачи):

```bash
# образ «до»: исходники коммита и текущий Dockerfile (с кэшем сборки)
mkdir -p /tmp/base-src && git -C ../../../../.. archive <base> | tar -x -C /tmp/base-src
docker build -f ../../../../back-end/Dockerfile -t encore-load-backend:base /tmp/base-src
# образ «после» — текущее дерево
docker compose -p encore-load -f ../../../../load/compose.yaml build backend
# прогоны вперемешку: на каждом проходе «до», затем «после», в каждом профиле
for pass in 1 2 3; do for profile in db app; do
  ./run.sh announce-storm PREFIX=perf-wrk-$profile-base- NAME=02a-announce-vus100-r$pass VUS=100 POOL=20 \
    PROFILE=$profile BACKEND_IMAGE=encore-load-backend:base
  ./run.sh announce-storm PREFIX=perf-wrk-$profile-<nn>- NAME=02a-announce-vus100-r$pass VUS=100 POOL=20 \
    PROFILE=$profile
done; done
node tools/compare.mjs ../../../../load/results perf-wrk-db-base- perf-wrk-db-<nn>- --md
```

Слив в 03a не обрезается окном. Скорость слива меняется по ходу: сначала идут задачи `encore_record_ticket`,
потом порождённые ими `encore_send_e_ticket`. Поэтому первые 30 с дают другую цифру, чем слив целиком, и
разброс у неё больше (6–8 % против 2–5 %). Слив с 8 и 32 воркерами и так короткий: 23–49 с.

## Решено не делать

- **NoSQL вместо PostgreSQL на одном узле.** Атомарная запись «событие + снапшот + задачи» в PostgreSQL — один
  запрос. В MongoDB это либо транзакция на 3–4 обращения, либо отказ от атомарности снапшота. Потолки 02b и 01 от
  базы не зависят. Вернуться, если понадобится масштабирование вширь и задача 15 окажется дороже.
- **`jsonb` вместо `json`.** Мы не ищем внутри payload. `jsonb` тратит CPU на преобразование при записи и обратно в
  текст при чтении.
- **`synchronous_commit = off`.** Быстрее, но при падении PostgreSQL пропадут команды за последние доли секунды, на
  которые клиент уже получил 200. Для источника истины это смена гарантий, а не оптимизация.
- **Одно соединение на всю команду.** Держать соединение во время бизнес-логики — значит сужать пул (М2). Довод
  «после задачи 02 взять соединение ничего не стоит по сети» верен лишь наполовину: при возврате sqlx всё равно
  пингует соединение. Поэтому вопрос пересматривается в задаче [04/16](../04_operation_costs/16_release_ping.md), уже с
  замером.
- **Растить пул дальше.** Замер: 20 → 40 соединений прироста не дали. Больше соединений — больше процессов
  PostgreSQL, которые делят те же 4 ядра.

## Приложение: инструменты замера `perf/`

Скрипты задачи 01 лежат в [`perf/`](perf/README.md), исходный нагрузочный стенд остаётся в
[`demo/load/`](../../../load/README.md) без изменений. Есть только одно исключение: в `run.sh` стенда добавлены две
общие точки расширения, `LOAD_COMPOSE_EXTRA` и `LOAD_HOOKS`.

- `perf/run.sh` запускает прогон стенда с `pg_stat_statements` (`compose.perf.yaml`) и снимками счётчиков
  (`hooks.sh`).
- `perf/matrix.sh` — точки 01/02a/02b/03a с `REPEAT` и `ONLY`.
- `perf/report.sh` и `perf/tools/compare.mjs` — медианы, min–max и сравнение серий.

Результаты прогонов лежат в `demo/load/results/` (не в git), HTML-отчёт эпика — в
`demo/load/results/perf-report.html`.
