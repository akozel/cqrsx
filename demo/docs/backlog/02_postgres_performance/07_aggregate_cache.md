## Сейчас

Каждая команда восстанавливает агрегат с нуля: читает снапшот, разбирает его JSON (у концерта 40 мест), читает до 9
событий после снапшота, разбирает JSON каждого и применяет их к состоянию. Через миллисекунду следующая команда к
тому же концерту делает всё то же самое. В 02b это не база, а CPU бэкенда, и именно он там предел (~4.9k/с).

`PostgresCommandExecutor` строит на каждый вызов новый `PersistedEventStore` (`postgres/command.rs`), поэтому
хранить что-то между командами сейчас негде.

## Станет

```rust
// cqrsx: cqrs/store/cache.rs
/// Last committed state per aggregate ID, bounded by entry count (LRU).
pub struct AggregateCache<A: Aggregate> { /* Mutex<Lru<String, Cached<A>>> */ }
struct Cached<A> { aggregate: A, current_sequence: usize, snapshot_version: Option<usize> }

// cqrsx: cqrs/store/persisted.rs
impl<R, A> PersistedEventStore<R, A> {
    pub fn with_cache(self, cache: Arc<AggregateCache<A>>) -> Self { … }
}

// cqrsx: postgres/command.rs
PostgresCommandConfig::with_aggregate_cache(capacity: NonZeroUsize)
// PostgresCommandExecutor::new creates one Arc<AggregateCache<A>> and hands a clone to every per-command store
```

Поведение:
- **Загрузка, попадание.** Взять копию из кэша и дочитать только события после закэшированного номера:
  `get_events_after(cached.current_sequence)`, одно обращение, обычно 0 строк. Снапшот не читается и не разбирается,
  события до этого номера не применяются заново.
- **Загрузка, промах.** Как сейчас.
- **Успешная запись.** Применить новые события к закоммиченному контексту и положить в кэш вместе с новым номером
  и версией снапшота.
- **Конфликт или неизвестный исход** (ошибка соединения). Выбросить агрегат из кэша. Retry загрузит его честно.

Режим «доверять кэшу» (не дочитывать хвост, 0 чтений на команду) — отдельный флаг для замера. Устаревший кэш в этом
режиме обнаружится конфликтом при записи. Включать его по умолчанию — отдельное решение после замеров и задачи 08.

## Зачем, на примере

Бронь при попадании в кэш: одно чтение хвоста (обычно пустое) и одна запись. Ни разбора JSON снапшота, ни повторного
применения событий. Сейчас (без задач 02–05) это 6–8 обращений и разбор до 10 JSON-документов. Для 02b это прямая
разгрузка CPU бэкенда. Для горячего ключа — более короткое окно между чтением и записью (М3).

## Почему это безопасно

Защиту от гонок по-прежнему даёт уникальный ключ `(aggregate_type, aggregate_id, sequence)` в базе. Устаревший кэш
(агрегат изменил другой экземпляр бэкенда или другой исполнитель) не может привести к неверной записи: запись
получит конфликт, кэш сбросится, команда повторится. Кэш ускоряет, но на корректность не влияет.

Тонкость со снапшотами: если другой экземпляр записал снапшот, версия в нашем кэше отстала. Наш следующий CAS
снапшота получит конфликт → выброс из кэша → retry. Это редкий и корректный путь, нужен тест.

## Риски

- **Память.** Лимит в записях плюс LRU. Концерт маленький, `Fan` после D-14 тоже ограничен. Для агрегатов, растущих
  без границы, кэш вреден, но для них уже есть правило из discussions/05.
- **Новая зависимость.** Свой простой LRU или крейт `lru` — решить при реализации по правилам зависимостей `cqrsx`.
- **Блокировка.** `Mutex` держится только на `get` и `put`, никогда через `await`.
- **По умолчанию выключен в библиотеке** (`with_aggregate_cache` не вызван — поведение как сейчас). В demo — env
  `ENCORE_AGGREGATE_CACHE_CAPACITY`, `0` = выключен; на стенде — параметр `CACHE=`.

## Как измерить

Матрица 02b и 01 с `CACHE=0` и `CACHE=10000`, `REPEAT=3`. Ожидание:
- 02b: `cpu_ms_per_1k_accepted` у бэкенда заметно ниже, RPS выше до следующего предела;
- `statements_per_command` ниже (нет запроса снапшота);
- 01: меньше 409/с.

Отдельно — режим «доверять кэшу».

## Критерии приёмки

- [ ] `AggregateCache` с юнит-тестами: попадание, промах, выброс при конфликте, выброс при неизвестном исходе,
      вытеснение по лимиту.
- [ ] `PersistedEventStore::with_cache`: загрузка с дочиткой хвоста, обновление после записи. Тест на устаревшую
      версию снапшота (конфликт → выброс → успешный retry).
- [ ] Интеграционный тест на PostgreSQL: два исполнителя со своими кэшами пишут в один агрегат («два экземпляра»).
      Журнал без дыр и дублей, оба кэша в итоге согласованы с базой.
- [ ] `PostgresCommandConfig::with_aggregate_cache`. Demo: env и сборка в `bootstrap.rs`. Стенд: `CACHE=`.
- [ ] `components.md`: новая строка в таблице компонентов, дерево исходников.
- [ ] Замер против базовой линии записан в тикет.
