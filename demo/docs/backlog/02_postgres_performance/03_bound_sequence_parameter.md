## Сейчас

```rust
// cqrsx: postgres/event_repository/sql_query.rs:83
pub fn select_events_after(&self, after_sequence: i64) -> String {
    format!("SELECT ... FROM {} WHERE aggregate_type = $1 AND aggregate_id = $2 AND sequence > {} ORDER BY sequence",
        self.event_table, after_sequence)
}
```

Тип и id агрегата передаются параметрами, а номер, после которого читать, вклеен в текст литералом.

sqlx держит на каждом соединении кэш разобранных запросов на 100 записей, и ключ кэша — текст запроса. Для него
`sequence > 30` и `sequence > 40` — два разных запроса. Каждый новый текст стоит отдельного обращения (`Parse` +
`Describe`, Postgres разбирает и планирует запрос). Когда кэш полон, нужно ещё одно — закрыть выселенную запись
(`sqlx-postgres 0.8.6`, `connection/executor.rs`, `get_or_prepare`).

## Станет

```rust
// sql_query.rs: one text for every watermark
select_events_after: format!(
    "SELECT ... FROM {event_table}
      WHERE aggregate_type = $1 AND aggregate_id = $2 AND sequence > $3
      ORDER BY sequence"),

// read.rs
sqlx::query(self.query_factory.select_events_after())
    .bind(A::TYPE)
    .bind(aggregate_id)
    .bind(encode_bigint(after_sequence)?)
```

`select_events` сейчас принимает готовый текст и привязывает два параметра. Ему нужен вариант с третьим параметром,
или общая функция, которая получает уже собранный `Query`.

## Зачем, на примере

Горячий концерт: номер снапшота растёт каждые 10 команд — 30, 40, 50… Команды раскиданы по 20–40 соединениям,
поэтому почти каждое соединение видит очередной текст впервые. Чтение «хвоста» стоит до трёх обращений вместо
одного: разбор, выселение, выполнение. Все три приходятся на окно гонки (М3).

В 02b эффект меньше. Номер вклеен, но id агрегата — параметр, поэтому текст `sequence > 30` общий для всех
концертов. В концерте не больше ~100 событий, различных текстов около десятка, и они быстро оседают в кэше.

## Риски

Нет: семантика запроса та же, меняется только способ передачи числа.

## Как измерить

- По схеме README эпика («Что мерить»): точка `01-hot-key-vus40`, профиль `db`, генератор k6; «до» и «после»
  вперемешку. Ожидание: `packets_per_command` и 409/с ниже, принятых команд/с больше.
- ~~В `pg_statements.tsv` вместо сотен строк `... sequence > <N>` одна строка с `$3`~~ — не так:
  `pg_stat_statements` сам заменяет литералы на `$n`, и строка одна и до правки. Разбор запросов виден в CPU
  PostgreSQL и в пакетах.

## Как сделано

Как в «Станет»:
- `SqlQueryFactory` строит текст `select_events_after` один раз, с `sequence > $3`, и отдаёт его как `&str`;
- `get_events_after` привязывает тип агрегата, id и номер (`encode_bigint`) к одному `Query`;
- общее чтение `fetch_events` принимает уже собранный запрос, так что `get_events` и `get_events_after`
  различаются только текстом и числом параметров.

Публичный API не меняется.

Тесты:
- юнит-тест текста запроса;
- интеграционный: пул на одно соединение, `get_events_after` с десятью отметками, проверяется исключающая
  нижняя граница; в `pg_prepared_statements` этой сессии один запрос с `sequence >`, и он с `$3`;
- существующие тесты `get_events_after` проходят без правок.

## Результат

Замер 2026-10-20: точка `01-hot-key-vus40`, профиль `db` (PostgreSQL 2 ядра), k6. «До» — `6186fa9`, «после» —
эта правка, прогоны вперемешку, 3 прохода. Медиана, в скобках min–max; ≠ — диапазоны не пересекаются.

| Метрика | До | После | Δ |
|---|---|---|---|
| принятых команд/с | 417 (411–423) | 477 (476–479) | **+14 %, ≠** |
| req/s (с ответами 409) | 1402 (1395–1410) | 1602 (1592–1608) | +14 %, ≠ |
| p99, мс | 65.2 (62.1–68) | 58.2 (50.9–58.4) | −11 %, ≠ |
| доля 409 | 70.7 % | 70.1 % | без изменений |
| CPU PostgreSQL на 1000 принятых, мс | 4874 (4835–4959) | 4337 (4323–4393) | −11 %, ≠ |
| CPU back-end на 1000 принятых, мс | 3409 | 3281 | −4 %, ≠ |
| пакетов на принятую команду | 168 (165–169) | 160 (160–161) | −5 %, ≠ |
| SQL-запросов на принятую команду | 33.1 | 33.4 | без изменений |

- **PostgreSQL в обоих случаях упирается в свои 2 ядра** (пик 201 %), так что +14 % — это экономия его CPU на
  разборе и планировании нового текста запроса и на закрытии выселенных из кэша. Число запросов то же:
  меняется цена запроса, а не их количество.
- **Доля 409 не изменилась.** Окно гонки по времени (М3) сократилось, но команд в секунду стало больше в той же
  пропорции.
- В горячем ключе на одну принятую команду приходится ~7 откатов и ~33 запроса: остальное — проигранные гонки и
  их повторы. Дальше этим займутся задачи 06 и 08.

## Критерии приёмки

- [ ] Текст `select_events_after` не зависит от номера (юнит-тест в `sql_query.rs`: две разные отметки дают один
      текст с `$3`).
- [ ] Интеграционный тест: пул на одно соединение, `get_events_after` с десятью разными отметками, затем на том же
      соединении `SELECT count(*) FROM pg_prepared_statements WHERE statement LIKE '%sequence > $3%'` возвращает 1.
- [ ] Существующие тесты `get_events_after` (исключающая нижняя граница) проходят без правок.
- [ ] Замер против базовой линии записан в тикет.
