## Сейчас

Стенд меряет пропускную способность, латентность и CPU контейнеров (`stats.tsv`). Для этого эпика не хватает
четырёх вещей:

- **Не видно, что делает база.** `pg_stat_statements` не включён, поэтому неизвестно, сколько SQL-запросов
  приходится на команду и какие из них дорогие.
- **CPU снимается в процентах.** Это неудобно, когда правка не сдвигает потолок: в 02b предел — CPU бэкенда, и
  если задача 02 уберёт пинги, RPS может не измениться, хотя Postgres станет тратить на команду меньше. Сравнивать
  нужно CPU на единицу работы.
- **Каждый прогон делается один раз.** Контрольная серия гуляла в пределах ±4 %, так что изменение меньше ~5 % без
  повторов не отличить от шума.
- **Нет общей базовой линии.** Прежние серии сняты на разных бюджетах CPU и размерах пула.

## Станет

1. PostgreSQL стенда стартует с `shared_preload_libraries=pg_stat_statements` и `track_io_timing=on`. Расширение
   создаёт init-скрипт стенда, схема `cqrsx` не меняется.
2. `run.sh` сбрасывает статистику перед k6 (`SELECT pg_stat_statements_reset()`), а после прогона сохраняет:
   - `pg_statements.tsv`: нормализованный запрос, `calls`, `total_exec_time`, `mean_exec_time`, `rows`,
     `shared_blks_hit`, `shared_blks_read`;
   - `pg_counters.json`: `xact_commit` и `xact_rollback` из `pg_stat_database`, `wal_bytes` из `pg_stat_wal`,
     пакеты интерфейса контейнера PostgreSQL (`/sys/class/net/eth0/statistics/{rx,tx}_packets`) до и после.
3. `collect.mjs` добавляет в `result.json` производные метрики:
   - `cpu_ms_per_1k_accepted` по каждому контейнеру: средний CPU × длительность / принятые команды × 1000;
   - `statements_per_command`: Σ `calls` / все принятые команды за все фазы (warm-up входит и в числитель, и в
     знаменатель, поэтому сброс до k6 не искажает отношение);
   - `rollbacks_per_command`: откаты, то есть конфликты и ошибки;
   - `packets_per_command`: грубая оценка обращений к базе, одно обращение — не меньше двух пакетов.
4. `matrix.sh REPEAT=N`: каждая строка матрицы повторяется N раз с суффиксом `-r1…-rN`. Отчёт показывает медиану и
   разброс min–max.
5. Базовая линия: матрица 01 / 02a / 02b / 03a с `REPEAT=3`, `POOL=20`, бюджет 4/4/3/4, префикс `perf-base-`. Её
   таблица записывается в README эпика.

Пинги и разбор запросов (задачи 02 и 03) — это не SQL-запросы, в `pg_stat_statements` их нет. Их видно только по
`packets_per_command`, CPU на 1000 команд и пропускной способности. Поэтому счётчик пакетов нужен, хотя он и грубый
(TCP ACK тоже пакеты).

## Зачем, на примере

Задача 02 убирает три пинга из команды. В 02b RPS может остаться ~4.9k, потому что потолок там — CPU бэкенда. Без
новых метрик правка выглядела бы бесполезной. С ними будет видно, что `packets_per_command` упал примерно на 6, а
`cpu_ms_per_1k_accepted` у Postgres снизился. Значит, запас у базы вырос, и он сработает, когда задача 07 разгрузит
бэкенд.

## Риски

- `pg_stat_statements` сам стоит немного CPU. Он включён во всех прогонах эпика, включая базовую линию, так что
  сравнение честное. С прежними сериями без него сравнивать нельзя.
- Путь к счётчикам пакетов зависит от образа и сети podman. Если `eth0` нет, метрика пропускается с пометкой в
  `run.log`, а не роняет прогон.

## Критерии приёмки

- [ ] `pg_stat_statements` включён на стенде, сброс перед k6, `pg_statements.tsv` и `pg_counters.json` в каждом
      прогоне.
- [ ] `cpu_ms_per_1k_accepted`, `statements_per_command`, `rollbacks_per_command`, `packets_per_command` есть в
      `result.json` и в HTML-отчёте.
- [ ] `matrix.sh REPEAT=N`, отчёт с медианой и min–max.
- [ ] Базовая линия `perf-base-` (×3) записана в README эпика.
- [ ] `load/README.md` описывает новые файлы и метрики.
