## Сейчас

Запись команды — один CTE (`outbox/write.rs:65`, `persist_one`). Конфликт версий распознаётся по **исключению**:
вставка события с занятым `(aggregate_type, aggregate_id, sequence)` падает с `23505` на `events_pkey`, и
`map_sqlx_error` превращает это в `OptimisticLockError`.

```sql
WITH written_events AS (INSERT INTO events (...) VALUES (...) RETURNING sequence),
     written_tasks  AS (INSERT INTO transactional_outbox ... WHERE EXISTS (SELECT 1 FROM written_events) ...)
SELECT 1::bigint AS snapshot_count            -- without a snapshot the conflict is only the error
```

Каждое исключение в PostgreSQL — это отменённый оператор и запись в лог сервера. По умолчанию
(`log_min_messages = warning`, `log_min_error_statement = error`) Postgres пишет строку `ERROR: duplicate key …`,
`DETAIL` с ключом и `STATEMENT` с полным текстом CTE.

## Станет

В записи **без снапшота** (9 команд из 10 при `ENCORE_SNAPSHOT_EVERY=10`) конфликт распознаётся по числу вставленных
строк:

```sql
WITH written_events AS (
    INSERT INTO events (...) VALUES (...)
    ON CONFLICT (aggregate_type, aggregate_id, sequence) DO NOTHING
    RETURNING sequence),
     written_tasks AS (... WHERE EXISTS (SELECT 1 FROM written_events) ...)
SELECT (SELECT count(*) FROM written_events)::bigint AS written   -- 0 → OptimisticLockError
```

Задачи и так защищены `WHERE EXISTS (written_events)`: при конфликте их тоже не будет.

Запись **со снапшотом** не меняется. Там исключение нужно: оно откатывает снапшот вместе с событием. Если бы
событие «тихо» не вставилось, а снапшот записался, в базе остался бы снапшот с состоянием, которого нет в журнале.
При одинаковом интервале снапшотов у всех писателей такого не бывает, но гарантировать это для чужих конфигураций
нельзя.

## Зачем, на примере

Горячий ключ, 40 VU (серия `c1-`): ~1025 ответов 409/с, и каждый — три неудачные попытки записи. Это больше 3 тыс.
исключений в секунду, столько же записей `ERROR` + `STATEMENT` в лог Postgres и столько же отменённых операторов. После
правки 9 из 10 таких попыток завершаются обычным ответом «0 строк», без лога и без отмены.

## Риски

- Ветвление в построителе SQL: два варианта финального `SELECT`. Тесты — на оба.
- `map_sqlx_error` остаётся, он нужен для записи со снапшотом.

## Как измерить

- Матрица 01 против `perf-base-`: `cpu_ms_per_1k_accepted` у PostgreSQL, принятых команд/с.
- Число строк `duplicate key` в логе контейнера PostgreSQL за прогон: стенд сохраняет лог, если `run.sh` ещё этого не
  делает — добавить.

## Как сделано

- **Запись без снапшота.** Вставка события получает `ON CONFLICT (aggregate_type, aggregate_id, sequence) DO
  NOTHING`, а итоговый `SELECT` возвращает число вставленных событий. Ноль означает `OptimisticLockError`.
  Задачи по-прежнему защищены `WHERE EXISTS (written_events)`. При занятом номере PostgreSQL проверяет индекс
  до вставки, поэтому нет ни ошибки, ни откатанной транзакции, ни мёртвой строки в `events`.
- **Запись со снапшотом не менялась.**
  - Обновление снапшота (`UPDATE … WHERE current_snapshot = версия − 1`) и раньше распознавало конфликт без
    исключения: строка не находится, событие не вставляется.
  - Исключение остаётся только у первого снапшота агрегата (`INSERT` в `snapshots`): там оно откатывает снапшот
    вместе с событием.
  - Значит, на долгоживущем горячем агрегате ошибок почти не остаётся.
- **Тест.** Пул на одно соединение, статистика сессии сбрасывается принудительно
  (`pg_stat_force_next_flush()`):
  - контрольная ошибка `1/0` даёт +1 к `xact_rollback`;
  - конфликт без снапшота даёт `OptimisticLockError`, +0 откатов и ни одной задачи проигравшего;
  - конфликт с первым снапшотом даёт `OptimisticLockError`, +1 откат, без снапшота, без события и без задач.

  Существующий тест конкурентной записи по всем трём режимам проходит без правок.
- **Стенд.** `perf/hooks.sh` считает строки `ERROR:` и байты лога PostgreSQL за прогон: `db.pg_log_errors`,
  `db.pg_log_bytes`, `efficiency.pg_log_errors_per_command`, они же в `compare.mjs`.

## Результат

Замер 2026-10-21: точка `01-hot-key-vus40`, профиль `db` (PostgreSQL 2 ядра), k6. «До» — `3140799`, «после» —
эта правка, прогоны вперемешку, 3 прохода. Медиана, в скобках min–max; ≠ — диапазоны не пересекаются.

| req/s / p99, мс | 1533 / 59.7 | 1583 / 58.7 | +3 % / −2 %, шум |
| CPU PostgreSQL на 1000 принятых, мс | 4580 (4447–4615) | 4497 (4397–4633) | −2 %, шум |
| откатов на команду | 7.14 (6.83–7.18) | 0 | −100 %, ≠ |
| WAL на команду, байт | 8259 (8116–8298) | 4362 (4307–4452) | −47 %, ≠ |

| объём лога PostgreSQL за прогон | 5.8–17.3 МиБ | 0.01 МиБ | −100 % |

- **На пропускную способность правка не влияет.** На горячем ключе PostgreSQL занят в основном ожиданием на
  строке снапшота: `UPDATE snapshots …` — самый дорогой запрос в `pg_stat_statements`, пишущие выстраиваются
  за его блокировкой. Путь ошибки — малая доля этой работы.
- **Конфликт перестал быть сбоем.** Нет отката транзакции, нет мёртвой строки в `events`. WAL на команду
  вдвое меньше: прервавшаяся вставка тоже писала журнал. Лог PostgreSQL больше не забивается `ERROR` +
  `STATEMENT` с полным текстом CTE. Счётчик лога «до» занижен: откатов было ~7 на команду, а строк `ERROR`
  ~1, часть строк при таком потоке, похоже, теряет логгер контейнера.
- **SQL-запросов на команду стало на 26 % больше только в отчёте.** `pg_stat_statements` не считает
  упавшие запросы, а теперь конфликтная попытка завершается нормально и попадает в статистику.

**Решение 2026-10-21: оставить.** Прироста пропускной способности нет, но конфликт версий — нормальная
ситуация оптимистичной блокировки, а не ошибка. Теперь он и для PostgreSQL выглядит как обычный результат.
