## Сейчас

```rust
// cqrsx: postgres/pool.rs
PgPoolOptions::new()
    .max_connections(max_connections.get())
    .connect_with(options)
```

У sqlx по умолчанию `test_before_acquire = true`: прежде чем отдать соединение из пула, проверить, что оно живо.
Проверка — отдельный обмен сообщениями с сервером (`Sync` → `ReadyForQuery`). Она делается при **каждой** выдаче,
а не только для давно простаивавших соединений: `sqlx-core 0.8.6`, `pool/inner.rs:469`.

Команда берёт соединение трижды (снапшот, события, запись), значит три пинга. Claim, settle и recover в очереди
берут по одному соединению, это ещё пинг на каждую операцию.

## Станет

Пинговать только соединения, которые простаивали дольше порога. Именно этот вариант sqlx приводит в документации
к `before_acquire`.

```rust
// cqrsx: postgres/pool.rs
/// Connections idle for less than this are handed out without a liveness round trip.
pub const IDLE_PING_AFTER: Duration = Duration::from_secs(10);

PgPoolOptions::new()
    .max_connections(max_connections.get())
    .test_before_acquire(false)
    .before_acquire(|connection, meta| Box::pin(async move {
        if needs_ping(meta.idle_for) {
            connection.ping().await?;
        }
        Ok(true)
    }))
    .connect_with(options)
```

Если пинг не прошёл, sqlx закрывает соединение и выдаёт другое, а при нехватке открывает новое, как и сейчас.
`needs_ping` — отдельная чистая функция для юнит-теста. Порог сначала делаем константой. Параметром он станет, если
кому-то понадобится другой.

## Зачем, на примере

Анонс (02a) сейчас — это 9 обращений: 3 пинга при выдаче соединения, снапшот, события, CTE и ещё 3 пинга при
возврате соединения в пул. Последние sqlx делает всегда (задача
[04/16](../04_operation_costs/16_release_ping.md)). Базовая линия это подтверждает: 3.01 SQL-запроса и 18 пакетов на
команду. После правки останется 6 обращений, то есть на 6 пакетов
меньше. Postgres в 02a загружен на 94 % на пике, и две трети входящих сообщений в нём — пинги (М1). Под
нагрузкой соединение не простаивает и миллисекунды, поэтому пингов при выдаче не останется вовсе. После ночного
простоя первая команда пинганёт соединение, как сейчас.

## Риски

Соединение, которое «умерло» меньше порога назад (по умолчанию 100 мс, см. «Как сделано») (перезапуск PostgreSQL, обрыв сети), обнаружится на первом
запросе, а не на пинге:

- **Команда** вернёт `CommandGatewayError::Unavailable` (повторяются только конфликты). По контракту исход записи в этом случае неизвестен, хотя на
  деле запрос не ушёл. Клиент и так обязан уметь повторять запрос при `Unavailable`.
- **Операция очереди** вернёт `TaskProcessingError::Unavailable`, задача вернётся в работу через восстановление
  lease.

Это редкое событие, и оно короче порога. Его описание — в doc-комментарии `ConnectionPingPolicy::Idle` и в
`components.md`.

## Как измерить

Точки `02a-announce-vus100,02b-spread-vus100,03a-drain-w8` (README эпика, «Что мерить») против `perf-base-`.
Ожидание:
- `packets_per_command` меньше примерно на 6, а `statements_per_command` не меняется: пинги — не SQL, так
  что это проверка, что убраны только они;
- `cpu_ms_per_1k_accepted` у PostgreSQL и бэкенда ниже;
- RPS 02a и задач/с 03a выше.

В 02b RPS может не измениться: там предел — CPU бэкенда.

## Как сделано

От «Станет» два отличия, оба по решению 2026-10-20:

- **Политику пинга пользователь `cqrsx` выбирает явно, при создании каждого пула.**
  `ConnectionPingPolicy::Default` — поведение sqlx: пинг при каждой выдаче. `ConnectionPingPolicy::Idle(d)` —
  пинг только для соединения, простоявшего дольше `d`. Всё остальное в конфигурации пула — это `PgPoolOptions`
  самого sqlx, своей структуры нет.
  - `connect_pool_with(options, PgPoolOptions, policy)` подключается с диагностикой `cqrsx`.
  - `connect_pool(options, policy)` — то же с настройками пула sqlx по умолчанию.
  - `policy.apply(PgPoolOptions)` нужен тем, кто подключается сам.

  `connect_pool_with_size` удалена. demo пишет `connect_pool_with(options,
  PgPoolOptions::new().max_connections(n), ConnectionPingPolicy::Idle(DEFAULT_IDLE_PING_AFTER))`. (С задачи
  [04](04_single_statement_queue.md) у обеих функций есть ещё обязательный `StatementTimeout`.)
- **Рекомендуемый порог — 100 мс (`DEFAULT_IDLE_PING_AFTER`), а не 10 с.** Очередь свободных соединений в sqlx
  работает по принципу «первым пришёл — первым ушёл», поэтому соединение простаивает примерно `размер пула /
  выдач в секунду`. При 10 соединениях и 100 мс пинги пропадают уже от ~100 выдач в секунду (при 20 — от
  ~200), то есть под любой заметной нагрузкой. При малой нагрузке пинг остаётся, и там он ничего не стоит.
  Окно риска — 100 мс вместо 10 с.

Тесты: порог (юнит), `apply` для обоих вариантов (юнит). Интеграционные:
- `Idle` с порогом по умолчанию заменяет соединение, простоявшее дольше порога;
- риск `Idle` (порог 60 с): соединение, умершее только что, падает на первом запросе, следующий запрос идёт
  на новом;
- `Default` заменяет только что умершее соединение незаметно для вызывающего.

## Критерии приёмки

- [x] Пул создаётся с явной `ConnectionPingPolicy`: `Default` (пинг при каждой выдаче, как в sqlx) или
      `Idle(d)` (пинг только после простоя дольше `d`, рекомендуемый порог `DEFAULT_IDLE_PING_AFTER` = 100 мс).
- [x] Юнит-тест `needs_ping` (меньше порога, ровно порог, больше порога).
- [x] Интеграционный тест: соединение, убитое `pg_terminate_backend` и простоявшее дольше порога, заменяется
      прозрачно, запрос проходит. Порог по умолчанию (100 мс), без ожидания 10 с в CI.
- [x] Интеграционный тест на риск: соединение, убитое меньше порога назад, падает на первом запросе, следующий
      запрос идёт на новом соединении.
- [x] Doc-комментарий и `components.md` (строка «Backend assembly») описывают поведение и риск.
- [x] Замер против базовой линии записан в тикет.
- [x] fmt, clippy `-D warnings`, полный `cargo test`, матрица фич, оба `llvm-cov` ≥ 97 % (97.74 % строк,
      `postgres/pool.rs` — 100 %); в demo — fmt, clippy и `cargo test --workspace`.
- [x] Тексты тикета и README эпика исправлены с учётом пинга при возврате; заведена задача
      [04/16](../04_operation_costs/16_release_ping.md).
