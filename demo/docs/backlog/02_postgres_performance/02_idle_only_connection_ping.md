# 02. Пинг соединения только после простоя

| | |
|---|---|
| Статус | предложено |
| Ценность | высокая: минус 3 обращения на команду и 1 на операцию очереди, правка на несколько строк |
| Цена | низкая |
| cqrsx | `postgres/pool.rs`, `tests/postgres/pool.rs`, `doc/components.md` |
| demo | нет (пул создаётся через `connect_pool_with_size`) |
| Зависимости | 01 для замера |
| Где выигрыш | 02a (Postgres — предел), 03a, остальные через М1 и М2 |

## Сейчас

```rust
// cqrsx: postgres/pool.rs
PgPoolOptions::new()
    .max_connections(max_connections.get())
    .connect_with(options)
```

У sqlx по умолчанию `test_before_acquire = true`: прежде чем отдать соединение из пула, проверить, что оно живо.
Проверка — отдельный обмен сообщениями с сервером (`Sync` → `ReadyForQuery`). Она делается при **каждой** выдаче,
а не только для давно простаивавших соединений: `sqlx-core 0.8.6`, `pool/inner.rs:469`.

Команда берёт соединение трижды (снапшот, события, запись), значит три пинга. Claim, settle и recover в очереди
берут по одному соединению, это ещё пинг на каждую операцию.

## Станет

Пинговать только соединения, которые простаивали дольше порога. Именно этот вариант sqlx приводит в документации
к `before_acquire`.

```rust
// cqrsx: postgres/pool.rs
/// Connections idle for less than this are handed out without a liveness round trip.
pub const IDLE_PING_AFTER: Duration = Duration::from_secs(10);

PgPoolOptions::new()
    .max_connections(max_connections.get())
    .test_before_acquire(false)
    .before_acquire(|connection, meta| Box::pin(async move {
        if needs_ping(meta.idle_for) {
            connection.ping().await?;
        }
        Ok(true)
    }))
    .connect_with(options)
```

Если пинг не прошёл, sqlx закрывает соединение и выдаёт другое, а при нехватке открывает новое, как и сейчас.
`needs_ping` — отдельная чистая функция для юнит-теста. Порог сначала делаем константой. Параметром он станет, если
кому-то понадобится другой.

## Зачем, на примере

Анонс (02a) сейчас: 3 пинга + снапшот + события + CTE = 6 обращений. После правки — 3. Postgres в 02a загружен
на 94 % на пике, и половина входящих сообщений в нём — пинги (М1). Под нагрузкой соединение не простаивает и
миллисекунды, поэтому пингов не останется вовсе. После ночного простоя первая команда пинганёт соединение, как
сейчас.

## Риски

Соединение, которое «умерло» меньше 10 секунд назад (перезапуск PostgreSQL, обрыв сети), обнаружится на первом
запросе, а не на пинге:

- **Команда** вернёт `Unavailable` с ошибкой соединения. По контракту исход записи в этом случае неизвестен, хотя на
  деле запрос не ушёл. Клиент и так обязан уметь повторять запрос при `Unavailable`.
- **Операция очереди** вернёт `TaskProcessingError::Unavailable`, задача вернётся в работу через восстановление
  lease.

Это редкое событие, и оно короче порога. Его описание — в doc-комментарии `connect_pool_with_size` и в
`components.md`.

## Как измерить

Матрица 02a, 02b, 03a против `perf-base-`. Ожидание:
- `packets_per_command` меньше примерно на 6;
- `cpu_ms_per_1k_accepted` у PostgreSQL и бэкенда ниже;
- RPS 02a и задач/с 03a выше.

В 02b RPS может не измениться: там предел — CPU бэкенда.

## Критерии приёмки

- [ ] `connect_pool` и `connect_pool_with_size` отключают пинг на каждую выдачу и пингуют только после простоя
      дольше `IDLE_PING_AFTER`.
- [ ] Юнит-тест `needs_ping` (меньше порога, ровно порог, больше порога).
- [ ] Интеграционный тест: соединение, убитое `pg_terminate_backend` и простоявшее дольше порога, заменяется
      прозрачно, запрос проходит. Для теста порог задаётся через внутренний конструктор или параметр — решить при
      реализации, без ожидания 10 с в CI.
- [ ] Doc-комментарий и `components.md` (строка «Backend assembly») описывают поведение и риск.
- [ ] Замер против базовой линии записан в тикет.
