## Сейчас

40 запросов одновременно бронируют места на одном концерте. Все 40 читают состояние с номером N, все решают, все
пытаются записать событие N+1. Выигрывает один, остальные получают конфликт, ждут 5–50 мс (политика
`AggregateConflictRetryPolicy`, 3 попытки) и повторяют. После третьей неудачи клиент получает 409.

Замер (серия `c1-`, 40 VU): ~440 принятых команд/с и ~1025 ответов 409/с. Каждый 409 — три неудачные записи, то
есть база обрабатывает больше 3 тыс. попыток в секунду, и более 85 % из них — выброшенная работа: чтение, решение,
запись, откат, сон.

Похожая гонка есть и у витрины `concert_halls`. Обработчики соседних команд обновляют один документ через CAS с
повторами (в discussions/05 видно, как CAS исчерпывает 16 повторов).

## Станет

Команды к одному агрегату внутри процесса выполняются по одной, в порядке прихода:

```rust
// cqrsx: cqrs/command/gate.rs
/// One FIFO turn per aggregate ID inside this process; entries vanish when nobody waits.
pub struct AggregateGate { /* Mutex<HashMap<String, Weak<tokio::sync::Mutex<()>>>> */ }

impl AggregateGate {
    pub async fn enter(&self, aggregate_id: &str, max_wait: Duration) -> Result<Turn, GateTimeout> { … }
}

// cqrsx: cqrs/command/executor.rs
CqrsCommandExecutor::new(build, retry_policy).with_gate(gate: Arc<AggregateGate>)
// PostgresCommandExecutor owns one Arc<AggregateGate> per aggregate type, like the cache of ticket 07
```

Решения при реализации:

- **Где отпускать очередь.**
  - *После записи:* больше пропускная способность, но обработчики соседних команд, включая проекцию в MongoDB, идут
    параллельно, как сейчас.
  - *После обработчиков:* обновления витрины одного агрегата внутри процесса строго упорядочены, и CAS-гонка на
    `concert_halls` исчезает. Зато обработчики (2 обращения к MongoDB) попадают в последовательный участок, и потолок
    ниже.

  Сделать настройкой, замерить оба варианта. По умолчанию предлагаю «после обработчиков»: порядок проекций важнее.
- **Лимит ожидания.** `max_wait`, после которого команда получает `Conflict` (409) или `Unavailable` (503) вместо
  бесконечной очереди. Плюс ограничение длины очереди на агрегат, чтобы всплеск не съел память.
- **Повтор при конфликте внутри очереди.** Конфликт остаётся возможен (другой экземпляр, другой исполнитель того же
  типа). Повтор идёт, не выходя из очереди.

## Зачем, на примере

Сейчас 40 человек одновременно пишут в одну строку тетради: записать успевает один, остальные стирают и пробуют
снова. В очереди каждый пишет с первого раза. Пропускная способность одного агрегата ≈ 1 / (чтение + решение +
запись [+ обработчики]). С кэшем из задачи 07 чтения почти нет. При записи ~0.5 мс с fsync это порядка 2 тыс.
команд/с против ~440 сейчас (оценка; проверит замер). 409 внутри одного процесса пропадают.

## Риски

- **Только внутри процесса.** Несколько экземпляров бэкенда конкурируют между собой, как сейчас, через проверку в
  базе. Это корректно, просто медленнее. Если понадобится — маршрутизация запросов по `aggregate_id`.
- **Взаимная блокировка.** Если обработка команды синхронно выполняет другую команду **того же** агрегата, она будет
  ждать сама себя. В demo такого нет (вложенные команды идут через outbox), но правило нужно записать в
  `components.md`.
- **Латентность в очереди.** Она становится видимой: p99 горячего ключа может вырасти при росте пропускной
  способности. Смотреть оба числа.

## Как измерить

Матрица 01 (5 / 10 / 20 / 40 VU) с очередью и без, оба варианта отпускания. Метрики: принятых команд/с, 409/с,
`rollbacks_per_command` (ожидание ~0), p50 и p99, `projection_warning`.

## Критерии приёмки

- [ ] `AggregateGate` с юнит-тестами: FIFO, взаимное исключение по id, независимость разных id, таймаут ожидания,
      очистка записей без ожидающих.
- [ ] Исполнитель с очередью: тест «N параллельных команд к одному агрегату без конфликтов»; тест повтора при
      конфликте извне (второй исполнитель без общей очереди).
- [ ] Настройка места отпускания и `max_wait`. Demo: env, стенд: параметр `GATE=`.
- [ ] `components.md`: строка компонента и правило о вложенных командах.
- [ ] Замер против базовой линии записан в тикет.
