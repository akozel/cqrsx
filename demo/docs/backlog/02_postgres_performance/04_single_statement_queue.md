## Сейчас

Каждая операция очереди открывает транзакцию только ради таймаута:

```rust
// cqrsx: postgres/task_queue.rs:36
async fn begin_queue_transaction(&self, operation: &'static str) -> Result<Transaction<'_, Postgres>, _> {
    let mut tx = self.pool.begin().await?;                                    // ping + BEGIN
    sqlx::query("SELECT set_config('statement_timeout', $1, true)")          // + 1
        .bind(self.statement_timeout.as_millis().to_string())
        .execute(&mut *tx).await?;
    Ok(tx)
}
// claim / settle: one statement + COMMIT
```

Claim и settle — одиночные SQL-запросы, атомарные сами по себе. Транзакция нужна только для того, чтобы таймаут
действовал локально и не «протёк» в общий пул. В итоге 5 обращений (пинг, `BEGIN`, `set_config`, запрос, `COMMIT`)
вместо одного.

`recover_expired` хуже: `SELECT … FOR UPDATE SKIP LOCKED`, затем по отдельному `UPDATE` на каждую строку в цикле
(`recovery.rs`). Это N+3 обращения, и такая операция выполняется на каждом тике poller'а.

## Станет

У очереди свой пул, и таймаут задаётся на уровне его соединений, а не транзакции:

```rust
// cqrsx: postgres/pool.rs
/// A pool whose sessions carry the queue's statement timeout; only `connect_queue_pool` builds it.
pub struct QueuePool(PgPool);

pub async fn connect_queue_pool(
    options: PgConnectOptions,
    max_connections: NonZeroU32,
    config: &PostgresTaskQueueConfig,
) -> Result<QueuePool, sqlx::Error> {
    let options = options.options([("statement_timeout", config.statement_timeout().as_millis().to_string())]);
    // the same ConnectionPingPolicy as the main pool (ticket 02), via connect_pool_with
}

// cqrsx: postgres/task_queue.rs
impl PostgresTaskQueue {
    pub fn new(pool: QueuePool) -> Self { … }
}
// claim / settle: sqlx::query(...).fetch_all(&self.pool) — autocommit, one round trip
```

- **Тип `QueuePool`.** Гарантирует при компиляции, что очередь не получит пул без таймаута. Обычный `PgPool` в
  `PostgresTaskQueue::new` больше не принимается.
- **`prepare_task_runtime(queue_pool, dispatcher, runtime_config)`.** `PostgresTaskQueueConfig` переезжает в
  создание пула.
- **`recover_expired` одним запросом:** `WITH expired AS (SELECT … FOR UPDATE SKIP LOCKED) UPDATE … FROM expired
  RETURNING …`. Бэкофф сейчас считает Rust: `redelivery_backoff(attempts)`, 5 с × 2^(n−1), не больше 300 с, джиттер
  ±20 %. Варианты, решить при реализации:
  - формула в SQL с `random()` и тестом, что границы совпадают с `redelivery_backoff`;
  - массив задержек по номеру попытки (`$2::float8[]`), посчитанный на каждый вызов. Тогда у задач с одинаковым
    номером попытки в одной пачке джиттер общий.

Demo создаёт два пула:
- **командный** `ENCORE_DATABASE_POOL_SIZE`: HTTP и команды, которые выполняют обработчики задач;
- **очереди** `ENCORE_QUEUE_POOL_SIZE`: poller и settle, по умолчанию «воркеры + 1».

Воркеры пользуются обоими: claim и settle идут через пул очереди, команда `Fan` — через командный. Это закрывает п. 4
из [discussions/05](../../discussions/05_outbox_task_throughput.md): воркеры перестают отбирать соединения у HTTP.

## Зачем, на примере

Задача `encore_record_ticket` по разбору в discussions/05 стоит ~3 мс, пропускная способность = воркеры ÷ латентность.
Сейчас на задачу приходится settle (5 обращений) и доля claim (5 обращений на пачку). После правки settle — одно
обращение. Если команда `Fan` внутри задачи уже ускорена задачами 02 и 03, доля очереди в латентности задачи
заметна. Оценка: в 1.5–2 раза больше задач/с на воркер, пока база не насыщена. Проверит замер.

## Риски

- **Ломающее изменение API** (`PostgresTaskQueue::new`, `prepare_task_runtime`) — описать в теле коммита.
- **Сессионный таймаут.** Действует на всё, что выполняется на соединениях пула очереди. Пул отдельный, кроме
  очереди там ничего нет, и это нужно записать в doc-комментарий `QueuePool`.
- **Семантика lease, fencing и «исход неизвестен при таймауте» не меняется**: меняется только упаковка запросов.
  Тесты `tests/postgres/task_queue/{claim,settlement,timeouts,recovery}.rs` — сторожа.

## Как сделано

Решение 2026-10-21 после обсуждения и замеров: **не свой пул у очереди, а общий пул с таймаутом на
сессии**, и отдельный пул без таймаута для длинных чтений.

- **Почему так.** Команды и задачи обращаются к строго типизированным таблицам (события, снапшоты, outbox)
  статическими запросами, время их выполнения почти постоянное. Им подходит общий потолок времени запроса,
  4 с, заданный на сессии. Длинные чтения — полная пересборка проекций (`stream_all_events`), `totals`,
  машина времени — идут в отдельный пул без таймаута.
- **`cqrsx`: `StatementTimeout::{Default (4 с), Custom(Duration), Unlimited}`.** Это обязательный
  параметр `connect_pool` и `connect_pool_with`, как и `ConnectionPingPolicy`. Таймаут уходит параметром
  запуска каждой сессии, поэтому ни одному запросу не нужна транзакция.
  - `Custom` принимает `Duration`, а не `i16`. Тесты и PostgreSQL работают в миллисекундах (тесты
    таймаутов идут с 100 мс), а `Duration` — обычный тип длительности в Rust.
  - Недопустимое значение (меньше 1 мс или больше `i32::MAX` мс) даёт `sqlx::Error::Configuration` до
    подключения.
  - `Unlimited` явно ставит `statement_timeout = 0`, что бы ни было настроено на сервере.
- **Очередь.** `PostgresTaskQueue::new(PgPool)` и `prepare_task_runtime(pool, factory, runtime_config)`
  снова принимают общий пул. `PostgresTaskQueueConfig` удалён вместе с env
  `OUTBOX_POSTGRES_STATEMENT_TIMEOUT_MS`: его единственное поле, таймаут, теперь свойство пула.
- **Claim, settle и recover — по одному запросу без транзакции.** Recover:
  `WITH expired AS (… FOR UPDATE SKIP LOCKED) UPDATE … RETURNING`. Бэкофф `redelivery_backoff` переписан в SQL
  с `random()` на каждую строку.
- **Изменение поведения claim.** Схема запрещает такие строки CHECK-ограничениями на payload и metadata, так что
  речь о базе, где схема разошлась с кодом. Строка, которая не разбирается в доставку, раньше откатывала всю
  пачку и на каждом опросе снова первой попадала в выборку, блокируя свой формат. Теперь заявка уже зафиксирована: строка
  остаётся в аренде и возвращается через восстановление аренды, пока задача не станет `failed`. Остальная
  пачка доставляется.
- **Снапшоты.** В `components.md` и в doc-комментарии `StatementTimeout` записано: без снапшотов команда
  читает всю историю агрегата, и в текущей реализации агрегат с длинной историей без снапшотов может
  упереться в таймаут.
- **Demo.**
  - Основной пул `ENCORE_DATABASE_POOL_SIZE` с `ENCORE_DATABASE_STATEMENT_TIMEOUT_MS` (не задан — 4 с,
    `0` — без потолка) служит HTTP, обработчикам задач и очереди.
  - Пул истории `ENCORE_DATABASE_HISTORY_POOL_SIZE` (по умолчанию 1, `Unlimited`, без постоянных соединений:
    `min_connections(0)`, `idle_timeout` 30 с) служит Encore!, verify, `totals` и машине времени.
  - В обычной работе соединений столько же, сколько было; одно добавляется, только пока идёт длинное
    чтение.
- **Тесты.**
  - Каждая сессия пула несёт свой таймаут (`4s`, `125ms`, `0`), потолок действительно обрывает запрос
    (`57014`), недопустимый `Custom` отклоняется.
  - Очереди не нужно ни транзакции, ни права на `set_config`.
  - Битая строка (CHECK снят, как при расхождении схемы) остаётся в аренде, остальная пачка доставляется,
    восстановление аренды переводит строку в `failed`.
  - Бэкофф восстановления в границах `redelivery_backoff` для попыток 1–8, у каждой строки свой.
  - Тесты таймаутов, fencing, отказа при фиксации и переходов `pending`/`failed` перенесены на пул с
    таймаутом без изменения смысла.

## Результат

Замер 2026-10-21: точка `03a-drain-w8`, профиль `db` (PostgreSQL 2 ядра), k6, у обоих общий пул 20. «До» —
`2d0a85c`, «после» — эта правка, прогоны вперемешку, 3 прохода. Медиана, в скобках min–max; ≠ — диапазоны не
пересекаются.

| Метрика | До | После | Δ |
|---|---|---|---|
| SQL-запросов на задачу слива | 6.99 | 2.88 | **−59 %, ≠** |
| пакетов на задачу | 19.8 | 11.6 | **−41 %, ≠** |
| CPU back-end на 1000 задач, мс | 308 (307–311) | 265 (262–269) | −14 %, ≠ |
| CPU PostgreSQL на 1000 задач, мс | 868 (857–1030) | 862 (841–958) | −1 % |
| задач/с при сливе | 1848 (1830–2076) | 2023 (1852–2044) | +9 % |
| время слива, с | 43 (39–43) | 38 (35–41) | −12 % |
| API во время всплеска, req/s | 3524 (3481–3563) | 3436 (3225–3471) | −2 %, ≠ |
| запросов на команду во время всплеска | 4.13 | 3.59 | −13 %, ≠ |

- **`BEGIN`, `COMMIT` и `set_config` исчезли.** Операция очереди — одно обращение вместо четырёх. Recover —
  один запрос вместо N+3.
- **Слив быстрее по медиане** (+9 %, время −12 %), но диапазоны пересекаются. В профиле `db` слив упирается не
  только в очередь: обработчик `encore_record_ticket` выполняет команду `Fan` и пишет проекцию в MongoDB.
- **API во время всплеска почти не изменился** (−2 %). Воркеры быстрее и забирают чуть больше CPU базы.
- **Соединений столько же:** общий пул 20.

E2E-проверка пересборки (временный скрипт, без нагрузки):
- свежий стенд, потолок основного пула 1 с;
- 24 брони, 49 событий и 48 задач, все обработаны;
- verify до пересборки `ok`;
- медленная пересборка (80 мс на событие) шла 4 с и прошла: `ok`, 49 событий, 7 агрегатов. Каждая проекция
  читалась одним запросом около 2 с, то есть через пул истории без таймаута;
- verify после пересборки `ok`, машина времени и таймлайн отвечают, ошибок в логах бэкенда нет.

### Почему не отдельный пул очереди

Первая реализация дала очереди собственный пул с таймаутом на сессии, `QueuePoolSize::Default =
1 + max(1, W/10)`. Замер 03a-w8 в профиле `db`:

| Пул очереди (основной) | Задач/с при сливе | API во время всплеска, req/s |
|---|---|---|
| «до»: общий пул 20, транзакции | 1 821 (1 514–2 065) | 3 569 |
| 2 (18) — правило `W/10` | 1 176 (1 110–1 206) | 3 510 |
| 3 (18) | 1 619 | 3 255 |
| 4 (16), всего тоже 20 | 1 928 | 3 060 |
| 8 (18) | 2 013 | 2 862 |

Работы на задачу при этом стало намного меньше: запросов −59 %, пакетов −42 %, CPU PostgreSQL −31 %. Но:
- пул очереди надо угадать по размеру. Супервизор ждёт claim в общей очереди к пулу за пачкой settle, а
  `encore_send_e_ticket` — быстрый HTTP-вызов, так что settle занимает около четверти времени задачи, а не
  десятую;
- отдельный пул добавляет соединения;
- он сдвигает CPU базы от API к воркерам.

Общий пул с таймаутом убирает все три вопроса.
