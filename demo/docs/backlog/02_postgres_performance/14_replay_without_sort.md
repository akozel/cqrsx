## Сейчас

```sql
-- cqrsx: postgres/event_repository/sql_query.rs (all_events)
SELECT ... FROM events WHERE aggregate_type = $1 ORDER BY sequence
```

Первичный ключ упорядочен по `(aggregate_type, aggregate_id, sequence)`, то есть «по агрегатам», а запрос просит
«по номерам»: сначала все первые события всех концертов, потом все вторые… Индекс тут не помогает. Postgres
сортирует всю историю типа и только потом отдаёт первую строку. При `work_mem` 4 МБ большая сортировка идёт через
временные файлы на диске.

## Станет

Чтение страницами по ключу, в порядке индекса:

```sql
SELECT ... FROM events
 WHERE aggregate_type = $1 AND (aggregate_id, sequence) > ($2, $3)
 ORDER BY aggregate_id, sequence
 LIMIT $4
```

- **Каждая страница идёт по индексу.** Из-за `LIMIT` индексный план самый дешёвый. Память постоянна, первое событие
  приходит сразу.
- **Почему не просто сменить `ORDER BY`.** Если оставить один запрос без `LIMIT`, на большой таблице планировщик
  всё равно может выбрать полное чтение и сортировку: так дешевле получить *весь* результат. Страницы с `LIMIT`
  снимают этот выбор.
- **Один снимок данных.** Страницы выполняются в одной транзакции `REPEATABLE READ READ ONLY` на соединении потока,
  поэтому весь replay видит один снимок, как сейчас с одним запросом.
- **Отмена.** Поведение при закрытии потока потребителем (`ReplayFeed::closed`) и при ошибках сохраняется. Сторожа —
  тесты `tests/postgres/event_store/streams.rs`.

## Меняется контракт порядка

Было: «по `sequence` среди всех агрегатов типа». Станет: «события одного агрегата по порядку; агрегаты по
`aggregate_id`». Прежний порядок бизнес-смысла не нёс: номера разных агрегатов не сравнимы по времени, и глобальной
позиции в журнале нет.

Потребители в demo: витрины `concert_halls` (документ на концерт) и `fan_wallets` (документ на ledger
`<fan>:<concert>`, после D-14 это id агрегата `Fan`). Каждый документ строится из событий одного агрегата, так что
порядок между агрегатами им не важен. Записать новый контракт в doc-комментарий `ReplayStream` и `components.md`.

## Зачем, на примере

10 млн событий: сейчас сортировка гигабайтов во временных файлах. Rebuild долго стоит на старте, нагружает диск
и мешает живым командам ([discussions/03](../../discussions/03_rebuild_lock.md): касса во время «Encore!» закрыта,
так что чем короче rebuild, тем короче простой). После правки первое событие приходит сразу, временных файлов нет.

## Риски

- Проекция, которая собирает данные из нескольких агрегатов и неявно опиралась на чередование «по номерам». В demo
  таких нет. Для будущих проектов правило записывается в контракт.
- Долгая транзакция `REPEATABLE READ` держит горизонт очистки, как и нынешний долгий запрос: хуже не становится.

## Как измерить

Генератор истории на 1 и 5 млн событий (скрипт стенда), replay без проекции (только счётчик). Сравнить до и после:
- время до первого события и общее время;
- `pg_stat_database.temp_bytes` (ожидание: 0 после правки).

Проверку плана в CI не делать: на маленьких таблицах планировщик законно выбирает другое.

## Критерии приёмки

- [ ] `stream_all_events` читает страницами по ключу в одной транзакции `REPEATABLE READ READ ONLY`. Размер страницы —
      константа или настройка репозитория.
- [ ] Тесты: порядок внутри агрегата, все события ровно один раз на границах страниц (агрегат, разрезанный
      страницей), пустая история, отмена посреди страницы, ошибка посреди потока.
- [ ] Новый контракт порядка в `ReplayStream` и `components.md`.
- [ ] Замер на 1 и 5 млн событий записан в тикет.
