## Сейчас

Стенд и dev-стек используют настройки образа `postgres:18.6-alpine` по умолчанию:

| Параметр | По умолчанию | Почему это может мешать |
|---|---|---|
| `shared_buffers` | 128 МБ | рабочий набор (хвосты потоков, снапшоты, outbox) на длинном прогоне перестаёт помещаться |
| `max_wal_size` | 1 ГБ | при десятках МБ WAL в секунду контрольная точка срабатывает по объёму каждые ~30–60 с |
| `wal_compression` | off | после каждой контрольной точки первая запись в страницу кладёт в WAL всю страницу целиком |
| autovacuum для `transactional_outbox` | общие пороги (20 % мёртвых строк) | на таблице в десятки миллионов строк очистка запускается редко и работает долго |

На 13-секундных прогонах всё это почти не видно: база свежая и маленькая, контрольных точек нет.

## Станет

Набор параметров для стенда за флагом `PG_TUNED=1` (`command: postgres -c …` в `compose.yaml`):

- `shared_buffers`: около 25 % памяти контейнера (сейчас лимита памяти нет — задать его вместе с этим);
- `max_wal_size=8GB`, `checkpoint_timeout=15min`: реже контрольные точки, меньше полных страниц в WAL;
- `wal_compression=lz4`: полные страницы, которые всё же попадают в WAL, сжимаются;
- для `transactional_outbox`: `ALTER TABLE … SET (autovacuum_vacuum_scale_factor = 0.01, autovacuum_vacuum_cost_limit
  = 2000)`, чтобы очистка шла часто и маленькими порциями.

По итогам — рекомендации в документации `cqrsx`: что и почему настраивать под event store. Переносить ли их в
`demo/compose.yaml`, решить отдельно, demo — витрина, а не прод.

## Зачем, на примере

Soak на 3 тыс. броней/с: WAL пишется со скоростью десятки МБ/с, и при `max_wal_size=1GB` контрольная точка случается
примерно раз в минуту. После неё каждая первая модификация страницы пишет в WAL 8 КБ вместо сотни байт, и на графике
WAL и латентности видна «пила». С большим `max_wal_size` и сжатием пила реже и ниже.

## Чего не трогаем

`synchronous_commit` остаётся `on` (см. «Решено не делать» в README эпика). `fsync`, `full_page_writes` — тоже: это
надёжность, а не производительность.

## Как измерить

Soak (задача 10) с `PG_TUNED=0` и `PG_TUNED=1`:
- `wal_bytes`;
- число контрольных точек;
- p99 во времени;
- CPU PostgreSQL на 1000 команд;
- autovacuum outbox.

Короткая матрица — убедиться, что на потолках нет регрессии.

## Критерии приёмки

- [ ] `PG_TUNED=1` на стенде, параметры видны в `meta` результата.
- [ ] Soak с обеими конфигурациями, выводы в тикете: какие параметры помогли, какие нет.
- [ ] Рекомендации в документации `cqrsx` (только подтверждённые замером).
