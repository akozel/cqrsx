## Зачем

Очереди из 08 работают внутри процесса. Между нодами по-прежнему действуют проверка версии в базе и CAS проекции.
Без второй ноды на стенде нельзя проверить два утверждения из плана:
- при N нодах в гонке за горячий ключ остаются N участников, а не число запросов;
- привязка агрегата к ноде (все команды концерта на одной ноде) превращает очередь внутри процесса в
  единственного писателя агрегата.

## Что делаем

Оверлей `perf/compose.nodes.yaml` подключается через `LOAD_COMPOSE_EXTRA`, как остальные оверлеи эпика:

```text
k6 / wrk ──► nginx (balancer:8080) ──┬──► backend   (нода 1)
                                     └──► backend-2 (нода 2)
                    PostgreSQL, MongoDB, mail — общие
```

- **`backend-2`** — тот же образ и окружение, что у `backend`, включая `BACKEND_IMAGE=` для «до». Запускается
  после того, как `backend` готов: схема и стартовые данные создаются один раз, без гонки двух стартов.
- **`balancer`** — nginx, точная версия образа выбирается при реализации:
  - `upstream` с обеими нодами и `keepalive`; `proxy_http_version 1.1`, пустой `Connection`;
  - журнал доступа выключен (он стоит CPU), кроме проверочного режима;
  - SSE через стенд не идёт; если понадобится — `proxy_buffering off` для его пути.
- **Распределение — параметр `BALANCE=`:**
  - `round_robin` — равномерно, по умолчанию;
  - `key` — `hash $aggregate_key consistent`. Ключ вынимается из пути через `map`: `/api/concerts/{id}/…` и
    `/api/fans/{id}/…` → `concerts:{id}`, `fans:{id}`. Все команды одного агрегата приходят на одну ноду.
- **Генератор** (k6 или wrk) получает `BASE_URL=http://balancer:8080` вместо `http://backend:8080`.
- **Параметры `perf/run.sh`:**
  - `NODES=1|2` (по умолчанию 1, как сейчас);
  - `BALANCE=none|round_robin|key`. `none` — без nginx, допустимо только при `NODES=1`. `NODES=1 BALANCE=round_robin`
    — одна нода за nginx, база для накладных расходов балансировщика.
- **Бюджет CPU.** Суммарный бюджет бэкендов профиля (`PROFILE=app`: 2 ядра) делится между нодами поровну,
  чтобы сравнение «одна нода против двух» шло при одинаковом CPU. nginx получает своё ядро и считается отдельно.
- **Учёт.**
  - `hooks.sh` снимает CPU `backend-2` и `balancer`;
  - `collect.mjs` пишет в `result.json` CPU по нодам и сумму бэкендов, а в `efficiency` — CPU на 1000 команд
    для суммы и для nginx;
  - `compare.mjs` показывает новые строки;
  - параметры прогона (`nodes`, `balance`) записываются в `result.json`.
- **Готовность.** `run.sh` ждёт обе ноды. Если для этого нужна точка расширения в `demo/load/run.sh`
  (сейчас он ждёт одну), она добавляется так же, как `LOAD_HOOKS` и `LOAD_COMPOSE_EXTRA`, — без изменения
  поведения по умолчанию.

## Пограничные случаи

| # | Случай | Ожидаемое поведение |
|---|---|---|
| 1 | Две ноды стартуют одновременно | вторая ждёт готовности первой: схема, индексы MongoDB и стартовые данные создаются один раз |
| 2 | Воркеры outbox | работают на обеих нодах, слив вдвое мощнее. В отчёте указывается число воркеров на ноду; при сравнении слива — `LOAD_OUTBOX_WORKERS` на ноду вдвое меньше |
| 3 | `BALANCE=key` на горячем ключе | весь горячий концерт на одной ноде, вторая почти простаивает. Это и есть «единственный писатель»; суммарный CPU это покажет |
| 4 | Нода недоступна | nginx уводит запросы на живую ноду; для замеров это сбой прогона, а не результат: прогон проверяет, что обе ноды получили запросы |
| 5 | Старый образ (`BACKEND_IMAGE=` для «до») | обе ноды запускают его |
| 6 | `NODES=1 BALANCE=none` | стенд как сейчас, результаты сравнимы со всеми прежними |

## Проверка

- `bash -n` для скриптов, `node --check` для инструментов, `docker compose config` с оверлеем;
- проверочный прогон `01-hot-key` при `NODES=2` и обоих `BALANCE`. Журнал nginx с `$upstream_addr` в
  проверочном режиме показывает:
  - при `round_robin` запросы делятся между нодами примерно поровну;
  - при `key` запросы одного концерта идут на одну ноду;
- у обеих нод CPU больше нуля; verify после прогона `ok`;
- `NODES=1 BALANCE=none` даёт те же цифры, что до задачи (в пределах шума).

## Замер

Не задача движка, а инструмент. Базовые цифры для HEAD (до 08a), профиль `app`, k6, 3 прохода:
- `01-hot-key-vus40`: `NODES=1` напрямую, `NODES=1` за nginx, `NODES=2` `round_robin`, `NODES=2` `key`;
- контроль — `02b-spread-vus50` (разбросанные ключи, где две ноды должны масштабироваться).

Цифры записываются в тикет и служат точкой «до» для замеров 08a и 08b при двух нодах.

## Как сделано

- **Стенд (`demo/load/run.sh`).** Новая точка расширения `LOAD_SERVICES_EXTRA`, рядом с `LOAD_COMPOSE_EXTRA` и
  `LOAD_HOOKS`. Это сервисы, которые поднимаются вместе со стендом, должны стать здоровыми до k6, а их лог
  сохраняется как `<service>.log`. Без неё стенд работает как прежде.
- **Оверлеи эпика.**
  - `compose.balancer.yaml` — nginx `1.30.6-alpine` (тот же образ, что у заглушки почты): своё ядро квоты,
    проверка здоровья, `BASE_URL` генератора указывает на него.
  - `compose.node2.yaml` — `backend-2` через `extends` сервиса `backend` из `compose.yaml` стенда. Окружение то
    же, без копии; `build: !reset null`; образ первой ноды, включая `BACKEND_IMAGE`. Стартует, когда первая
    нода здорова. Путь `extends.file` compose v5 считает от `demo/load`, как и остальные относительные пути
    оверлеев.
- **nginx** (`perf/nginx/`):
  - один воркер, журнал доступа выключен;
  - keep-alive к клиентам и к нодам;
  - `$aggregate_key` из пути (`concerts:{id}`, `fans:{id}`);
  - заголовок ответа `X-Upstream` с нодой, которая ответила;
  - POST на другую ноду не повторяется;
  - три upstream: `single`, `round_robin`, `key` (`hash $aggregate_key consistent`).
- **`perf/run.sh`.**
  - `NODES=1|2`, `BALANCE=none|round_robin|key`; недопустимые сочетания отвергаются.
  - С балансировщиком стенд работает под квотой CPU (`PIN=quota`, `PIN=cpuset` — ошибка).
  - Две ноды делят бюджет CPU бэкенда профиля и воркеры outbox: `WORKERS` — итог стенда, чётный.
  - Делёж воркеров добавлен после первой серии. Без него каждая нода выбирала задачи своими двумя
    воркерами, и в окно нагрузки попадало вдвое больше работы очереди: на 02b +27 % CPU PostgreSQL на
    команду, захватов задач 0.079 → 0.201 на команду. Эту серию я выбросил.
- **Учёт.**
  - `hooks.sh` снимает CPU каждого сервиса из `LOAD_SERVICES_EXTRA`.
  - `collect.mjs`: `backend` — сумма нод (одна нода и две сравниваются как есть), отдельно `backend_node1`,
    `backend_node2`, `balancer`. В `meta` — `nodes`, `balance`, `outbox_workers_total`, бюджеты второй ноды и
    nginx.
  - `compare.mjs`: строки для nginx и нод.
  - Документация: `perf/README.md`, `demo/load/README.md`.

## Как проверено

- `docker compose config` для всех вариантов:
  - окружение `backend-2` совпадает с `backend`;
  - `BACKEND_IMAGE` доходит до обеих нод;
  - бюджет CPU делится.
- `nginx -t` для всех трёх upstream.
- Распределение на живом стенде по `X-Upstream`, 6 концертов по 4 запроса:
  - `round_robin` — ноды чередуются на каждом концерте;
  - `key` — каждый концерт всегда на одной ноде, концерты разошлись 3/3.
- Короткие прогоны через `perf/run.sh` (`NODES=2 round_robin`, `NODES=1 round_robin`): логи `backend-2.log` и
  `balancer.log`, счётчики CPU обеих нод и nginx, `meta`. Недопустимые сочетания, нечётный `WORKERS` и
  `PIN=cpuset` отвергнуты.
- Новый `collect.mjs` на старом прогоне одной ноды даёт те же цифры (плюс `meta.nodes = 1`,
  `meta.balance = none`).

## Результат

Замер 2026-10-21, HEAD (код `a747f06`). Профиль `app`: бэкенду 2 ядра на все ноды, nginx 1 ядро, квота CPU. k6,
пул 20 на ноду, воркеров outbox 2 на стенд. 3 прохода вперемешку, медиана, в скобках min–max. На горячем ключе —
принятые команды/с (70 % ответов там 409), на 02b все ответы — принятые.

| Вариант | 01 hot key, принятых/с | p99, мс | 02b, команд/с | p99, мс |
|---|---|---|---|---|
| одна нода напрямую (`NODES=1`) | 636 (622–653) | 32.2 | 3320 (3208–3333) | 28.8 |
| одна нода за nginx (`NODES=1 BALANCE=round_robin`) | 540 (425–644) | 45.1 | 3202 (2611–3278) | 28.4 |
| две ноды по очереди (`NODES=2 BALANCE=round_robin`) | 678 (659–683) | 32.1 | 4092 (4071–4412) | 24.4 |
| две ноды по ключу (`NODES=2 BALANCE=key`) | 504 (489–511) | 41.5 | 3916 (3891–4303) | 26.4 |

CPU на 1000 принятых команд, мс:
- **nginx:** 137–150 на горячем ключе (≈ 40 мкс на запрос, на принятую команду приходится ~3.4 запроса), 37–40
  на 02b (≈ 37 мкс на запрос).
- **Две ноды по очереди** нагружены поровну: 1196 / 1197 на горячем ключе, 226 / 226 на 02b.
- **По ключу** горячий концерт целиком на одной ноде: 1819 против 462 (вторая нода только выбирает задачи
  outbox). На какую ноду он попадёт, решает хеш id концерта прогона.

Выводы:
1. **Инструмент работает:** распределение проверено напрямую, учёт по нодам сходится.
2. **nginx дешёв** (~40 мкс CPU на запрос), значимой потери пропускной способности не видно: диапазоны с
   прямым подключением перекрываются. Но на горячем ключе медиана ниже (один прогон из трёх — 425). Поэтому
   эффект нескольких нод меряем против **одной ноды за nginx**, чтобы балансировщик был с обеих сторон.
3. **Разбросанные ключи (02b).** Две ноды по одному ядру дают +28 % команд/с против одной ноды за nginx при том
   же CPU (≠). CPU бэкенда на команду −16 % (≠), p99 −14 % (≠).
   - Вероятная причина — рантайм на двух ядрах под квотой тратит больше на планирование, чем два процесса по
     одному ядру; не проверялось.
   - CPU PostgreSQL на команду +12 % (≠): у двух нод вдвое больше соединений (пул 20 на ноду).
4. **Горячий ключ.**
   - Две ноды по очереди держат столько же, сколько одна, доля 409 почти та же (68–71 %): гонки идут внутри
     каждой ноды, на неё приходится по 20 VU.
   - По ключу горячий концерт целиком на одной ноде с одним ядром: −10 % против одной ноды за nginx, 409 те же
     ~70 %. Привязка к ноде сама по себе ничего не даёт, проигранные гонки остаются внутри процесса.
   - Это и убирает 08a: с блокировкой агрегата при `BALANCE=key` у агрегата будет единственный писатель, при
     `round_robin` — два участника гонки вместо сорока.

Эти цифры — точка «до» для замеров 08a и 08b при двух нодах.
