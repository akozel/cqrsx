## Зачем

Очереди из 08 работают внутри процесса. Между нодами по-прежнему действуют проверка версии в базе и CAS проекции.
Без второй ноды на стенде нельзя проверить два утверждения из плана:
- при N нодах в гонке за горячий ключ остаются N участников, а не число запросов;
- привязка агрегата к ноде (все команды концерта на одной ноде) превращает очередь внутри процесса в
  единственного писателя агрегата.

## Что делаем

Оверлей `perf/compose.nodes.yaml` подключается через `LOAD_COMPOSE_EXTRA`, как остальные оверлеи эпика:

```text
k6 / wrk ──► nginx (balancer:8080) ──┬──► backend   (нода 1)
                                     └──► backend-2 (нода 2)
                    PostgreSQL, MongoDB, mail — общие
```

- **`backend-2`** — тот же образ и окружение, что у `backend`, включая `BACKEND_IMAGE=` для «до». Запускается
  после того, как `backend` готов: схема и стартовые данные создаются один раз, без гонки двух стартов.
- **`balancer`** — nginx, точная версия образа выбирается при реализации:
  - `upstream` с обеими нодами и `keepalive`; `proxy_http_version 1.1`, пустой `Connection`;
  - журнал доступа выключен (он стоит CPU), кроме проверочного режима;
  - SSE через стенд не идёт; если понадобится — `proxy_buffering off` для его пути.
- **Распределение — параметр `BALANCE=`:**
  - `round_robin` — равномерно, по умолчанию;
  - `key` — `hash $aggregate_key consistent`. Ключ вынимается из пути через `map`: `/api/concerts/{id}/…` и
    `/api/fans/{id}/…` → `concerts:{id}`, `fans:{id}`. Все команды одного агрегата приходят на одну ноду.
- **Генератор** (k6 или wrk) получает `BASE_URL=http://balancer:8080` вместо `http://backend:8080`.
- **Параметры `perf/run.sh`:**
  - `NODES=1|2` (по умолчанию 1, как сейчас);
  - `BALANCE=none|round_robin|key`. `none` — без nginx, допустимо только при `NODES=1`. `NODES=1 BALANCE=round_robin`
    — одна нода за nginx, база для накладных расходов балансировщика.
- **Бюджет CPU.** Суммарный бюджет бэкендов профиля (`PROFILE=app`: 2 ядра) делится между нодами поровну,
  чтобы сравнение «одна нода против двух» шло при одинаковом CPU. nginx получает своё ядро и считается отдельно.
- **Учёт.**
  - `hooks.sh` снимает CPU `backend-2` и `balancer`;
  - `collect.mjs` пишет в `result.json` CPU по нодам и сумму бэкендов, а в `efficiency` — CPU на 1000 команд
    для суммы и для nginx;
  - `compare.mjs` показывает новые строки;
  - параметры прогона (`nodes`, `balance`) записываются в `result.json`.
- **Готовность.** `run.sh` ждёт обе ноды. Если для этого нужна точка расширения в `demo/load/run.sh`
  (сейчас он ждёт одну), она добавляется так же, как `LOAD_HOOKS` и `LOAD_COMPOSE_EXTRA`, — без изменения
  поведения по умолчанию.

## Пограничные случаи

| # | Случай | Ожидаемое поведение |
|---|---|---|
| 1 | Две ноды стартуют одновременно | вторая ждёт готовности первой: схема, индексы MongoDB и стартовые данные создаются один раз |
| 2 | Воркеры outbox | работают на обеих нодах, слив вдвое мощнее. В отчёте указывается число воркеров на ноду; при сравнении слива — `LOAD_OUTBOX_WORKERS` на ноду вдвое меньше |
| 3 | `BALANCE=key` на горячем ключе | весь горячий концерт на одной ноде, вторая почти простаивает. Это и есть «единственный писатель»; суммарный CPU это покажет |
| 4 | Нода недоступна | nginx уводит запросы на живую ноду; для замеров это сбой прогона, а не результат: прогон проверяет, что обе ноды получили запросы |
| 5 | Старый образ (`BACKEND_IMAGE=` для «до») | обе ноды запускают его |
| 6 | `NODES=1 BALANCE=none` | стенд как сейчас, результаты сравнимы со всеми прежними |

## Проверка

- `bash -n` для скриптов, `node --check` для инструментов, `docker compose config` с оверлеем;
- проверочный прогон `01-hot-key` при `NODES=2` и обоих `BALANCE`. Журнал nginx с `$upstream_addr` в
  проверочном режиме показывает:
  - при `round_robin` запросы делятся между нодами примерно поровну;
  - при `key` запросы одного концерта идут на одну ноду;
- у обеих нод CPU больше нуля; verify после прогона `ok`;
- `NODES=1 BALANCE=none` даёт те же цифры, что до задачи (в пределах шума).

## Замер

Не задача движка, а инструмент. Базовые цифры для HEAD (до 08a), профиль `app`, k6, 3 прохода:
- `01-hot-key-vus40`: `NODES=1` напрямую, `NODES=1` за nginx, `NODES=2` `round_robin`, `NODES=2` `key`;
- контроль — `02b-spread-vus50` (разбросанные ключи, где две ноды должны масштабироваться).

Цифры записываются в тикет и служат точкой «до» для замеров 08a и 08b при двух нодах.
