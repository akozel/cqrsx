## Сейчас

```rust
// cqrsx: cqrs/store/persisted.rs:420
let snapshot = self.repo.get_snapshot::<A>(aggregate_id).await?;            // round trip 1
// ... restore context from the snapshot ...
SnapshotPolicy::Every(_) => self.load_events_after(aggregate_id, &context).await?,  // round trip 2
```

Второй запрос зависит от ответа первого (номер снапшота), поэтому выполнить их одновременно нельзя. Каждая команда
делает два последовательных обращения на чтение.

## Станет

Новый метод трейта с реализацией по умолчанию. Старые реализации (тестовые репозитории, будущие бэкенды)
продолжают работать без правок:

```rust
// cqrsx: cqrs/store/repository.rs
/// The current snapshot and the events after its watermark (every event when there is none).
fn get_snapshot_with_events<A: Aggregate>(
    &self,
    aggregate_id: &str,
) -> impl Future<Output = Result<(Option<SerializedSnapshot>, Vec<SerializedEvent>), PersistenceError>> + Send {
    async move {
        let snapshot = self.get_snapshot::<A>(aggregate_id).await?;
        let after = snapshot.as_ref().map_or(0, |s| s.last_sequence);
        Ok((snapshot, self.get_events_after::<A>(aggregate_id, after).await?))
    }
}
```

PostgreSQL переопределяет метод одним запросом, и связывает снапшот с событиями сам Postgres:

```sql
WITH snapshot AS (
    SELECT last_sequence, current_snapshot, payload
      FROM snapshots WHERE aggregate_type = $1 AND aggregate_id = $2
)
SELECT 'snapshot' AS kind, last_sequence AS sequence, current_snapshot,
       NULL AS event_type, NULL AS event_version, payload, NULL::json AS metadata
  FROM snapshot
UNION ALL
SELECT 'event', sequence, NULL, event_type, event_version, payload, metadata
  FROM events
 WHERE aggregate_type = $1 AND aggregate_id = $2
   AND sequence > COALESCE((SELECT last_sequence FROM snapshot), 0)
ORDER BY kind DESC, sequence          -- the snapshot row first
```

`PersistedEventStore::load_aggregate` с включённым снапшотом вызывает новый метод. Репозиторий с outbox
делегирует его читателю, как остальные чтения.

**Запасной путь.** Сейчас при ошибке десериализации снапшота (структура агрегата изменилась) контекст начинается с
нуля и читаются **все** события. Новый запрос вернёт только события после снапшота, поэтому в этом редком случае
нужен второй вызов `get_events_after(0)`. Поведение сохраняется, и его стережёт существующий тест
`load_aggregate_after_deserialize_error`.

## Зачем, на примере

Бронь: два чтения + запись = 3 обращения (без пингов, после задачи 02). После правки — 2. Для 02a, где предел —
Postgres, это на треть меньше сообщений на команду (М1). Для горячего ключа окно между чтением и записью короче на
одно обращение (М3).

## Риски

- **Корректность.** События неизменяемы, а снапшот и события читаются из одного снимка MVCC. Новый способ не менее
  корректен, чем два запроса.
- **Типы колонок.** `UNION ALL` требует согласованных типов, поэтому `NULL` нужно явно привести. Декодер строк
  получает поле `kind`. Тесты декодирования — на обе ветви.

## Как измерить

Матрица 01 / 02a / 02b против `perf-base-` (лучше уже после 02 и 03, иначе эффект теряется на фоне пингов).
Ожидание:
- в `pg_statements.tsv` вместо двух запросов на загрузку — один;
- `statements_per_command` у 02a и 02b меньше на 1.

## Как сделано (и откатано)

- **Движок.** Метод трейта `get_snapshot_with_events` с реализацией по умолчанию (`get_snapshot`, затем
  `get_events_after`). `load_aggregate` со снапшотами делал один вызов. При несовместимом снапшоте —
  пустой контекст с сохранённой версией и второй вызов `get_events_after(0)`.
- **PostgreSQL.** Один статический запрос: CTE `MATERIALIZED` с самым новым снапшотом
  (`ORDER BY last_sequence DESC LIMIT 1`, ключ таблицы допускает несколько строк), `UNION ALL` событий после его
  номера, `ORDER BY part, sequence`. Каждую часть разбирал свой декодер строк. Репозиторий с outbox делегировал
  метод читателю. После пяти исполнений PostgreSQL переходит на обобщённый план:
  - снапшот: `Index Scan Backward … LIMIT 1`;
  - события: `events_pkey` с `sequence > InitPlan`.

  Перепланирования на каждый вызов нет.
- **Тесты.**
  - Юнит: порядок вызовов репозитория, запасной путь и ошибка его второго чтения, `Disabled` без снапшота.
  - Интеграция: результат равен двум чтениям на историях из 0–25 событий с интервалами 1, 3, 10 и без
    снапшотов; outbox отдаёт то же, что читатель; из двух строк снапшота берётся самая новая; чужой тип
    агрегата не попадает в результат; на соединении подготовлен ровно один запрос; запасной путь.
  - Полный набор проверок, покрытие 97.57 %, e2e smoke на отдельном стенде.

Выводы:
- **Объединённый запрос дороже двух простых.** В 02b его среднее исполнение — 67.6 мкс, у двух старых
  вместе — 62.4 мкс (32.8 + 29.6): CTE, `Append`, сортировка и InitPlan. Экономия на одном цикле протокола
  этого не покрывает. Где предел — PostgreSQL, запросов меньше, а пропускная способность ниже. Выигрывает
  только новый агрегат (02a, пустой ответ).
- **На горячем ключе гонку решает свежесть состояния, а не число обращений.**
  - Снимок MVCC, с которым команда идёт на запись, берёт последнее чтение. В двух запросах это чтение хвоста,
    а снапшот к этому моменту уже передан и разобран.
  - В одном запросе передача снапшота, разбор его JSON и более тяжёлое исполнение попадают в окно между
    снимком и записью. Коммит здесь идёт каждые ~2 мс, поэтому хватает ~0.2 мс, чтобы заметно сдвинуть долю
    выигранных записей.
  - v3 возвращает эту долю к базе, но проигрывает на лишней работе PostgreSQL. v2 чуть ниже базы по той же
    причине: разбор снапшота в нём переехал в окно.
- **Гипотеза тикета «окно гонки короче на одно обращение» неверна.** Окно начинается с последнего чтения, а не
  с первого.

**Решение 2026-10-21: отклонить.** Код откатан. Нынешний порядок «снапшот и его разбор, затем хвост» лучше
не случайно, его стоит сохранить. Чтение без снапшота даст задача 07 (2026-10-26 заменена задачей
[04/15](../04_operation_costs/15_state_through_lock_line.md): следующая команда в очереди блокировки берёт состояние
у предыдущей).
