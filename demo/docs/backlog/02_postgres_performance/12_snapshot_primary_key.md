# 12. Первичный ключ снапшотов без изменяемого поля

| | |
|---|---|
| Статус | предложено |
| Ценность | низкая: снапшот пишется раз в 10–25 команд |
| Цена | низкая по коду, но это изменение схемы — нужна миграция |
| cqrsx | `sql/001-event-store.sql`, `sql/migrations/` (новый каталог), `postgres/event_repository/sql_query.rs`, `postgres/outbox/write.rs`, `doc/components.md` |
| demo | dev-база: применить миграцию или пересоздать том |
| Зависимости | 10 для замера; хорошо делать вместе с любым другим изменением схемы |
| Где выигрыш | долгая работа: размер и мусор индекса `snapshots_pkey`, объём WAL |

## Сейчас

```sql
-- cqrsx: sql/001-event-store.sql
PRIMARY KEY (aggregate_type, aggregate_id, last_sequence)
```

У агрегата одна строка снапшота, но обновление меняет `last_sequence` (`sql_query.rs`, `update_snapshot`;
`outbox/write.rs`, `append_snapshot`).

PostgreSQL умеет обновлять строку «на месте» без записи в индексы (HOT update), только если не меняется ни одна
индексируемая колонка. Здесь меняется колонка ключа, поэтому каждое обновление снапшота:
- пишет новую запись в `snapshots_pkey`;
- оставляет старую мусором до autovacuum;
- даёт лишний объём WAL.

## Станет

```sql
PRIMARY KEY (aggregate_type, aggregate_id)
-- optional: WITH (fillfactor = 80), so the page has room for a HOT update
```

- `insert_snapshot`: `ON CONFLICT (aggregate_type, aggregate_id) DO NOTHING`.
- Имя ограничения остаётся `snapshots_pkey`, поэтому `map_sqlx_error` распознаёт конфликт как раньше.
- Миграция для существующих баз `sql/migrations/003-snapshots-primary-key.sql`:
  1. проверить, что дублей по `(aggregate_type, aggregate_id)` нет (иначе остановиться с понятной ошибкой);
  2. `DROP CONSTRAINT snapshots_pkey`;
  3. `ADD PRIMARY KEY (aggregate_type, aggregate_id)`.

У `cqrsx` пока нет механизма миграций: схема — `CREATE TABLE IF NOT EXISTS`, который не меняет существующие таблицы.
Каталог `sql/migrations/` с нумерованными файлами и строкой в `components.md` («SQL assets») — минимальный порядок.
Полноценный механизм — отдельный вопрос.

## Зачем, на примере

Горячий концерт за час soak-прогона получает десятки тысяч обновлений снапшота. Сейчас каждое — новая запись в индекс
и мусор. После правки, если строка помещается на страницу, обновление идёт «на месте», и индекс не меняется. Большой
`payload` (> ~2 КБ) уходит в TOAST, основная строка остаётся маленькой, и HOT для неё возможен.

## Риски

- Изменение схемы библиотеки: dev-база demo и любые развёрнутые базы требуют миграции. Описать в теле коммита.
- Выигрыш небольшой. Если soak его не покажет, задачу можно закрыть без слияния.

## Как измерить

- Интеграционный тест: после нескольких обновлений снапшота `pg_stat_user_tables.n_tup_hot_upd` для `snapshots`
  больше 0 (сейчас всегда 0).
- Soak (задача 10): размер `snapshots_pkey` и `wal_bytes` во времени, до и после.

## Критерии приёмки

- [ ] Схема с новым ключом. `ON CONFLICT` в `insert_snapshot` обновлён. Конфликт первой вставки снапшота
      по-прежнему `OptimisticLockError`.
- [ ] Миграция с проверкой дублей, тест на базе со старой схемой: миграция проходит, данные на месте.
- [ ] Тест HOT-обновлений (`n_tup_hot_upd > 0`).
- [ ] `components.md`: «SQL assets» упоминает миграции.
- [ ] Замер на soak записан в тикет.
