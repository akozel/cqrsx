# Эпик 03. Надёжные проекции

[← все эпики](../README.md)

Источник: обсуждение 2026-10-24 «EventSourcing → Projection: как у Axon и что делать в cqrsx». Сейчас проекции
обновляются обработчиками исполнителя команд после коммита, в памяти процесса и без гарантии доставки: падение
процесса или сбой MongoDB между коммитом и записью витрины теряет обновление до следующего Encore!, а Encore!
(`EventReplay`) — второй, отдельный механизм. Эпик заменяет оба одним: проекция сама читает журнал от своей
закладки, а пересборка — задание «свернуть историю ключа и заменить документ», то же, что чинит документ после
сбоя. Закладка устроена как у Axon (tracking token), Marten (event progression), EventStoreDB (persistent
subscriptions) и Akka Projections (offset store); пересборка по ключу — следствие правила непрерывности и того,
что документ `ViewProjection` строится из одного потока (D-19).

## Принцип

Журнал уже переживает падения; для проекций не хватает порядка чтения и закладки.

1. **Позиция.** Каждое событие запоминает номер транзакции, которая его записала (`events.tx xid8`, умолчание
   `pg_current_xact_id()`). Читатель берёт события с номером больше закладки и меньше горизонта снимка
   (`pg_snapshot_xmin(pg_current_snapshot())`): всё ниже горизонта завершено, поэтому дыр нет — читатель не
   пропускает, а ждёт. Внутри агрегата порядок по `tx` совпадает с порядком по `sequence`.
2. **Закладка.** Строка `projection_checkpoints` на пару «проекция + тип агрегата»: позиция, аренда владельца,
   курсор пересборки. Пишет её только владелец аренды, короткими запросами; во время записи в MongoDB никакие
   блокировки базы не держатся.
3. **Процессор.** Цикл «продлить аренду → прочитать страницу → разложить по ключам в `OrderedDelivery` →
   дождаться квитанций → сдвинуть закладку до события перед первым сбоем; при сбое пауза с ростом».
   Пересборка — задание на ключ «прочитать историю агрегата, свернуть, заменить документ» через того же
   рабочего ключа: одного ключа по запросу, всех ключей журнала для Encore! (курсор в строке закладки) и
   автоматически для документа, который отверг событие как дыру. Закладку пересборка не трогает, wipe не нужен.
4. **Непрерывность документа.** Документ витрины хранит `last_sequence` и принимает только событие
   `last_sequence + 1`: более старые пропускаются, дыра — ошибка. Поэтому доставка «хотя бы раз», перехват аренды,
   повторное чтение после падения и пересборка рядом с живой доставкой не портят витрину.

## Два вида витрин

Находка обсуждения 2026-10-24 (D-19): витрина строится одним из двух способов, и у каждого свои правила
непрерывности и пересборки. Эпик реализует кодом первый; для второго записаны правила, и схема их не исключает.

| | Документ из одного потока | Документ из нескольких потоков |
|---|---|---|
| Что это | `ViewProjection`: `view_id == aggregate_id`, документ — свёртка событий одного агрегата. Все витрины демо; кошелёк склеивается из ledger-ов на чтении | один документ питают события нескольких агрегатов, возможно разных типов: «страница концерта» из `Concert` и `Fan` |
| Непрерывность | одно `last_sequence` ([01](01_contiguous_views.md)) | `last_sequence` на каждый поток, карта «поток → номер»; правило по каждому потоку отдельно |
| Порядок | внутри потока гарантирует библиотека | внутри потока — библиотека; между потоками — никто: процессоры типов независимы, и свёртка обязана давать один результат при любом перемешивании потоков |
| Ключ документа | тождество | функция от события |
| Закладки | одна на проекцию и тип | по одной на каждый питающий тип, все кормят один обработчик |
| Полная пересборка | все ключи журнала заданиями на ключ, без wipe, касса открыта ([03](03_projection_processor.md)) | wipe один раз на поколение, затем истории всех ключей всех питающих типов теми же заданиями, параллельно; очередь типов не нужна |
| Частичная пересборка | один ключ | невозможна без обратного индекса «документ → потоки»: журнал не знает, какие потоки питают документ |
| Самолечение дыры | пересборка ключа из истории | по потоку, для существующего документа; отсутствующий документ лечится только полной пересборкой |
| В эпике | код: [01](01_contiguous_views.md)–[04](04_demo_on_processor.md) | только правила; форма `last_sequence` и схема закладок их не исключают, совместимость не нужна |

Почему без очереди типов: порядок «сначала тип A, потом тип B» нельзя обеспечить вживую, значит свёртка и так
обязана его не требовать. Последовательная пересборка лишь скрывала бы эту ошибку, держала бы тип B в ожидании
всего прогона типа A и останавливалась бы на первом битом событии типа A.

## Что гарантируем

| # | Гарантия | Чем обеспечена | Где проверяется |
|---|---|---|---|
| G1 | Событие, попавшее в журнал, будет применено к каждой проекции своего типа — при падении процесса, ноды, MongoDB или PostgreSQL | закладка остаётся ниже события, пока оно не применено; горизонт снимка исключает пропуски | [03](03_projection_processor.md) «Модель сбоев» |
| G2 | Внутри агрегата события применяются по порядку, без пропусков и повторов | порядок `tx` = порядок `sequence`; непрерывность документа | [01](01_contiguous_views.md), [02](02_event_position.md) |
| G3 | Документ витрины всегда равен свёртке непрерывного префикса событий своего агрегата — при любом числе нод и перехватах аренды | `last_sequence` + CAS по версии; fencing закладки по `lock_token` | [01](01_contiguous_views.md), [03](03_projection_processor.md) F5, F19 |
| G4 | Сбой не пропускает событие молча: проекция останавливается на нём, и это видно | закладка не двигается за сбой; `failures`, `last_error`, отставание в статусе | [03](03_projection_processor.md) F6–F8, [04](04_demo_on_processor.md) |
| G5 | Пересборка не останавливает запись, не требует wipe и идёт тем же рабочим ключа: целиком, одним ключом, самолечением | задание на ключ через `OrderedDelivery`, курсор в строке закладки; у документа один писатель | [03](03_projection_processor.md) F14–F17, F22–F23, [04](04_demo_on_processor.md) |
| G6 | Путь записи не дорожает | колонка с умолчанием и одна запись в индекс; ни одной лишней строки на команду | замер в [03](03_projection_processor.md) (горячий ключ до/после `tx`) и [04](04_demo_on_processor.md) |

## Общие правила

- Одна задача — один коммит: `feat(cqrsx): <что>; adopt in demo` (с `!`, если API ломается) или
  `feat(demo): <что>`. Агент не коммитит по своей инициативе: оставляет готовое рабочее дерево и предлагает
  сообщение коммита и список файлов.
- Покрытие `cqrsx` не ниже 97 %, матрица фич из корневого `CLAUDE.md`; ядро процессора компилируется без
  `postgres`.
- Обратная совместимость не нужна: проект не выпущен. API, схему базы и скрипты меняем так, как чище, без
  алиасов, умолчаний «для старых данных», ассетов обновления и переходных слоёв; существующие базы
  пересоздаются (`make reset`), витрины — Encore! (решение пользователя 2026-10-24).
- Каждое настраиваемое значение — константа умолчания в cqrsx и переменная `ENCORE_*` в демо. Режимов и
  переключателей не добавляем.
- В логах нет идентификаторов агрегатов и содержимого событий (как в `diagnostics`).
- Нагрузочный замер — против серии `perf-08b-` эпика 02 на стенде `demo/load`, `VERIFY=1` в каждом прогоне.
  Запущенный dev-стек пользователя не трогаем.

## Вне рамок

- Сегменты по хешу идентификатора агрегата (одна проекция на нескольких нодах параллельно): добавляются колонкой
  `segment` в ключ таблицы закладок, когда одной ноды не хватит.
- Dead-letter на ключ (как у Axon): больной агрегат паркуется, остальные идут дальше. Пока сбой хранилища
  останавливает проекцию и виден; дыра — исключение, её лечит пересборка ключа.
- Многопоточные витрины (документ из нескольких агрегатов): правила в разделе «Два вида витрин», механизм —
  когда появится первая такая витрина.
- Общий читатель журнала на тип агрегата для нескольких проекций: пока процессор на проекцию.
- Пересборка в соседнюю коллекцию с переключением в конце (blue/green).
