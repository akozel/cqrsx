## Сейчас

Settle сначала выбирает и блокирует строку задачи, потом проверяет срок аренды и обновляет её. Выборка — в
`settlement.rs:76`:

```sql
WITH owned AS MATERIALIZED (
    SELECT id, locked_until FROM transactional_outbox
    WHERE id = $1 AND lock_token = $2 AND status = 'processing'
    FOR UPDATE
)
UPDATE transactional_outbox AS o SET … FROM owned
WHERE o.id = owned.id AND owned.locked_until > clock_timestamp()
RETURNING o.status
```

Условие `status = 'processing'` совпадает с предикатом частичного индекса
`transactional_outbox_expired_idx (locked_until, id) WHERE status = 'processing'` (`sql/002-transactional-outbox.sql:33`).
По статистике в нём мало строк, а `id = $1` годится как условие на его второй столбец. Поэтому PostgreSQL 18 ищет
строку по нему, а не по первичному ключу:

```text
->  Index Scan using transactional_outbox_expired_idx on transactional_outbox
      Index Cond: (id = $1)
      Filter: ((lock_token = $2) AND (status = 'processing'::text))
```

Пока идёт слив, в этом индексе лежат записи всех задач, закрытых с прошлого VACUUM, и каждый settle читает их все.

| Где | settle, мс | блоков на вызов | доля времени SQL |
|---|---|---|---|
| стенд, слив `03a`, 8 воркеров | 0.402 | 92 | 73 % |
| стенд, горячий ключ, 40 VU | 0.202 | 42 | 35 % |
| эксперимент, 80 тыс. settle | 0.273 | 122 | — |

## Станет

```sql
WHERE id = $1 AND lock_token = $2
```

Условие на `status` уходит: CHECK таблицы (`sql/002…:23`) требует, чтобы `lock_token` был не `NULL` ровно у строк в
`processing`. Значит, `lock_token = $2` уже означает `processing`, и смысл запроса не меняется. Комментарий в коде
объясняет, почему условия нет: без него его вернут, и план снова уйдёт на частичный индекс.

В эксперименте после правки settle идёт по `transactional_outbox_pkey`: 0.071 мс и 17.5 блока на вызов (−74 %).

## Зачем, на примере

Всплеск броней оставил 40 тыс. задач `encore_record_ticket`. 8 воркеров закрывают их по 2 000 в секунду. Через 10 с в
индексе просроченных аренд 20 тысяч записей закрытых задач, и каждый следующий settle идёт по ним всем, чтобы найти
одну строку по id. После правки settle читает только ветку первичного ключа до этой строки.

## Вариант на потом

Одиночный `UPDATE` без CTE и без `FOR UPDATE`, с условиями `id`, `lock_token` и `locked_until > clock_timestamp()` в
`WHERE`: в эксперименте 0.061 мс против 0.071, ещё −14 %. Комментарий в `settlement.rs` защищает порядок «сначала
блокировка, потом проверка времени» от держателя блокировки, который отпустил строку неизменённой. В этой схеме
строку в `processing` без изменения не блокирует никто: восстановление аренды меняет каждую строку, которую
блокирует. Если пользователь захочет, этот вариант мерится отдельной строкой в той же задаче.

Замерен в этой задаче и отклонён — см. «Результат».

## Риски

- Кто-то снимет CHECK со схемы, и тогда `lock_token = $2` перестанет означать `processing`. Схема принадлежит cqrsx,
  тест схемы (`tests/postgres/schema.rs`) её проверяет.
- План зависит от версии PostgreSQL. Образ закреплён (18.6) и на стенде, и в тестах.

## Как измерить

«До» — HEAD перед задачей, «после» — правка. Прогоны вперемешку, `REPEAT=3`, `POOL=20`:

## Результат

**Что сделано:**
- `settlement.rs`: в CTE `owned` нет `status = 'processing'`; комментарий объясняет почему.
- **Тест** `settlement_finds_its_row_by_the_primary_key_while_closed_tasks_fill_the_expired_lease_index`:
  - пул на одно соединение, 2 000 задач закрыты без VACUUM, после `ANALYZE`;
  - текст settle берётся из `pg_prepared_statements` — тот, что очередь действительно отправляет;
  - `EXPLAIN (FORMAT JSON) EXECUTE` проверяется при `force_custom_plan` и `force_generic_plan`.

  На старом SQL тест падает: план читает `transactional_outbox_expired_idx`.
- `components.md`: строка «PostgreSQL queue».

**Вариант с одиночным `UPDATE`** (образ `e04-03u`, только для замера): `UPDATE … WHERE id = $1 AND lock_token = $2
AND locked_until > clock_timestamp() RETURNING status`, без CTE и `FOR UPDATE`. Он ломает два теста:
- `a_lease_expiring_while_settlement_waits_on_an_unchanged_row_cannot_be_completed` — ровно то, от чего защищает
  нынешний порядок. Тест держит строку через `FOR UPDATE` неизменной, пока аренда истекает. Вариант закрывает
  задачу после истечения аренды: условие на время проверено до ожидания и после него не перепроверяется.
- новый тест плана — он ищет текст `WITH owned`.

В дерево вариант не попадал; образ и правка варианта удалены после решения.

**Что видно:**
- **Settle стал дешевле в 4 раза.** При сливе 0.44 → 0.11 мс и 94 → 17 блоков на вызов, как в эксперименте
  аудита (0.07 мс, 17.5 блока). Слив 8 воркерами быстрее на 38 %, бронь через всю цепочку стоит PostgreSQL на
  20 % меньше. Операторов и WAL на команду столько же: меняется только цена одного оператора.
- **Горячему ключу это не помогает.** Принятых/с −1 %: предел там — ожидание WAL. Освободившийся PostgreSQL
  уходит на цепочку: её доля в окне 0.72 → 0.75, а по задаче 01 цепочка в окне отнимает пропускную способность
  у горячего ключа.
- **Вариант 03u.** Settle ещё на 10 % быстрее и на 28 % меньше блоков, CPU PostgreSQL по цепочке −2 % к 03. Но
  слив медленнее, 2 436 задач/с против 2 688 у 03: диапазоны трёх повторов не пересекаются. Причина не
  выяснена. Выигрыша, ради которого стоит менять порядок «блокировка, потом проверка времени», замер не
  показывает.

**Решение по варианту (пользователь, 2026-10-26): отклонён, принят только основной вариант.**
- Экономия на settle (−10 % времени, −28 % блоков) — это 3–4 % времени SQL при сливе, меньше шума стенда. Ни в сливе,
  ни на горячем ключе, ни на 5-минутной точке выигрыша нет. Разница сливов 03 и 03u (2 688 и 2 436 задач/с)
  укладывается в разброс самого 03 между сессиями: в итоговой серии 03 дал 2 469–2 748.
- Вариант снимает проверенную тестом защиту — порядок «блокировка, потом проверка времени». Он держался бы на
  неявном правиле «строку в `processing` никто не блокирует, не меняя её». Сейчас его соблюдает весь код cqrsx, но
  его легко нарушить молча: новым компонентом очереди, ручным `SELECT … FOR UPDATE` оператора, чужим кодом в той же
  базе. Последствие — задача закрывается после истечения аренды. Повторного выполнения нет, но это нарушение
  контракта.
- Если очередь снова станет пределом, рычаги крупнее — задачи [07](07_delete_completed_tasks.md) (отложена) и
  [19](19_claim_in_batches.md); [08](08_settle_with_next_claim.md) отклонена.
