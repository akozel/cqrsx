## Сейчас

`ViewProjection::apply_events` (`projection.rs:509`) на каждую пачку событий ключа сначала читает документ
(`load_with_context`, в MongoDB `find_one`), применяет события и пишет: `insert_one` для нового документа или
`update_one` с проверкой версии. Для нового концерта чтение заведомо ничего не находит. Получается две операции
MongoDB на документ, плюс сдвиг закладки раз на страницу.

## Станет

Если пачка ключа начинается с события № 1, первая попытка не читает документ. Она берёт пустой вид и контекст с
версией 0, применяет события и пишет: версия 0 означает вставку. Все три репозитория витрин (`MongoViewRepository`,
`PostgresViewRepository`, `MemViewRepository`) уже вставляют документ при версии 0 и отвечают конфликтом на дубликат.

Дубликат значит, что документ уже есть: повторная доставка после падения или пересборка ключа рядом. Тогда вторая
попытка идёт обычным путём: чтение документа, пропуск уже применённого по правилу непрерывности (`last_sequence`).

## Зачем, на примере

Анонс концерта даёт событие `ConcertAnnounced` № 1. Процессор `concert_halls` получает страницу из сотен таких событий
по разным концертам и по каждому делает `find_one` (пусто) и `insert_one`. После правки — только `insert_one`.

## Риски

- После wipe витрин документы исчезли, а закладка начинается с начала журнала (D-15). Первое событие потока снова
  № 1, вставка проходит. Это правильный путь.
- Повторная доставка страницы, где документ уже есть: одна лишняя неудачная вставка, потом обычный путь. Это редкий
  случай: потеря аренды или падение.

## Как измерить

Хуки стенда получают счётчики операций MongoDB: `db.serverStatus().opcounters` (`insert`, `query`, `update`, `delete`,
`command`) в точках `before`, `after` и `drained`. По ним считаются операции MongoDB на команду.

Точка `02a-announce-vus100`, профиль `full`, wrk, «до» и «после» вперемешку, `REPEAT=3`: анонсов/с, CPU MongoDB на
1000 анонсов, операции MongoDB на анонс. Ожидание: 2 → 1 операция на анонс плюс закладка.

## Результат

Правка откачена (см. «Решение» в конце); ниже — что было сделано и что показал замер.

**Что было сделано:**
- **`ViewProjection::apply_events`.** Пачка, которая начинается с события № 1, сначала идёт через `insert_new`:
  - пустой вид, контекст с версией 0, правило непрерывности, `update_view`;
  - запись удалась — готово;
  - дубликат (`OptimisticLockError`) или разрыв в пачке — обычные попытки с чтением, все `max_attempts`;
  - конфликт этой попытки не ошибка: наблюдатель его не видит, в `max_attempts` он не считается. Поэтому и при
    `max_attempts = 1` повторная доставка того, что документ уже держит, проходит.
- **Тесты:**
  - модульный двойник `Repository` получил правила версий настоящих репозиториев: версия 0 — вставка и
    конфликт с любым документом, иначе — только та же версия. Его журнал вызовов показывает запись без чтения;
  - новые случаи: повторная доставка с № 1 поверх документа — с хвостом и без, при одной попытке; разрыв в
    пачке с № 1 — с документом и без; технический сбой после записи;
  - `MemViewRepository`: документ создаётся с версией 0, повторная доставка проходит через конфликт;
  - MongoDB: `a_new_document_is_one_insert_without_a_read_and_a_redelivery_reads_it` — счётчик чтений поверх
    `MongoViewRepository`.
- **Счётчики операций MongoDB** (`opcounters` через `mongo-probe`) появились ещё в задаче 01, чтобы их видела
  базовая линия; на команду — `efficiency.mongo_ops_per_command` и `efficiency.chain.mongo_ops_per_command`.
- **Документация:** `components.md`, строка «Read-model projection».

**Замер.** Итоговая серия: образы `e04-04` и `e04-05` вперемешку с остальными этапами, пул 20. Анонсы —
`REPEAT=5`, `full`, wrk, `DRAIN=1`: точка ждёт, пока проекции догонят журнал, поэтому операции считаются до
конца. Остальные точки — `REPEAT=3`. Партии `e04f-04-`, `e04f-05-`; медианы, в скобках min–max.

Кроме числа анонсов в секунду, все строки про анонсы различаются вне диапазонов повторов. В анонсах два прогона
этапа 05 из пяти попали на паузы диска хоста (10.3 и 10.6 тыс./с при p99 до 190 мс); три других — 13.4–13.8 тыс./с.
Быстрый замер сразу после правки (`REPEAT=1`, партии `e04-q05-*`) дал то же: 12 475 → 13 712 анонсов/с, 2.01 → 1.01
операции.

**Что видно:** ожидание тикета сбылось точно — одна операция MongoDB на новый документ вместо двух, MongoDB тратит на
анонс на 42 % меньше CPU. В `full` MongoDB теперь занят на 1.5 ядра из 3, PostgreSQL — на 3.2 из 4: следующий предел
анонсов — PostgreSQL. В бронях каждый новый концерт и каждая новая книжка болельщика тоже экономят чтение: −8 % операций по
цепочке. Горячему ключу правка ничего не даёт: его документ давно существует.

## Решение

**Отклонено** (пользователь, 2026-10-26). В production новый документ витрины — редкая операция: концерты
анонсируются редко, а основная нагрузка — брони по уже существующим документам. На бронях выигрыш — −8 % операций
MongoDB по цепочке, на горячем ключе его нет. При этом правка заметно усложняет `ViewProjection`: второй путь записи,
своя обработка конфликта вне `max_attempts`, и тестовые двойники должны точно повторять правила версий репозиториев.

`projection.rs`, тесты MongoDB и `MemViewRepository`, счётчик записей тестового двойника процессора и строка
`components.md` возвращены к коммиту `47733f6`. Счётчики операций MongoDB на стенде остались: они часть инструментов
задачи [01](01_chain_accounting.md).
