## Сейчас

`Floating::return_to_pool` пингует каждое соединение, которое возвращается в пул (`Sync` → `ReadyForQuery`). Пинг
безусловный, настройки для него нет: `after_release` вызывается до пинга и отменить его не может. Так в
`sqlx-core 0.8.6` и так же в вышедшем 2026-05-06 `sqlx-core 0.9.0` (`pool/connection.rs:314` в обеих версиях,
проверено по исходникам). Обновление sqlx — вариант «В» прежнего тикета — не помогает.

Возврат идёт в фоновой задаче tokio (`Drop` → `spawn`), поэтому ответ команды пинг не задерживает. Но:
- он тратит CPU PostgreSQL на сообщение;
- держит соединение вне пула до ответа;
- на бэкенде стоит одной задачи tokio на каждый оператор.

Аудит: 4.03 пакета на оператор в `02b` и 4.06 на горячем ключе — два пакета сам оператор, два пинг.

| Кто | Операторов | Пингов при возврате |
|---|---|---|
| команда | 3: снапшот, события после него, запись | 3 |
| задача outbox | claim (на пачку) и settle | 2 |
| процессор | страница ленты на пробуждение | 1 |

## Варианты

| Вариант | Что убирает | Цена и риск |
|---|---|---|
| **Б′.** Снапшот и события после него читаются на одном соединении: метод репозитория, который делает оба запроса подряд на одном `acquire` | 1 пинг из 3 на команду | низкая; соединение не держится во время `handle`. Это не задача 05: запроса два, оба простые и подготовленные |
| **Б.** Одно соединение на команду: загрузка и запись | 2 из 3 | соединение держится во время `handle`. В демо это микросекунды CPU, в общем случае — риск для пула (М2), если `handle` ходит во внешние сервисы. Пересмотр пункта «Одно соединение на всю команду» из «Решено не делать» эпика 02 |
| **Г.** sqlx с отключаемым пингом при возврате: PR в sqlx с настройкой пула, до слияния — `[patch.crates-io]` с форком | все пинги при возврате: команды, очередь, процессоры | поддержка форка до слияния PR; что делать с соединением, брошенным посреди запроса (ради этого пинг и стоит), — оставить пинг для таких случаев |

После задачи 15 горячий ключ и так делает один оператор на команду из очереди. Тогда вариант Б′ важен для холодных
ключей (`02b`), а Г — для всех.

## Как измерить

Точки задачи 02/02: `02a-announce-vus100` (wrk), `02b-spread-vus50` и `01-hot-key-vus40` (k6), профиль `db`,
`REPEAT=3`. Смотреть:
- пакетов на оператор;
- CPU PostgreSQL и бэкенда на команду;
- req/s там, где предел — база.

По аналогии с 02/02 (пинги при выдаче): −4…7 % CPU PostgreSQL на команду. Для варианта Б — ещё занятость пула:
ожидание `acquire` под нагрузкой `02b`.

## Критерии приёмки

- [ ] Решение по варианту записано в тикет: Б′ мерится первым, Г — отдельным решением пользователя.
- [ ] Выбранный вариант реализован с тестами; `components.md` (раздел о пуле) описывает, где пинг остаётся.
- [ ] Замер записан в тикет.
