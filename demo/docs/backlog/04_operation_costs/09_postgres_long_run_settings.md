## Сейчас

Стенд и dev-стек используют настройки образа `postgres:18.6-alpine` по умолчанию:

| Параметр | По умолчанию | Почему это может мешать |
|---|---|---|
| `autovacuum_naptime` | 60 с | при сливе 2 000 задач/с голова очереди между проходами VACUUM копит десятки тысяч мёртвых версий |
| autovacuum для `transactional_outbox` | общие пороги (20 % мёртвых строк) | на большой таблице очистка запускается редко и работает долго |
| `shared_buffers` | 128 МБ | рабочий набор (хвосты потоков, снапшоты, outbox) на длинном прогоне перестаёт помещаться |
| `max_wal_size` | 1 ГБ | при 7 МБ/с WAL (брони, `02b`) контрольная точка по объёму — каждые ~2.5 минуты |
| `wal_compression` | off | после контрольной точки первая запись в страницу кладёт в WAL всю страницу; с контрольными суммами (включены в PostgreSQL 18) — и простановка hint bits |

Что видно сейчас: claim при сливе читает 112 блоков ради 2.6 строки, на горячем ключе — 29 блоков ради одной. В
эксперименте аудита 124 из 132 буферов claim уходят на просмотр начала `transactional_outbox_ready_idx`. Там версии
`pending` уже забранных задач, мёртвые до VACUUM. Задача 07 их не убирает: мёртвую версию оставляет сам claim.

## Станет

- **Параметры хранения outbox в схеме cqrsx.** Очередь обязана чиститься часто, это знание библиотеки, а не
  оператора:
  ```sql
  CREATE TABLE IF NOT EXISTS transactional_outbox (…) WITH (
      autovacuum_vacuum_scale_factor = 0, autovacuum_vacuum_threshold = …,
      autovacuum_vacuum_insert_scale_factor = 0, autovacuum_vacuum_insert_threshold = …,
      autovacuum_vacuum_cost_delay = 0);
  ```
  Пороги выбираются замером.
- **Настройки сервера на стенде** за `PG_TUNED=1` (`command: postgres -c …`):
  - `autovacuum_naptime` около секунды;
  - `shared_buffers` около 25 % памяти контейнера (лимит памяти задать вместе с этим);
  - `max_wal_size=8GB`, `checkpoint_timeout=15min`;
  - `wal_compression=lz4`.
- **Рекомендации в документации cqrsx** — только подтверждённые замером: что и почему настраивать под event store и
  очередь. Переносить ли их в `demo/compose.yaml`, решить отдельно: демо — витрина, а не прод.

## Зачем, на примере

Всплеск оставил 40 тыс. задач. Пока VACUUM не прошёл, каждый claim начинает с первой записи индекса готовых задач и
перебирает тысячи версий уже забранных задач, чтобы найти восемь живых. Чем дольше нет VACUUM, тем дороже каждый
claim. Частый VACUUM маленькими порциями держит голову очереди короткой.

## Чего не трогаем

`synchronous_commit` остаётся `on` («Решено не делать» эпика 02). `fsync` и `full_page_writes` тоже не трогаем: это
надёжность, а не производительность.

## Как измерить

5-минутный прогон (02) с `PG_TUNED=0` и `PG_TUNED=1`, отдельно с параметрами хранения outbox и без них:
- блоков и времени на claim во времени (срезы `pg_stat_statements` или выборка по срезам);
- `n_dead_tup` и `autovacuum_count` outbox;
- контрольные точки, `wal_bytes`, `wal_fpi`;
- p99 во времени, CPU PostgreSQL на 1000 команд.

Короткая матрица — убедиться, что на потолках нет регрессии.

## Критерии приёмки

- [ ] Параметры хранения outbox в схеме cqrsx; тест схемы видит их в `pg_class.reloptions`.
- [ ] `PG_TUNED=1` на стенде, параметры видны в `meta` результата.
- [ ] Прогоны с обеими конфигурациями записаны в тикет: какие параметры помогли, какие нет.
- [ ] Рекомендации в документации cqrsx — только подтверждённые замером.
