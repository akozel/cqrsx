## Сейчас

`PgInspector` (`sidecar/src/postgres.rs`) опрашивает базу каждые 400 мс (`SIDECAR_POLL_MS`) в одной транзакции
REPEATABLE READ. Каждый запрос в ней читает таблицу целиком:

| Запрос | Что делает |
|---|---|
| последние 200 событий (`postgres.rs:12`) | `ORDER BY metadata->>'recorded_at'`: разбор JSON каждой строки журнала и сортировка |
| `SELECT count(*) FROM events`, снапшоты, outbox | полный проход |
| `GROUP BY aggregate_type, aggregate_id` по событиям | полный проход с группировкой |
| `GROUP BY status` по outbox | полный проход |
| последние 200 задач (`postgres.rs:21`) | `ORDER BY created_at`, индекса нет |

На свежем демо это миллисекунды. После нагрузки на dev-стек — миллион событий или миллион выполненных задач до
задачи 07 — каждый опрос стоит секунды CPU базы. Транзакция всё это время держит горизонт очистки, и VACUUM не может
убрать мёртвые версии очереди (задача 09).

## Станет

- **Итоги — по оценкам.** Счётчики берутся из `pg_stat_user_tables.n_live_tup` или `pg_class.reltuples`. Точный
  `count(*)` — только по запросу пользователя (кнопка или отдельный эндпоинт), если он нужен.
- **Последние события — по `tx`** через `events_feed_idx`: по одному запросу на тип агрегата
  (`WHERE aggregate_type = $1 ORDER BY tx DESC LIMIT n`), слияние в sidecar. Порядок коммита вместо `recorded_at`.
- **События одного агрегата** — с типом агрегата в условии, по первичному ключу.
- **Группировка по агрегатам** — по требованию, а не на каждом опросе.
- **Последние задачи.** После задачи 07 в outbox только живые задачи, и сортировка по `created_at` дешёвая. Если 07
  не будет — id задач UUIDv7 (`Uuid::now_v7()`), и «последние» читаются по ключу.

## Зачем, на примере

Пользователь прогнал на dev-стеке нагрузку и открыл UI. Пока открыта вкладка X-ray, PostgreSQL каждые 400 мс разбирает
JSON метаданных миллиона событий, чтобы показать последние 200.

## Риски

- Оценки `n_live_tup` отстают от точного числа. UI показывает их как приблизительные («≈»), это решение владельца
  демо.
- Порядок «последних событий» меняется: по коммиту, а не по `recorded_at`. Для демо это то же самое, разница видна
  только при одновременных коммитах.

## Как измерить

Своя база без стенда: журнал на 1 млн событий и 1 млн строк outbox, сгенерированный SQL. Время одного опроса X-ray
до и после (`EXPLAIN (ANALYZE, BUFFERS)` по каждому запросу) и сколько секунд держится транзакция.

## Критерии приёмки

- [ ] Ни один запрос опроса не читает журнал или outbox целиком; время опроса не растёт с размером журнала (замер на
      1 млн событий записан в тикет).
- [ ] UI показывает приблизительные итоги понятно; точные — по запросу, если решено их оставить.
- [ ] Тесты sidecar обновлены.
