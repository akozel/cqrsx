## Сейчас

Три траты на каждую команду, которые ничего не дают.

1. **SQL собирается заново на каждую команду.** `PostgresFrameworkFactory::framework` (`postgres/command.rs:79`) создаёт
   `PostgresEventRepositoryWithOutbox::new(pool)`. Тот создаёт `PostgresEventRepository::new(pool)` (`outbox.rs:32`), а
   тот — `SqlQueryFactory::new("events", "snapshots")` (`event_repository.rs:131`). Это 12 `format!` строк SQL длиной в
   сотни байт на каждую команду, хотя тексты одни и те же для всего процесса.
2. **Снапшот копируется целиком перед разбором.** `TryFrom<SerializedSnapshot> for EventStoreAggregateContext`
   (`store/persisted.rs:593`) вызывает `serde_json::from_value(snapshot.aggregate.clone())`, хотя снапшот передан по
   значению. Для зала на 40 мест это копия дерева JSON из сотен узлов на каждую загрузку.
3. **Асинхронный мьютекс в `EventSink`.** `EventSink::write` (`event_sink.rs:24`) берёт `tokio::sync::Mutex` ради
   `Vec::push`. Мьютекс не держится через `.await`, поэтому хватит `std::sync::Mutex`.

## Станет

1. Тексты SQL строятся один раз. `PostgresEventRepository` держит `Arc<SqlQueryFactory>`. Фабрика исполнителя создаёт
   репозиторий при сборке, а на команду только клонирует его — копия пула и `Arc`. Открытый API
   (`PostgresEventRepository::new`, `with_tables`, `PostgresEventRepositoryWithOutbox::new`) остаётся.
2. `serde_json::from_value(snapshot.aggregate)` без клона.
3. `std::sync::Mutex` в `EventSink`. Сигнатуры `write` и `collect` остаются асинхронными: это API агрегатов.

## Зачем, на примере

На горячем концерте команды идут строго по одной, и всё, что команда делает под блокировкой, умножается на ~700 в
секунду. Копия снапшота и 12 строк SQL — мелочь на команду, но эта мелочь никому не нужна.

## Риски

Нет: поведение не меняется. Тесты репозитория на свои имена таблиц (`custom_tables_reach_every_query`) остаются.

## Как измерить

`02b-spread-vus50` и `01-hot-key-vus40`, профиль `app`, «до» и «после» вперемешку, `REPEAT=3`. Смотреть CPU бэкенда на
1000 команд и принятых в секунду. Эффект может оказаться в пределах шума. Тогда правка всё равно остаётся ради
простоты, если пользователь согласен.

## Критерии приёмки

- [x] `SqlQueryFactory` создаётся один раз на репозиторий исполнителя; тест: две команды одного исполнителя делят
      один экземпляр.
- [x] Клона снапшота нет; тест загрузки со снапшотом и с несовместимым снапшотом (откат к полной истории) проходит.
- [x] `EventSink` на `std::sync::Mutex`.
- [x] Замер записан в тикет.

## Результат

**Что сделано:**
- **SQL один раз:**
  - `PostgresEventRepository` держит `Arc<SqlQueryFactory>` и стал `Clone`, как и
    `PostgresEventRepositoryWithOutbox`;
  - `PostgresFrameworkFactory` хранит репозиторий, созданный вместе с исполнителем, и на команду отдаёт его клон с
    задачами команды;
  - `new`, `with_tables` и `PostgresEventRepositoryWithOutbox::new` остались;
  - тесты: `every_command_reads_with_the_sql_texts_of_its_executor` (`postgres/command.rs`) и
    `clones_share_the_sql_texts_and_new_tables_build_their_own` (`postgres/event_repository.rs`).
- **Снапшот без клона:** `serde_json::from_value(snapshot.aggregate)`. Загрузку со снапшотом и откат к полной
  истории при несовместимом снапшоте проверяют прежние тесты `load_aggregate_existing` и
  `load_aggregate_after_deserialize_error`.
- **`EventSink`:** `std::sync::Mutex`. При отравлении берётся содержимое: push не оставляет буфер наполовину
  изменённым. `write` и `collect` остались асинхронными.
- **Документация:** `components.md`, строки «Event emission», «SQL operations», «Backend assembly».

**Замер.** Итоговая серия: образы `e04-03` и `e04-04` вперемешку с остальными этапами, профиль `app` (бэкенд —
2 ядра под квотой), пул 20, `REPEAT=3`. Партии `e04f-03-`, `e04f-04-`; медианы, в скобках min–max.

| | 03 | 04 | Δ |
|---|---|---|---|
| **Брони по разным концертам, 50 VU** | | | |
| CPU бэкенда на 1000 команд, мс | 473 (460–531) | 449 (434–458) | **−5 %**, диапазоны не пересекаются |
| принятых/с | 3 748 (3 428–3 896) | 3 848 (3 776–3 969) | +3 % |
| p50, мс | 13.0 | 12.1 | −7 %, диапазоны не пересекаются |
| память бэкенда (`anon`), МиБ | 9.3 | 8.8 | −5 % |
| **Горячий ключ, 40 VU** | | | |
| CPU бэкенда на 1000 команд, мс | 1 099 (1 059–1 113) | 1 053 (1 009–1 064) | −4 % |
| принятых/с | 678 | 698 | +3 % |
| p50 / p99, мс | 59.0 / 70.0 | 57.1 / 67.2 | −3 % / −4 % |

Быстрый замер сразу после правки (`REPEAT=1`, партии `e04-q04-*`) показал то же: −3 % и −5 % CPU бэкенда.

**Что видно:** выигрыш небольшой, как и ожидал тикет, но не в шуме. В бронях CPU бэкенда на команду −5 %, и
диапазоны повторов не пересекаются. На горячем ключе −4 %: диапазоны соприкасаются. CPU PostgreSQL и MongoDB
не меняется — правка их не касается. Правка ещё и упрощает код: SQL строится один раз, без клона и без
асинхронного мьютекса.
