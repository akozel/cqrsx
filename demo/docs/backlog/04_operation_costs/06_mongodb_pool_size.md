## Сейчас

Демо создаёт клиента MongoDB без `max_pool_size` (`process.rs:199`), поэтому у драйвера 10 соединений
(`mongodb-3.9.1/src/cmap.rs:50`, `DEFAULT_MAX_POOL_SIZE`). Через этот клиент идут:
- документы двух процессоров, каждый пишет до 16 одновременно (`DEFAULT_PROCESSOR_CONCURRENCY`,
  `ENCORE_PROJECTION_CONCURRENCY`);
- закладки, аренды и статус проекций;
- чтения HTTP: залы, кошельки.

На страницах с сотнями ключей (`02a`, `02b`) до 32 операций ждут 10 соединений внутри драйвера.

## Станет

`ENCORE_MONGODB_POOL_SIZE` с умолчанием демо `DEFAULT_MONGODB_POOL_SIZE` в `config.rs`. Пул клиента MongoDB — настройка
демо, а не cqrsx: клиента собирает демо. Значение умолчания выбирается по замеру. Не меньше суммарной параллельности
процессоров, если замер не покажет иного. Переменная — в разделе 1 `.env.example`.

## Зачем, на примере

Страница из 1 000 анонсов — 1 000 новых залов. Процессор пишет 16 из них одновременно, второй процессор (кошельки) в
это время тоже пишет, а соединений 10. Часть записей ждёт свободного соединения, и время страницы растёт без всякой
нагрузки на саму MongoDB.

## Риски

Больше соединений — больше потоков у сервера MongoDB. Если MongoDB уже упирается в CPU, рост пула ничего не даст или
ухудшит. Решать по замеру.

## Как измерить

`02a-announce-vus100` (`full`, wrk) и `02b-spread-vus50` (`db`) при пуле 10, 32 и 64, `REPEAT=3`:
- анонсов и броней в секунду;
- CPU MongoDB на 1000 команд;
- отставание проекций p99.

## Критерии приёмки

- [x] `ENCORE_MONGODB_POOL_SIZE` в конфигурации, `.env.example` и стенде (`MONGO_POOL=`).
- [x] Умолчание выбрано по замеру, замер записан в тикет.

## Результат

**Что сделано:**
- **Демо:**
  - `config.rs`: `ENCORE_MONGODB_POOL_SIZE`, константа `DEFAULT_MONGODB_POOL_SIZE` (`NonZeroU32`, ноль
    отклоняется) и тест `the_mongodb_pool_takes_the_demo_default_and_rejects_zero`;
  - `process.rs`: `max_pool_size` клиента;
  - `testing.rs`: поле в тестовой конфигурации;
  - `.env.example`, раздел 1.
- **Стенд:**
  - `load/compose.yaml` и `load/run.sh`: `MONGO_POOL=` → `ENCORE_MONGODB_POOL_SIZE`, пусто — умолчание бэкенда;
  - `load/tools/collect.mjs`: `meta.mongo_pool`;
  - `load/README.md`.

**Замер.** Образ с задачами 03–06 (`e04-06`), `MONGO_POOL` 10 / 32 / 64, `REPEAT=3` вперемешку, пул PostgreSQL 20.
Партии `e04-q06-pool10-`, `-pool32-`, `-pool64-`, медианы.

| | пул 10 | пул 32 | пул 64 |
|---|---|---|---|
| **Анонсы, 100 VU, `full`, wrk** | | | |
| анонсов/с | 13 609 | 13 421 | 13 383 |
| p50 / p99, мс | 7.27 / 13.2 | 7.40 / 12.7 | 7.45 / 11.6 |
| CPU MongoDB на 1000 анонсов, мс | **116** | 135 (+17 %) | 135 (+17 %) |
| ядер MongoDB | 1.45 | 1.68 | 1.64 |
| операций MongoDB на анонс | 1.01 | 1.01 | 1.01 |
| **Брони, 50 VU, `db`** | | | |
| броней/с | 4 074 | 4 099 | 4 082 |
| p50 / p99, мс | 7.39 / 49 | 7.64 / 55 | 8.28 / 51 |
| CPU MongoDB на 1000 броней, мс | **252** | 269 (+7 %) | 280 (+11 %) |

**Решение: умолчание 10** — то же, что у драйвера. Гипотеза тикета не подтвердилась: при 32 и 64 соединениях
команд в секунду не больше, разница в пределах шума. CPU MongoDB на команду растёт на 7–17 %, диапазоны
повторов не пересекаются. p50 броней при 64 соединениях выше на 12 %. Записи процессоров не ждут соединения так,
чтобы это стоило пропускной способности: предел анонсов в `full` — PostgreSQL, он занят на 3.1 ядра из 4.
Переменная осталась: пул — настройка развёртывания.
