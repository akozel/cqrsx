# Эпик 04. Цена операций после эпика 03

[← все эпики](../README.md)

Источник: [аудит производительности 2026-10-25](../../PERFORMANCE_AUDIT.md), коммит `678117d`. В тикетах пункты аудита
называются по его номерам: Q — очередь outbox, C — путь команды, N — соединения, P — проекции, M — замеры, D — demo.

После эпика 03 главные траты сместились. Самая дорогая операция базы теперь не команда, а учёт задач outbox.
Горячий ключ упирается во время, пока команда держит блокировку агрегата. Каждый оператор SQL по-прежнему стоит двух
обращений. Эпик снижает цену каждой операции — операторов, обращений и CPU на команду и на задачу — и поднимает три
потолка:
- устойчивую пропускную способность цепочки «бронь → задача → команда `Fan` → письмо»;
- горячий ключ;
- создание агрегатов.

После задач 01–06 (2026-10-26; 05 отклонена; итоговая серия: [results_01_06.md](results_01_06.md)). Пул PostgreSQL 20, пауза
процессора 10 мс.

После задачи 19 (Q = C, аренда 30 с, порог подзагрузки 25 %; [19](19_claim_in_batches.md)) на сливе с 8 воркерами
claim забирает ~5 задач вместо 2.7. CPU PostgreSQL на бронь по цепочке −9 % (1 756 → 1 597 мс на 1 000), бэкенда
−7 %, слив быстрее на 9–25 % (точную цифру смазывают паузы хоста). Горячий ключ без изменений.

Что видно во всех сценариях:
- **Накладные расходы.** Около 0.1 мс CPU PostgreSQL на оператор уходит не на сам оператор: протокол, транзакция,
  фиксация, пинг при возврате соединения. Число операторов важнее их планов; исключением был settle, его
  исправила задача 03.
- **Окно k6 видит не всю цепочку.** Задачи outbox, порождённые бронями, в основном выполняются после окна. Поэтому
  метрики «на команду» теперь считаются и по всей цепочке (01), а устойчивую пропускную способность меряет прогон
  с постоянной частотой (02). Короткие прогоны её завышают: в `full` 1 100 броней/с выдерживаются 2 минуты, но не 5.

**По задачам:**
- **01, 02 — инструменты, приняты.** Метрики до слива, WAL и полные страницы по операторам, ожидания, операции
  MongoDB; прогон с постоянной частотой и графики во времени. Главные находки:
  - процессор проекций сверх учёта PostgreSQL не дороже обработчика в команде;
  - цепочка outbox в окне отнимает у горячего ключа до 20 % пропускной способности;
  - короткие прогоны завышают устойчивую пропускную способность: settle и claim дорожают, пока таблица outbox
    копит мёртвые строки.
- **03 — принята, главный выигрыш:** settle в 4–5 раз дешевле, слив +39 %, бронь по цепочке −29 % CPU PostgreSQL,
  устойчивая частота в `db` 750 → 850–900 броней/с. Вариант с одиночным `UPDATE` отклонён
  ([03](03_settle_by_primary_key.md), «Решение»).
- **04 — принята:** CPU бэкенда на бронь −5 % (диапазоны не пересекаются), на горячем ключе −4 %, код проще.
- **05 — отклонена и откачена:** одна операция MongoDB вместо двух на новый документ (анонсы +11 %, MongoDB
  −42 %). Но в production это редкая операция, а код `ViewProjection` она заметно усложняет.
- **06 — принята как настройка:** пул 32 и 64 не быстрее 10 и дороже по CPU MongoDB; умолчание 10 — как у
  драйвера.
- **Горячий ключ не сдвинулся:** его предел — ожидание WAL при фиксации (задачи 14, 15, 17), а освобождённый
  PostgreSQL уходит цепочке.
- **Память** ни на одном этапе не изменилась вне шума: бэкенд 11–20 МиБ, PostgreSQL и MongoDB растут вместе
  с данными.

2. **03 — одна строка с самым большим ожидаемым эффектом.**
3. **04–06** — дёшево, каждая со своим замером.
4. **09, 10** — очередь и долгая работа (19 сделана). 07 отложена (2026-10-26): политика хранения outbox не решена, журнал

5. **11–13** — расширения API исполнителя и хранилища.
6. **14, затем 15–17** — горячий ключ. Что брать после 15, решит раскладка удержания блокировки из 14.

16 от горячего ключа не зависит, её можно взять раньше, если пакеты на оператор окажутся главным рычагом в 02.

## Общие правила

- **Одна задача — один коммит**, сообщение `perf(cqrsx): <что>; adopt in demo`. Если задача только про стенд —
  `perf(load): <что>`, только про демо — `perf(demo): <что>` или `perf(sidecar): <что>`. В коммит входят изменение,
  тесты, `cqrsx/doc/components.md` и перевод demo.
- **Коммитит только пользователь.** Агент не коммитит по своей инициативе (`git commit`, `--amend`, `push`): он
  оставляет готовое рабочее дерево и предлагает сообщение коммита и список файлов.
- **Замер — «до» и «после» вперемешку, в одной сессии**, как в эпике 02: образ «до» собирается из `git archive <base>`
  (README эпика 02, «Что мерить»), инструменты — в
  [`../02_postgres_performance/perf/`](../02_postgres_performance/perf/README.md). Пока задача в работе, хватает `REPEAT=1`; для приёмки нужно `REPEAT=3`. Во время замера на машине ничего не собирать.
- **После задачи 01** метрики «на команду» в сценариях с цепочкой считаются до слива (`chain`), а не по окну k6.
- **После задачи 02** каждая задача про очередь (03, 09, 19) мерит ещё и 5-минутную точку на частоте базовой линии.
- **Результат** записать в тикет (статус, коммит, цифры «было → стало») и в `demo/docs/PROGRESS.md`. Правка без
  выигрыша не вливается автоматически: решаем по цифрам, оставить ли её ради простоты кода.
- **Покрытие `cqrsx` не ниже 97 %**, матрица фич из корневого `CLAUDE.md`.
- **Обратная совместимость не нужна:** API, схема и скрипты меняются так, как чище; базы пересоздаются (`make reset`).
- **Каждое настраиваемое значение** — константа умолчания (в cqrsx, если это знание библиотеки) и переменная `ENCORE_*`
  в `.env.example`. Режимов и переключателей не добавляем без нужды.
- **Стенд изолирован** (`encore-load`), запущенный dev-стек пользователя не трогаем. Прогон не дольше 5 минут (D-22
  эпика 03).

## Решено не делать

- **Settle одиночным `UPDATE`** (вариант задачи 03): выигрыша нет, а снимается проверенный порядок «блокировка,
  потом проверка времени» ([03](03_settle_by_primary_key.md), «Решение»).
- **Закрытие задачи вместе со следующим claim и пакетный settle** ([08](08_settle_with_next_claim.md)): одна
  транзакция на много задач. Сбой или таймаут оставляют неизвестным итог всей пачки, повторять нельзя, и вся пачка
  выполнится ещё раз. Выигрыш — около 10 % CPU PostgreSQL по цепочке, и это оценка.
- **Канал больше числа воркеров** ([19](19_claim_in_batches.md), «Решение»). При Q = 4·C цепочка дешевле ещё на
  9–15 %, слив быстрее до +35 %. Но любой Q > C требует аренду на вторую волну (в демо больше 32 с), а горячий ключ
  и устойчивую частоту не поднимает. Правило: Q = C, аренда 30 с.
- **Новый документ витрины без чтения** ([05](05_new_view_without_read.md)): в production это редкая операция, а
  код `ViewProjection` заметно сложнее.
- **Кэш документа витрины у рабочего ключа.** Он экономит чтение только ключам, у которых в буфере стоит следующая
  пачка: на горячем ключе это 70–100 чтений в секунду, а MongoDB там занята на 0.34 ядра из трёх (аудит, P).
- **Из эпика 02 в силе:**
  - `synchronous_commit = off` — смена гарантий, а не оптимизация;
  - `jsonb` для событий;
  - растить пул PostgreSQL дальше 20.
