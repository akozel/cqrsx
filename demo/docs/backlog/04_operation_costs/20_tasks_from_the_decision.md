## Было (до задачи)

Задачи привязываются к команде до её выполнения. Сервис приложения строит `Vec<NewTask>` и передаёт его в
`CommandExecutor::execute(…, tasks)`. `FrameworkFactory::framework(tasks)` (`executor.rs:16–27`) вызывается «once per
command, before its first attempt», и повторы после конфликта используют тот же список. Агрегат задач не видит: его
`handle` пишет в `EventSink` только события.

```
application/concert/tasks.rs     контракты RecordTicketV1, RecordCancellationV1 и их сборщики
application/tasks.rs::new_task   метаданные причинности, max_attempts
        ▲ вызываются из сценариев до команды
application/concert/cancel_booking.rs   refund_tasks(): предварительное чтение концерта → задача
application/concert/book_seat.rs        задача из команды и констант зала
        │ Vec<NewTask>
        ▼
CommandService::run(…, tasks) → executor.execute_with_metadata(…, tasks)
  → FrameworkFactory::framework(tasks) → репозиторий с outbox: события + задачи одним SQL
```

Бронь строит задачу из команды и констант зала. Отмене нужны id брони и сумма возврата — цена, уплаченная при
бронировании. В команде их нет, а принимать их от клиента нельзя. Поэтому демо читает концерт до команды
(`cancel_booking.rs:59`, `self.history.load_aggregate`):

```
cancel_booking(concert, CancelBooking{seat, fan, cancellation_id})
 ├─ ① history.load_aggregate(concert)  ── снапшот + события после него, ВНЕ блокировки
 ├─ state.bookings[seat] → booking_id, price → задача record_cancellation
 └─ executor.execute(concert, CancelBooking, metadata, [задача])
     ├─ lock(concert) … очередь блокировки
     ├─ попытка: ② load_aggregate ── второй раз; handle → BookingCancelled{booking_id, refund, …}
     │           commit(события + [задача])
     └─ конфликт → новая попытка: ② и handle заново, задача та же
```

Что это стоит:
- **Лишняя загрузка.** На каждую отмену — два оператора (снапшот и события после него) и разбор снапшота, вне
  блокировки.
- **Масштаб на горячем ключе.** Отмена — половина команд: 20 581 загрузка против 15 806 коммитов за окно. Без
  предварительного чтения уходит 9 550 операторов из 86 167, то есть 11 %.
- **Окно рассогласования.** Между предварительным чтением и коммитом другая команда может изменить бронь. Агрегат
  решит по свежему состоянию, но задача построена по старому чтению и при повторе не пересчитывается.

При этом событие `BookingCancelled` (`domain/concert/events/booking_cancelled.rs`) несёт всё, что нужно задаче
`encore_record_cancellation`: место, фаната, id брони, id отмены и возврат. `SeatBooked` несёт всё для
`encore_record_ticket`: зону, цену, фаната, его имя и id брони.

## Решение

**Пользователь, 2026-10-26: спроектировать новый компонент фреймворка, с которым пользователю удобно композировать
агрегат и задачи.** Пользователь должен легко описывать такую оркестрацию: решение агрегата → задачи → команды
других агрегатов. Компонент реализуется средствами ядра cqrsx и годится для любого домена, не только для демо.

Принципы, согласованные при разборе задачи 11:
1. **Агрегат решает только события.** Задачи в домен не попадают: `sink.write(event, task, self)` отклонён.
   - `NewTask` — контракт доставки, а не факт предметной области. В нём тип и версия задачи, JSON, `max_attempts`
     из конфигурации и метаданные причинности команды. Ничего из этого у `handle` нет.
   - Реакция на событие — правило приложения. Тот же агрегат в другом приложении может реагировать иначе.
   - У события может не быть задачи, а может быть несколько. Задача может зависеть от нескольких событий.
2. **Задачи — функция решения.** На входе — состояние до команды, команда, решённые события и метаданные.
   Одной пары «агрегат + команда» мало:
   - в состоянии после команды данных может уже не быть: отмена удаляет бронь;
   - без событий построитель задач повторял бы логику агрегата, например правило возврата;
   - команда без событий не должна давать задач.
3. **Ядро вызывает функцию после `handle`**, на каждой попытке, под блокировкой агрегата и до коммита. Задачи
   коммитятся вместе с событиями этой попытки, одной транзакцией. Повтор после конфликта строит задачи заново.
4. **Функция чистая и синхронная**, без ввода-вывода: она работает под блокировкой. Внешние данные приходят в
   команде.
5. **Ошибка функции отказывает команде**, ничего не записав, как сейчас `Executed::tasks_unavailable`.
6. **Одно место на тип агрегата.** Его регистрирует исполнитель. Сервис передаёт только команду: у `execute`
   пропадает параметр `tasks`, у `FrameworkFactory::framework` — аргумент.
7. **Исполнитель сообщает закоммиченные задачи** в своём результате. Сейчас сценарий знает их заранее и пишет в
   ленту активности (`Executed.tasks`).

```
service ──команда──▶ executor (блокировка агрегата)
                       ├─ загрузить агрегат                              ── один раз
                       ├─ handle(команда) ──▶ события   (ошибка домена → отказ, ничего не пишется)
                       ├─ задачи = f(состояние до, команда, события, метаданные)   (ошибка → отказ)
                       ├─ commit(события + задачи)       ── одна транзакция
                       │    конфликт → новая попытка: загрузка, handle, f заново
                       └─ ответ: принята, события, задачи
позже: воркер outbox берёт задачу → команда другому агрегату
```

## Дизайн (согласован с пользователем 2026-10-26)

План реализации утверждён пользователем. Три развилки решил он:
- **Правила живут в процессах.** Процесс — один тип (`TicketDelivery`, `Refund`), он реализует
  `TaskPlanner<Concert>` и `TaskPlanner<Fan>`. Исполнитель агрегата регистрирует один планировщик — кортеж
  процессов, которые реагируют на этот агрегат (`workflows::concert_tasks(n)`, `fan_tasks(n)`). Процесс
  читается целиком в своей папке `workflows/`: реакции, шаги, контракты задач.
- **Метаданные остаются картой, причинность применяет ядро.** Порт по-прежнему принимает
  `HashMap<String, String>`. Ядро читает из неё `Causation`, штампует её в каждую задачу и выводит id задачи.
  Планировщик видит `decision.causation` и карту. Нового параметра-типа нет.
- **Id задачи детерминированный:** UUID v5 из типа и id агрегата, id команды, типа и версии задачи и номера
  задачи среди задач этого формата в плане. Без причинности в метаданных id случайный (v4).

Решено в плане:
- **Место вызова — вариант (а).** `CqrsFramework` планирует между `handle` и `EventStore::commit`; задачи —
  часть коммита.
- **`FrameworkFactory` удалён.** Он нужен был только для привязки задач к хранилищу команды. Теперь
  хранилища без состояния: исполнитель владеет одним фреймворком, сервисы `PostgresCommandExecutor` больше
  не клонируются (`A::Services: Clone` не нужен).
- **Хранилища.** `EventStore::commit(events, context, metadata, tasks)`. У `PersistedEventRepository` есть
  метод по умолчанию `persist_with_tasks`: он отказывает непустым задачам до любого ввода-вывода, так что
  хранилище без outbox отказывает само, а около 140 вызовов `persist` в тестах не меняются. Его переопределяют
  outbox-репозиторий и `MemEventRepository` (outbox в памяти по правилам PostgreSQL, `outbox::<A>()`).
- **Ответ исполнителя** — `CommitReport { events, tasks }`.
- **Ошибка планировщика** — `AggregateError::TaskPlan(TaskPlanError)` → `CommandGatewayError::Unavailable`;
  ничего не записано, повтора нет, в журнал — один раз с категорией `task_plan`, без текста ошибки.
  `TaskPlanError`: невалидная задача, причинность, ошибка приложения (например, id агрегата, который
  планировщик не разобрал).
- **Причинность строгая.** Без `command_id` причинности нет. С ним все три id должны быть UUID, иначе команда,
  которая планирует задачи, получает отказ.
- **Нет событий — нет плана.** Планировщик не вызывается для решения без событий; коммит, как и раньше,
  вызывается. Повтор после конфликта планирует заново по свежему состоянию.
- **Несколько событий в одном коммите PostgreSQL по-прежнему запрещены (D-02).** `ON CONFLICT DO NOTHING` со
  счётом строк атомарен только для одной строки: несколько строк могли бы частично вставиться рядом с
  конкурентом-победителем. API планировщика уже принимает срез событий.
- **Не делаем:** типизированные метаданные, планировщики-замыкания, помощники в `TestFramework`.

```rust
// cqrsx::cqrs::command::planner
pub struct Decision<'a, A: Aggregate> {
    pub aggregate_id: &'a str,
    pub before: &'a A,                          // the committed state the command was decided on
    pub after: &'a A,                           // `before` with `events` applied
    pub command: &'a A::Command,
    pub events: &'a [A::Event],                 // never empty
    pub metadata: &'a HashMap<String, String>,
    pub causation: Option<&'a Causation>,       // parsed from `metadata`; stamped on every task by the core
}

pub trait TaskPlanner<A: Aggregate>: Send + Sync {
    fn plan(&self, decision: &Decision<'_, A>) -> Result<Vec<NewTask>, TaskPlanError>;
}
// tuples of 2 to 8 planners are planners: in order, concatenated, the first error wins

// demo: application/workflows/ticket_delivery.rs
impl TaskPlanner<Concert> for TicketDelivery { /* SeatBooked → encore_record_ticket */ }
impl TaskPlanner<Fan> for TicketDelivery { /* TicketRecorded → encore_send_e_ticket */ }
// application/workflows.rs: one planner per aggregate type
pub fn concert_tasks(max_attempts: i32) -> impl TaskPlanner<Concert> {
    (TicketDelivery { max_attempts }, Refund { max_attempts })
}
// bootstrap: PostgresCommandExecutor::new(..).with_task_planner(workflows::concert_tasks(n))
```

## Что решено по вопросам дизайна

- **Форма компонента и удобство композиции.** Трейт `TaskPlanner<A>` плюс кортежи. Процесс из нескольких шагов
  читается целиком: один тип планирует для каждого агрегата, на чьи события реагирует, а шаги-обработчики и
  контракты лежат в той же папке. Отдельное общее описание процесса не понадобилось.
- **Метаданные приложения.** Типизированно нужна только причинность. Её разбирает ядро
  (`Causation::from_event_metadata`) и само применяет к задачам. Ключи приложения планировщик читает из карты.
- **Место вызова** — вариант (а).
- **Хранилища без outbox.** Отказ до ввода-вывода (`persist_with_tasks` по умолчанию). `MemStore` принимает
  задачи с событиями и не хранит их. `MemEventRepository` ведёт outbox по правилам PostgreSQL.
- **Несколько событий на коммит** — вне задачи (D-02).
- **Id задачи** — UUID v5, одинаковый на всех попытках. Тот же `command_id` на том же агрегате второй раз
  упирается в первичный ключ outbox: коммит отклоняется целиком (`Unavailable`). Повторную доставку задачи по
  истечении аренды это не отсекает — у каждой обработки новый `command_id`; от повтора защищают правила
  агрегата (R9, R11).
- **`TestCommandExecutor`.** Тот же планировщик (`with_task_planner`), `take_published_tasks()` — задачи
  закоммиченных ответов; `take_bound_tasks` удалён.
- **Перевод демо.** Планировщики `TicketDelivery` и `Refund` для `Concert` и `Fan`. Шаги цепочки строятся из
  событий. Предварительное чтение в `cancel_booking` удалено, `history_store` тоже. `Executed.tasks` берётся
  из ответа исполнителя.

## Тесты

- **Юнит-тесты cqrsx:**
  - `causation.rs`:
    - разбор причинности из карты: нет `command_id`, `Missing`, `NotUuid`, без `source`;
    - `task_id`: эталонное значение (посчитано независимо через Python `uuid5`), зависит от каждого входа,
      поля не «перетекают» друг в друга;
    - `uuid_v5` против эталонов крейта uuid;
    - проверка свойств: разные входы дают разные id.
  - `planner.rs`:
    - кортежи 2, 3 и 8, первая ошибка останавливает остальных;
    - штамп сохраняет ключи приложения, расписание и `max_attempts`, номер считается по формату;
    - без причинности id и метаданные не меняются;
    - битая причинность отказывает только плану с задачами;
    - проверка свойств: id уникальны и стабильны.
  - `cqrs.rs`:
    - что видит планировщик (до и после, команда, события, метаданные, причинность);
    - нет событий или отказ домена — планировщик не вызывается;
    - ошибка планирования ничего не коммитит;
    - клон команды: ноль без планировщика, один с ним;
    - второй планировщик заменяет первый.
  - `executor.rs`:
    - повтор после конфликта планирует заново по свежему состоянию с теми же id;
    - исчерпанные конфликты ничего не публикуют;
    - отказ блокировки не загружает и не планирует;
    - планировщик выполняется строго между загрузкой и коммитом своей команды (20 параллельных команд);
    - два исполнителя публикуют задачи только закоммиченных попыток;
    - паника планировщика освобождает блокировку;
    - `Send`-команда без `Sync` с планировщиком;
    - ошибка планирования пишется в журнал один раз, без данных.
  - Хранилища:
    - outbox в памяти: задача без события, повтор id, конфликт, порядок;
    - отказ хранилищ без outbox;
    - `TestCommandExecutor`.
- **Интеграционные cqrsx, в памяти** (`tests/cqrs/planning.rs`):
  - процесс через два агрегата с сохранением correlation id и повторной доставкой;
  - проверка свойств: опубликованы ровно задачи закоммитившихся попыток, каждая — по своему состоянию,
    с внешними конфликтами;
  - гонка двух исполнителей;
  - конфликт, после которого домен отказывает.
- **Интеграционные cqrsx, PostgreSQL** (`tests/postgres/planning.rs`, `command.rs`):
  - два узла и 40 команд с SQL-инвариантом «каждая задача соединяется со своим событием, payload и id —
    от него»;
  - 40 параллельных команд через один исполнитель;
  - команда, брошенная во время коммита: событие и задача вместе или ничего;
  - ошибка планировщика, решение без событий, битая причинность;
  - повтор `command_id`: второй коммит отклонён целиком;

  - хранилище без outbox.
- **Демо:**
  - юнит-тесты планировщиков обоих процессов (точный JSON, другие события, чужой id агрегата);
  - сценарии: бронь и отмена со штампом и выводимым id, ровно одна загрузка на отмену;
  - детерминированный тест на устаревшее чтение: отмена в очереди блокировки за отменой и перебронированием
    возвращает деньги за свою бронь;
  - случайные гонки отмен и броней;
  - шаги цепочки и повторная доставка;
  - на PostgreSQL — гонка броней и отмен на двух узлах с SQL-инвариантом.

## Риски

- **Функция не должна обращаться наружу:** она выполняется под блокировкой. Синхронная сигнатура не даёт сделать
  `await`. Правило — в документации компонента.
- **Ошибка функции** (невалидная задача) — отказ команды до коммита.
- **Широкое изменение API.** Меняются `CommandExecutor`, `FrameworkFactory`, `EventStore::commit` и все места
  вызова в демо. Обратная совместимость не нужна (проект не выпущен).

## Как измерить

`01-hot-key-vus40`, `db` и `app`, «до» и «после», порядок вариантов в каждом проходе перемешан, `REPEAT=3`:
- загрузок агрегата столько же, сколько коммитов;
- операторов на команду −11 %;
- CPU бэкенда и PostgreSQL на команду;
- принятых в секунду.

## Результат

**Что сделано** (дизайн и тесты — в разделах выше):
- **cqrsx:**
  - модуль `cqrs::command::planner`: `Decision`, `TaskPlanner<A>` с кортежами от 2 до 8 планировщиков,
    `TaskPlanError`;
  - `with_task_planner` у `CqrsFramework`, `CommandExecutorCore`, `PostgresCommandExecutor` и
    `TestCommandExecutor`. Ядро планирует после `handle` на каждой попытке с событиями и коммитит задачи вместе с
    событиями этой попытки. Ответ исполнителя — `CommitReport { events, tasks }`;
  - `Causation::from_event_metadata`, `Causation::task_id` и `TASK_ID_NAMESPACE`. Ядро штампует причинность в
    каждую задачу, id задачи — UUID v5. SHA-1 берётся из крейта `sha1`: он уже был в дереве зависимостей;
  - `EventStore::commit(…, tasks)`. `PersistedEventRepository::persist_with_tasks` по умолчанию отказывает
    непустым задачам; outbox-репозиторий без состояния, `with_outbox` и `FrameworkFactory` удалены;
  - outbox в памяти у `MemEventRepository` (`outbox::<A>()`). `TestCommandExecutor::take_published_tasks`
    возвращает задачи закоммиченных ответов, `take_bound_tasks` удалён;
  - `AggregateError::TaskPlan` → `Unavailable`, в журнал — с категорией `task_plan`;
  - `README.md` (Quick start с планировщиком), `doc/components.md` (строка «Task planning»);
  - покрытие строк — 97.67 % по workspace и 97.65 % по cqrsx.
- **Демо:**
  - процессы `TicketDelivery` и `Refund` планируют задачи для `Concert` и `Fan`; исполнители регистрируют
    `workflows::concert_tasks(n)` и `fan_tasks(n)`;
  - контракты задач лежат в модуле `tasks` своего процесса, `application/concert/tasks.rs` удалён;
  - `cancel_booking` не читает концерт, `history_store` удалён, шаги цепочки не строят следующую задачу;
  - `PLAN.md` (D-25), `docs/API_MAPPING.md`.
- **Стенд:** `collect.mjs` считает загрузки агрегата (чтение снапшота) и коммиты (запись событий) в окне и при
  сливе: `commands.{window,drain}.{loads, commits, loads_per_commit}`. В `compare.mjs` — строки `loads/commit` и
  `drain loads/commit`, описание — в `perf/README.md`.

**Замер.** Образы `e20-base` (HEAD `a9baac7`: задачи строятся до команды, отмена читает концерт заранее) и `e20`
(планировщик, без предварительного чтения), пул 20, `REPEAT=5`, две серии по 30 прогонов. В серии 1 порядок
вариантов должен был перемешиваться в каждом проходе, но `shuf --random-source` с повторяющимся текстом зерна дал
один порядок на все проходы. Серия 2 перемешана по-настоящему (`random.Random` с зерном прохода), порядок каждого
прохода записан в журнал серии. В таблице — медианы серии 2, в последнем столбце — Δ серии 1; «≠» — диапазоны

Память бэкенда — 11–12.5 МиБ у обоих образов.

**Что видно:**
- **Предварительного чтения больше нет.** Загрузок агрегата ровно столько же, сколько коммитов: на горячем ключе
  1.29 → 1.00, на сливе по-прежнему 1.00. Через всю цепочку команда стоит на один оператор меньше (10.3 → 9.27),
  транзакций и пакетов тоже на 10–11 % меньше. Так и предсказывал разбор: 9 550 операторов из 86 167. WAL на
  команду тот же: ушли чтения, а не записи.
- **PostgreSQL дешевле на 3–5 % CPU на команду**, в окне и по цепочке; в обеих сериях диапазоны не пересекаются.
  По цепочке это 78 мс на 1000 команд, или 0.08 мс на ушедший оператор — цена протокола и транзакции (около 0.1 мс
  на оператор, «Что видно во всех сценариях» в README эпика). Остальное время PostgreSQL уходит на запись, а её
  задача не меняла.
- **Бэкенд дешевле на 6–10 % CPU на команду.** Разбор снапшота и событий при предварительном чтении стоил больше,
  чем теперь стоит планирование под блокировкой: клон команды, сериализация задачи, SHA-1 и штамп. В серии 1
  диапазоны не пересекаются; в серии 2 пересекаются из-за одного прогона e20.
- **Пропускная способность горячего ключа та же:** 762 → 763 принятых/с, p50 52 мс. Предел — ожидание WAL при
  фиксации (69–74 % выборок занятых сеансов), а не CPU. Планирование под блокировкой удержание заметно не
  удлинило.
- **MongoDB не изменилась.** В серии 1 операций MongoDB на команду было на 21 % меньше, и диапазоны не
  пересекались. В серии 2 разница −8 %, а прогоны обоих образов разбросаны от 1.24 до 2.07 операции на команду.
  Число операций зависит от того, сколько событий одного ключа попадает в одну пачку процессора, то есть от
  времени. Код процессоров задача не трогала. Сдвиг серии 1 — следствие её одинакового порядка.
- **Слив — в пределах разброса.** Там только брони, и предварительного чтения не было и раньше. Цены планировщика
  на книжке болельщика не видно: CPU на бронь по цепочке тот же. Задач/с по медиане на 6–8 % меньше, но
  диапазоны повторов почти совпадают.
