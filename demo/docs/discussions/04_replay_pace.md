# 04. Замедленный replay: `speed` в контракте

Статус: обсуждается, низкий приоритет. Откуда: аудит K-2 (§4.2 [`../BOUNDARY_AUDIT.md`](../BOUNDARY_AUDIT.md)).

## 1. Контекст

`POST /api/projections/rebuild { "speed": "slow" | "fast" }`; `slow` — пауза `ENCORE_REPLAY_SLOW_DELAY_MS`
(80 мс) перед каждым событием, чтобы на проекторе «места загорались по одному». Реализовано через библиотечный
`EventReplay::with_pace(Duration)` (тикет 06); back-end лишь переводит `slow` в `Duration`.

Темп пересборки — честная production-настройка (не перегружать read DB во время replay), но имена `slow`/`fast`
и дефолт `slow` при пустом теле — чистый демо-театр в контракте production-подобного эндпоинта.

## 2. Варианты

| | Контракт | Плюсы | Минусы |
|---|---|---|---|
| A. Как есть | `speed: slow \| fast`, пустое тело = `slow` | ничего не менять | названия из демо; дефолт «медленно» для production странен |
| B. Темп в миллисекундах | `pace_ms: u64`, пустое тело = `0` | честное production-имя; UI шлёт `80` или `0` | UI и i18n правятся; `ENCORE_REPLAY_SLOW_DELAY_MS` переезжает в UI как «значение для галочки 🐢» |
| C. Убрать замедление | без параметра | минус настройка | теряется лучший визуальный момент демо |

## 3. Что нужно, чтобы решить

Только вкус владельца демо. B — пять строк в back-end и десять в UI; делать вместе с любой следующей правкой
контракта `/api/projections/*`.
