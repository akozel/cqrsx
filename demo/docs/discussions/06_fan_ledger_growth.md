# 06. Рост состояния `Fan`: журнал на пару «фанат + концерт»

**Решение: вариант C1, 2026-10-18 (D-14).** Идентичность агрегата `Fan` — пара «фанат + концерт»,
`aggregate_id = <fan_id>:<concert_id>` (`FanLedgerId`, `domain/shared/ids.rs`). Реализовано 2026-10-18.
Откуда: нагрузочный прогон `03b-drain-hot-fan-w8` ([`../../load/README.md`](../../load/README.md),
`demo/load/results/20261018-144205-03b-drain-hot-fan-w8`).

## 1. Контекст

У фаната было два «тела», и оба хранили каждый билет целиком и навсегда: состояние агрегата `Fan`
(`tickets: BTreeMap<Uuid, Ticket>`, оно же `snapshots.payload`, перезаписываемый целиком каждое 10-е событие) и
документ `fan_wallets` (читается и пишется целиком `ViewProjection`). Один билет — ~135 байт в снапшоте и ~170 в
кошельке. Задача `encore_record_ticket` для фаната с 10 000 билетов перегоняла ~5 МБ JSON и BSON ради билета в
150 байт: стоимость события O(n) от истории фаната.

Что показал прогон (50 VU, 10 с всплеска, все брони на `fan-hot`, 8 воркеров):

| Метрика | Горячий фан | Для сравнения: 3a, 8 воркеров |
|---|---|---|
| Слив outbox | не завершился за 900 с, 17 513 из 39 542 задач открыты | 38 с |
| Скорость слива | 120 → 12 задач/с, монотонно падает | ~1800 задач/с |
| CPU бэкенда | 178 % из 200 при Postgres 20 % и Mongo 21 % | 128 % |
| Память бэкенда | 308 МиБ | 14 МиБ |
| Потери проекции | 3 × `category=event_handler`: CAS кошелька исчерпал 16 ретраев, задача завершена успешно | 0 |

`Concert` ограничен 40 местами по построению и не деградировал ни в одном тесте.

## 2. Варианты

| Вариант | Агрегат O(1) | Витрина O(1) | Помог бы в 03b | Меняет формат | Работа |
|---|---|---|---|---|---|
| 0. Паллиативы: точечный `$set`, сжатие снапшота, реже снапшоты | нет | нет | почти нет | нет | мало |
| A. Отменённые билеты не хранить целиком (множество `booking_id`) | только churn | нет | нет (в 03b все билеты активны) | снапшот | мало |
| B. Витрина «документ на билет» (`fan_tickets`), собственный `EventHandler` | нет | да | наполовину | ответ кошелька внутри тот же | средне |
| **C1. Агрегат на пару «фанат + концерт»** | **да** | **да** | **полностью** | `aggregate_id`, база с нуля | небольшая |
| C2. Lifecycle по времени: архивирование билетов прошедших концертов | да | да | полностью | новые события и концепты | много |

C1 выбран как самое маленькое из полных изменений: домен `Fan`, wire-форматы событий и снапшота, `ViewProjection`,
rebuild и verify не трогаются; меняется только то, какой поток загружают два обработчика задач, у них `concert_id`
уже лежит в payload. Кросс-концертных инвариантов у `Fan` нет (лимит билетов R6 проверяет `Concert`), поэтому домен
ничего не теряет. Вариант A остаётся возможной гигиеной модели, отдельным решением.

## 3. Что изменилось в коде

| Где | Что |
|---|---|
| `domain/shared/ids.rs` | `FanLedgerId` (`new`, `parse`, `fan`, `concert`, `id_range`), разделитель `:` не входит ни в один алфавит id |
| `application/fan.rs`, `application/workflows.rs` | `FanApp::execute(&FanLedgerId, …)`; `run_chain_step` строит журнал из `fan_id` и `concert_id` шага |
| `application/fan/views/fan_wallet.rs` | `fan_id` документа — из разбора `aggregate_id`; форма документа без изменений |
| `application/ports.rs`, `infrastructure/mongo/view_repository.rs`, `testing.rs` | `ReadModelStore::list_range(lower, upper)` — диапазон по `_id`, индекс не нужен |
| `application/fan/wallet.rs` | `ReadModels::wallet_of(&FanId)`: объединение журналов диапазона `[fox:, fox;)` |
| `presentation/http/fans/wallet.rs` | `GET /api/fans/{fan_id}/wallet` → `{ fan_id, ledgers: [{ concert_id, version, last_sequence }], view }` |
| front-end | сортировка билетов по `changed_at` (sequence — per ledger), `lib/ledger.ts` для фильтров X-ray, типы, i18n |
| сайдкар | без правок: запросы generic, `/inspect/mail/{fan_id}` фильтрует по `to_fan_id`; poller показывает первые 100 документов `fan_wallets`, теперь это журналы |

Следствия: `aggregate_id` потока `Fan` и `_id` кошелька несовместимы со старыми данными — dev-стек пересоздаётся
(`make reset`). Снапшоты `Fan` при `ENCORE_SNAPSHOT_EVERY = 10` практически не возникают: в журнале не больше
`ticket_limit` билетов и вдвое больше событий.

Выводы. Горячий фан перестал быть особым случаем: его слив совпадает с `03a-w8` по времени и по форме кривой,
память бэкенда вернулась к норме, потерь проекции нет, `verify` зелёный (функциональный `smoke.sh`). Контрольные
серии (один стрим, анонсы, разброс броней) не изменились в пределах шума десятисекундных окон на общем хосте
(до ±10 %, разнонаправленно): C1 ничего не стоил пути API. Разброс на сливах `03a` (+11…+31 % задач/с) — дисперсия
коротких сливов на 10–30 с, не эффект изменения.

Дополнение, тот же день: перераспределение 16 ядер (бэкенд 4, Postgres 4, Mongo 3, k6 3 вместо 2 / 6 / 2 / 2,
прогоны `bal-*`). Брони на 100 VUs: 3463 → 4325 req/s, на 200 VUs снова плато 4245 при p50 46 мс; анонсы
7295 → 7385, на 200 VUs 7287. Ни один контейнер при этом не у потолка: бэкенд 66 % квоты, Postgres 46 %, Mongo
48 %, k6 35 %. Удвоение CPU бэкенда дало +25 % броней и ничего анонсам — потолок задаёт общий пул из 10 соединений
(около 2.3 мс транзакции брони и 1.4 мс анонса на соединение), а не CPU и не генератор нагрузки. Следующий
эксперимент — размер пула 20 и 40 (параметр `connect_pool` в cqrsx).

Оговорки. CPU базовых прогонов снимался `docker stats` через эмуляцию podman раз в 2–3 с, CPU `c1-*` — потоком
libpod раз в секунду; второй метод ловит пики выше (например, бэкенд 131 % → 174 % на одинаковом `02b-vus100`),
поэтому CPU между партиями сравнивать нельзя, память (cgroup `memory.peak`) — можно. Два прогона первой партии
(`02b-vus100`, `03a-w2`) попали на внешнюю нагрузку хоста (RPS всплеска −24 % и −81 % при неизменной скорости
слива в том же прогоне) и были повторены.
