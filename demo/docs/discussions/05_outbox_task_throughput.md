## 1. Контекст

Вопрос, с которого началось обсуждение: «outbox работает медленно, потому что мы достаём из него данные раз в
400 мс?» Ответ: нет. 400 мс — это poller сайдкара для X-ray, к outbox он не относится. Интервал опроса outbox —
300 мс (`OUTBOX_POLL_INTERVAL_MS`), и он не ограничивает пропускную способность. Ниже — почему, что ограничивает
на самом деле и какие правила для задач из этого следуют.

Измерено на изолированном стенде (всплеск броней 10 с при 50 VU, затем слив очереди; почтовый сервис —
заглушка без задержек):

| Воркеров (`OUTBOX_WORKER_CONCURRENCY` = `OUTBOX_QUEUE_CAPACITY`) | Слив, задач/с | Слив всплеска | RPS API во время всплеска |
|---|---|---|---|
| 2 (дефолт демо) | 611 | 134 с | 3355 |
| 8 | 1803 | 38 с | 3065 |
| 32 | 2422 | 15 с | 2264 |
| 8, все брони на одного фана | 22 (падает 120 → 12) | не слилась за 900 с | 2379 |

Бронь порождает две задачи (`encore_record_ticket`, затем `encore_send_e_ticket`), так что 611 задач/с — это
около 300 броней/с сквозной пропускной способности против ~3300 броней/с, которые принимает API.

## 2. Как устроен цикл выборки (`cqrsx/src/task/runtime/supervisor.rs`)

Один producer на процесс. Он забирает задачи по двум триггерам:

- по тику интервала (`poll_interval`, 300 мс) — заодно восстанавливает протухшие lease;
- по сигналу `capacity_available` — его шлёт воркер, освободивший слот.

Размер выборки — `buffer_capacity − queued`, запрос `SELECT … ORDER BY available_at, id LIMIT $n FOR UPDATE SKIP
LOCKED` плюс `UPDATE` с lease, одним statement. Пока в очереди есть работа, цикл выглядит как «claim → выполнить →
зафиксировать → сразу claim»: тика никто не ждёт. Если бы темп задавал тик, два воркера давали бы не больше двух
задач за 300 мс — около 7 в секунду; измерено 611.

На что интервал влияет на самом деле: на задержку подхвата при **пустой** очереди. Новая задача ждёт ближайшего
тика (до 300 мс); вторая задача цепочки подхватывается сразу, потому что завершение первой освободило слот.
Итого интервал — нижняя граница сквозного лага «бронь → письмо» на малой нагрузке, а не потолок throughput.

## 3. Из чего складывается стоимость одной задачи

Последовательные обращения к базам на примере `encore_record_ticket`:

| Шаг | Куда | Обращений |
|---|---|---|
| claim (общий на пачку) | PostgreSQL | 1 |
| загрузка агрегата `Fan`: снапшот + события после него | PostgreSQL | 2 |
| CTE: событие `TicketRecorded` + задача `encore_send_e_ticket` (+ снапшот каждое 10-е) | PostgreSQL | 1 |
| проекция `fan_wallets`: прочитать документ, записать документ (CAS по версии) | MongoDB | 2 |
| settle (completed / retry) | PostgreSQL | 1 |

Около 3 мс на задачу. Пропускная способность = воркеры ÷ латентность задачи: 2 ÷ 3 мс ≈ 600/с, что совпало с
замером. Рост от 2 к 8 воркерам — в 3 раза, от 8 к 32 — в 1.3: воркеры, HTTP и poller делят один пул на
10 соединений (`cqrsx/src/postgres/pool.rs`, размер зашит), больше 10 операций с базой одновременно не бывает.
Второе следствие того же пула: во время всплеска RPS API падает на треть при 32 воркерах.

Отдельный случай — горячий фан: стоимость задачи растёт линейно с размером состояния агрегата и документа
кошелька (см. обсуждение про рост `Fan`), поэтому слив не сходится вообще. И три записи `category=event_handler`
в логе: проекция кошелька исчерпала 16 немедленных ретраев CAS, при этом команда и задача завершились успешно —
витрина `fan-hot` расходится с журналом до следующего rebuild.

## 4. Правила реализации outbox task — к обсуждению

1. **Задача стоит O(1) от истории.** Обработчик не должен загружать или переписывать растущее состояние.
   Если агрегат или витрина растут без границы, это проблема модели, а не настроек outbox
   (решено для `Fan`: [`06_fan_ledger_growth.md`](06_fan_ledger_growth.md), D-14).
2. **Обработчик не ждёт внутри.** Ожидание (сон; `wait_for_unlock` до 3 с, который здесь был, удалён вместе с замком кассы, D-16 эпика 03)
   занимает один из C воркеров. Лучше вернуть `Retry { retry_after }` сразу.
3. **Успех задачи ≠ обновлённая витрина.** Снято эпиком 03: витрины ведут процессоры от закладки, коммит задачи
   больше не ждёт витрину и не узнаёт о её сбое (`CommittedWithEventHandlerFailure` удалён в 03/05); отставание
   и сбои видны в статусе проекций.
4. **Бюджет соединений.** Либо отдельный пул для воркеров, либо правило вида «C ≤ половина пула». Иначе воркеры
   отбирают соединения у API, а API — у воркеров.
5. **Дефолты.** Для стенда 8 воркеров выглядят разумно; дефолт 2 выбран ради демо-темпа с хаос-почтой
   (0.6–1.8 с на письмо), а не ради производительности. Интервал опроса трогать только ради idle-лага.
6. **Пакетная обработка не нужна.** Claim уже пакетный; выполнение по одной задаче — это и есть at-least-once
   с индивидуальным lease. Батчить письма ради throughput смысла нет: узкое место не в них.
